# 建模复盘与改进

目标是核对关联需求是否完成验证、判断已确认改进的效果，并在保持源忠实、业务覆盖和
独立验收标准的前提下，缩短获得合格模型的总时间。
质量是约束，时间是优化目标；值得增加的澄清、建模或验证工作，应说明它能解决的质量缺口
及可能减少的返工。不要用一个加权总分让提速抵消质量退步。

这是技术宿主侧的复盘技能，不挂载给生产建模角色。默认读取保留证据、更新相关验证状态
及优化台账、输出建议与验证计划；用户明确要求只读时仅提出建议变更。
用户已要求实施时，在已有授权内更新归属需求、实现或权威提示，并按仓库要求验证。
本技能不另授 semantic start、平台写入或验收权限，不解除已有暂停。
实时推进与安全接续交给 [modeling-dev-loop](../modeling-dev-loop/SKILL.md)，不建立第二条监督链。

## 需求验证与跨轮改进闭环

每次先读用户指定或既有的独立优化台账；本仓库默认使用
[优化跟踪台账](../../docs/delivery/modeling-retrospectives/optimization-tracker.md)。
它与单轮报告分开，跨轮续写，不在每个 run 中另建一份。首次无台账时，在用户确认优化点后
按[记录格式](references/report-template.md#已确认优化台账记录格式)建立；未确认建议只留在报告。

先结合本轮任务、实际采用的变更和台账引用，定位关联需求，包括并非来自优化台账的相关
需求；不默认遍历全项目。按各需求原定验收条件核对实现版本、场景覆盖、验证层级与结果，
工程完成不等于验收完成，不要求所有需求都经过真实建模或全业务语义验收。

在权威需求文档的既有状态中分别记录实现进度与验证结论，并指向交付／测试证据及剩余缺口：

| 验证状态 | 判定依据 |
| --- | --- |
| 未验证 | 尚无适用的验收证据 |
| 部分验证 | 部分约定条件已通过，仍有未覆盖或缺证据项 |
| 验证通过 | 该需求当前约定的验收条件全部满足 |
| 验证未通过 | 适用证据显示至少一项约定条件明确不符合；同时保留其他已通过项 |

通过或失败都注明范围／层级、采用版本和证据；缺证据不能判失败。有仍适用的历史证据时
可复用，本轮未触发场景不撤销既有通过结论；版本／范围变化或新反证影响结论时说明理由
并保留历史。设计审阅、开发测试、独立功能验收和真实语义结果各自注明，不相互替代。

需求文档保存验收结论，优化台账保存问题、原预期与改进效果，通过编号关联，不复制另一套
需求状态。一个需求与优化点可多对多关联，局部优化关闭不代表整条需求验证通过，需求通过
也不自动证明额外的提速预期。这里只核对已有验证证据并指出缺口；所需测试、独立验收仍由
原流程执行，复盘者不自行启动运行、替代独立裁决或增加完成门。

1. **确认后保存。** 为每个已确认项保留稳定编号（已有需求／问题编号可复用）、确认依据、
   原问题、预期效果与质量约束、验证方法、关联需求／实现、状态和历次证据。不得把分析者
   的建议当用户确认；用户已在当前会话确认时直接登记，不重复请示。必须与用户细化的条目
   保留该条件，确认方向不等于授权 Agent 自行补全方案。未给定的阈值或决定不自行补造。
2. **再验证旧优化项。** 完成上述需求核对后，结合交付记录与本轮实际加载身份，确认
   实现是否进入本轮、相关场景是否发生，再对照保存的原预期和质量约束。
3. **更新状态并保留历史。** 未实现／仍待细化为“已确认待处理”；实现后为“已实现待实测”。
   本轮未采用、未触发场景、不可比或证据不足时保持待实测并写明原因，不能判为效果失败。
   本轮采用且证据表明未达预期／发生退步时标“待调整”，提出原需求调整或关联新建议；
   新建议经用户确认后再登记，不自动另立需求或改变原预期。达到原预期且质量约束满足时
   标“已关闭”，记录验证轮次、采用版本和证据。缺决定性证据不能关闭；只关闭该项原定范围，
   不强行要求每项都取得全业务 PASS，也不缩小原预期。后续反证可重开原项，保留旧关闭记录。
4. **再发现新项。** 完成旧项复核后再分析新问题，核对已有编号，区分旧项未生效、效果不足
   和真正新增问题，不重复立项。默认报告顺序为“旧项验证 → 待调整项 → 新建议”，更新本次
   需求验证状态及台账变化。默认先呈现关联需求验证，再呈现上述优化结论。
   正常复盘按本闭环更新相关状态；用户明确要求只读或不更新记录时，仅输出建议变更，
   不写需求或台账。没有新优化也是有效结论。

台账仅存可共享的通用结论、必要定位和状态，不复制隐藏题、答案或私有诊断；受限原件留在
原权限目录。调用本技能不授权实现建议或启动下一轮建模，后续运行仍由用户和既有流程控制。

## 选择范围与证据

1. 确认仓库根目录，读当前 [AGENTS.md](../../AGENTS.md) 和本次适用的
   [版本化需求](../../docs/requirements/)。当前效率口径入口为 R4.3-001 与 R4.0-021，
   具体时间目标、题目范围、角色和工具以所分析轮次及当前权威合同为准，不硬编码为所有场景规则。
2. 用户指定 run、时段或问题时遵循其范围；否则从最近几轮相关任务开始，包含失败、中止
   和未完成样本。已有证据足以支持决定时停止扩展，不全量扫描历史，也不为了凑样本启动运行。
3. 从摘要定位原始证据，按需使用 [证据导航](references/evidence-map.md)。将同一业务任务的
   fresh starts、恢复、修模与重验串成完整时间线，另列各 run 的状态；不要只取最后成功片段。
4. 记录输入资料、范围、题集及评分版本、模型与 effort、Task/Profile、代码和提示身份；
   区分从零建模、生产恢复与只读验收。不可比样本可以解释失败机制，不能直接计算优化增益。
5. 按台账复核上次建议和当前交付，区分当时可用能力、实际行为与本次建议改变的步骤。
   历史问题已经修复时优先验证效果；实际 run 加载身份未知则标待证，不把当前文件或工程
   测试结果当旧进程已生效，也不从“有工具却未使用”直接推断 Agent 忽略提示。

## 同时看质量与时间

| 维度 | 需要回答的问题 |
| --- | --- |
| 模型质量 | 业务定义、条件、计算口径、关系和共享身份是否正确？范围是否完整，未知是否忠实？候选、计划、应用与消费中的缺口分别在哪里？ |
| 消费质量 | 冻结完整题集实际通过多少？必答点缺在模型、检索还是答案综合？证据及分页是否完整？ |
| 时间 | 从输入就绪且获准开始，到完整独立 PASS 和必要收尾用了多久？首条可消费业务链、返工和等待在哪里？ |
| 辅助计数 | 哪些角色往返、重复读取、dry-run、输入体积或唤醒能解释瓶颈？不要将计数当质量或语义 start 数。 |

复用 [同轮效率记录](../../modeling_team/references/efficiency-round-record.md) 和已有事件。
尚无完整 PASS 时报告已观察时间、真实结果和未完成项，不能称作成功性能基线。
仅有摘要或情境材料中的通过数时，写“报告记载通过，独立资格未核验”；原始报告、冻结
身份与读取证据未核对前，不把该记载称为已证实的独立 PASS。
修模、重验及同一任务的重启不重置总起点；并行区间按墙钟并集，累计 Agent 时间另列。
正常推理、读取、调度、输入纠错、质量返工及人工等待保留在总时间内。
有证据阻断关键路径的故障可另报去重后的扣除估算，不能冒充无故障实测。

跨度、进程存活时间和意图到回执间隔均不等于有效语义工时、数据库 CPU 或单次 HTTP 时间。
未被分类的余时不能全部视为可删除；并行等待减少也不必然等额缩短总时间。
缺失数据写 unknown，估算注明依据，不补造 token、费用或精确节省时间。
有效语义时间比例仅在分子、分母及活动证据充分时计算，按 AGENTS.md 处理；不以分类不明
为由新建监控平台或强制逐工具打点，也不让本复盘成为每轮启动的前置门。

## 从现象定位最窄原因

每项发现形成：**现象 → 原始证据 → 对时间或质量的影响 → 原因及把握 → 最小改动**。
明确区分观察事实、因果推断和待验证假设；出现频率高不等于根因已确定。
按同一对象、操作及明确依赖关联事件，时间相邻不能证明因果，也不能将无关异常扩展为
全局检查条件。建议中的新回执字段或检查步骤同样须有当前合同缺口与成本收益依据。

- 第一失败层沿用 `modeling-quality`、`platform-contract`、`collaboration/routing`、
  `runtime/infrastructure`。证据不足写尚未定位；同时记录修改对象为实现、prompt-contract
  或流程设计，不增加另一套失败分类。“平台故障”等笼统描述不能区分平台合同与基础设施，
  在缺具体失败证据时保留首层未确定，不为了填写类别猜测。
- 语义消费不足进一步检查：获准材料是否支持该事实、模型是否表达、平台实际返回什么、
  Consumer 是否使用、Judge 依据是否有效。粗粒度失败标签不能独立证明模型缺失。
  已返回但未使用时检查消费表达；尚未返回时区分检索与模型证据，保留未确定项。
- 先定位具体阶段：候选表达、计划转换、批准、应用、检索或回答。关系晚应用不等于晚设计，
  材料不可读不等于未产出，控制层 resume 不等于受阻业务已获准继续。解释建议时用
  “当前做法 → 建议做法”说明改变哪一步；已有切片、工具或提示不重新作为新增能力提出。
- 重复读取、催办、唤醒和等待先查正常用途及本次触发是否合理；它们可能用于发现任务
  丢失、异常停止或交付失败。沿问题、处理回复和后续实际动作核对，不仅看 issue 数量或
  pause/resume 名称。没有多余执行、实际阻塞或质量损害的证据，不建议削减必要催办。
  同时检查过早停止读取、遗漏限定条件等质量问题；必要的语义工作可以增加。
- Agent 兜底先评估当前实际风险与收益、整轮累计调用／读取／推理／协作成本，以及提示
  分支和维护复杂度。低成本、简单且有效的兜底可以保留；高成本或复杂兜底优先考虑平台
  修复或已有确定性能力。未知成本说明依据不足，不默认 Agent 不能兜底，也不为每种假想
  平台故障增加检查。区分成功回执处理、异常对账和业务语义读取，不将单例取舍变成通用禁令。
- 守卫导致阻断时按 AGENTS.md 的 T0 复核必要不变量和上层覆盖，考虑删除或降级重复防御；
  保留授权、dry-run/application、原子性、必要异常恢复与真实语义消费证据。具体兜底与
  读取取舍按当前用户决定和归属需求处理，不以优化名义改变验收标准或绕过待讨论约束。
- 改动落到当前责任面：实现不符合同则修实现；输入或角色说明有歧义则修权威提示；
  正常等待不自行归为流程缺陷，只有证据支持时才提协作调整。只改证据指向的环节，
  不附加通用编排或治理机制。

## 输出和验证优化建议

使用 [报告模板](references/report-template.md) 按任务大小裁剪。默认优先给最有价值的几项，
不要凑满条数。每项包含证据引用、当前状态、原因及把握、最小改动与责任面、时间收益假设、
质量影响、验证方式和退步处置。节省分钟数或百分比须有可核对计算，否则只说明方向与待测项。

优先选择同时改善质量和时间的项，其次是保持质量的提速项；增加时间以补必要质量的项说明
代价。结合影响、证据把握、实现成本和影响范围排序，不追求虚假的精确评分。
允许结论为“保持现状”“先验证已实现改进”或“补一项决定性证据”。

验证先选最小可比较切口：确定性数据搬运看合同及完整性，提示与协作看实际生效及行为，
语义质量看获准的独立消费和裁决。前后保持范围、评分及关键配置可比；同时改变多个因素时
披露混杂，必要时分项验证，不自动扩大为全面基准或强制多轮 A/B。
局部工程通过、真实语义效果、端到端达标和重复性分别结论；单次改善只支持本次范围。
不缩小分母、不删难题、不改变未知口径、不降低评分来达标，不拼接不同尝试的通过题。

按跨轮闭环更新台账；证据改变判断时，保留原结论和修正理由，修正当前建议，不让已撤回
建议继续作为待实施项。质量退步时提出修正，已写入模型按现有恢复合同处置，不盲目回滚。
获准实施时将通用纠正落到真正被加载的权威提示或实现，不能只留在复盘报告或临时提醒中。

## 证据与完成边界

运行原件、冻结题池和历史裁决只读保留；报告写入既有宿主工作目录或用户指定位置，
分清可交付通用建议与含隐藏信息的私有分析。默认先读元数据和公开证据，只有定位必要且
在获准范围内才读隐藏材料；不能将隐藏题、答案、评分细节或其变相提示带回生产。
已暴露材料按当前合同标记，不追称严格盲测；复盘者不自任被其生产或修复过的 run 的最终验收者。

当关键瓶颈、证据限制、建议顺序及验证计划已明确时完成本次复盘，不为填满报表继续取数。
资料缺口只阻止依赖它的判断，先交付已有证据支持的结论。无授权的真实验证列为待证，
按现有授权继续可做工作，不把“提出优化建议”自动扩大为启动建模。
