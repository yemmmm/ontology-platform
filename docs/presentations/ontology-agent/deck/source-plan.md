## 二、先明确的内容口径

1. **哲学中的 ontology 与工程中的 ontology 分开讲。** 前者研究存在以及存在者的类别和关系；工程本体将一个领域中的概念及其含义、关系等显式表达，以便共同理解和机器处理。工程本体不是对哲学问题的直接答案。[哲学来源](https://plato.stanford.edu/entries/logic-ontology/)
2. **Palantir 是重要应用案例，不能写成 ontology 的发明者。** Foundry 将 Ontology 用作连接数据、业务对象和操作的组织运行层。可以说它展示了本体在企业软件中的产品化应用；“近几年由它带火”缺少本次可量化的传播证据，不作为事实断言。[Foundry 官方说明](https://www.palantir.com/docs/foundry/ontology/overview/)
3. **“本体驱动 Agent”作为架构思路介绍。** Palantir 官方已有通过 Ontology MCP 向 Agent 暴露对象、动作和查询能力的实现；据此可以介绍“用显式业务语义约束 Agent 的理解和工具使用”。“所有 Agent 的新范式”“行业已经形成统一标准”均不采用。后一项架构概括是本演示的归纳。[Ontology MCP 官方说明](https://www.palantir.com/docs/foundry/ontology-mcp/overview/)
4. **区分 RDF、RDFS、OWL、SPARQL。** RDF 是图数据模型；RDFS 提供基础类型和层级词汇；OWL 表达更丰富的形式化语义；SPARQL 用于查询 RDF。它们各有职责，不能统称为本体数据库，也不能把 OWL 直接说成业务规则执行引擎。[RDF Primer](https://www.w3.org/TR/rdf11-primer/)、[OWL Primer](https://www.w3.org/TR/owl2-primer/)、[SPARQL Overview](https://www.w3.org/TR/sparql11-overview/)
5. **方法能力与项目现状分开。** 本体技术可以支持形式推理，但 OntoWeave 当前按 R4.0-025 阶段性退役 OWL 自动推理、SHACL 专用校验和业务规则脚本化合同。仍保留普通业务条件、分类、关系、确定性写入、受治理读取和独立业务验证。这里不承诺自动推理重新上线。
6. **案例全部为虚构教学材料。** 退货时间窗、商品范围、退款条件均为模拟商家规则，不表述为行业通例或法律规定。案例推演不冒充真实平台运行结果或性能对比。
7. **平台名称统一为 OntoWeave（织义）。** 当前仓库已正式更名；封面及开场讲稿只使用新名称，不再附旧名称。
8. **共享知识、形式语义和自动执行分别说明。** 共享资料并不必然需要本体；业务条件进入语义模型后，也不自动变成可执行规则。页面明确哪些内容是关系、哪些是业务说明，哪些计算和操作由外部工具或业务系统完成。
9. **项目状态按时间和范围陈述。** P25 使用截至 2026-10-14 的需求与交付记录，分别呈现已实现能力、有界历史验证和待验证范围。旧场景通过、近期部分验证及本次教学预期分别保留，不合成为全平台质量结论。

### P04｜Agent 怎样完成一个业务任务

- **本页目的：** 保留首页问题与五步机制，同时让“相似政策的理解与选择”出现在实际任务中。
- **需要呈现：** 当前会话选中 A101。订单查询返回归属 A 店、普通商品、未使用声明和签收、验收、审批状态。检索同时出现 A 店签收后七天与 B 店付款后七天两份完整政策。
- **步骤与本例操作：** ①理解请求：分别判断申请资格和退款前提。②查业务事实：A101 属于 A 店，签收 10-01 10:00、普通商品、声明未使用；验收未开始、审批未申请。③检索候选政策：两份相似政策同时出现，需辨清适用范围。④理解政策并判断：先选 A 店 RET-DEMO-v1，再使用签收起点，拟申请 10-06 10:00，间隔 120 小时；可申请，退款前提尚未满足。⑤解释与继续：按声明可申请，退款前仍需验收与批准。
- **呈现方式：** 五个横向步骤，保留具体查询结果和后续判断。标明全部虚构、2026 年、UTC+08:00，本次没有提交申请或退款。
- **讲解深度：** 理解压力来自政策相似但适用商家、时间起点不同，不靠拿掉已经确认的信息制造歧义。订单归属、申请与退款阶段都需要明确关联，不能只按相似文字和数值判断。
- **承接下一页：** 两份都写“七天内可退”的政策，为何会给同一笔订单带来相反判断？

### P05｜两份相似政策，两个判断

- **本页目的：** 展示检索命中多份相似政策时，Agent 需要理解适用性和条件含义。
- **需要呈现：** A 店 RET-DEMO-v1 与 B 店 RET-B-DEMO-v1 均要求普通商品、客户声明未使用、连续 0—168 小时且含边界；A 店按签收起算，B 店按付款起算。A101 属于 A 店，付款 09-28 10:00、签收 10-01 10:00、拟申请 10-06 10:00，全部为 2026 年 UTC+08:00。实际应用 A 店政策得到 120 小时、可申请；错套 B 店政策会得到 192 小时、超时。
- **呈现方式：** 顶部为同一订单事实；下方并列两份完整政策，分别显示商家、政策身份、时间含义、计算与结论。HTML 和 PDF 同时可见，不再切换两种假设。
- **讲解深度：** B 店政策只用于展示错用的后果，并不适用于 A101。此处不是同一政策自相矛盾，也不声称真实 Agent 已经答错。申请资格与退款前提仍分别判断，后续完整案例继续采用 A 店政策。
- **承接下一页：** 怎样帮助 Agent 正确理解并区分这两份政策？

### P06｜怎样让 Agent 分清相似政策

- **本页目的：** 六种方法均聚焦 P05 的具体理解问题。
- **需要呈现：** 提示与示例明确商家、范围、起点的比较维度；RAG 取得完整正文与商家、版本、出处；微调用相似政策样例学习辨别及缺信息时补问；工具提供订单归属、日期字段及含义，并做相应计算；专家在范围、含义缺失或冲突时确认；本体将政策、商家、时间起点及申请条件显式关联，供不同任务引用。
- **呈现方式：** 六项以两行三列的简洁文字区展开，每项说明在 A/B 政策情境中怎样帮助理解，不再标注“第几步的作用”。
- **讲解深度：** 方法可以组合，本体是知识模型，建模与复用是方法。微调不提供当前实时政策，算出日期间隔也不等于选对政策。已给足的业务信息无需重复澄清；本体也需建对、读全和验证。
- **承接下一页：** 已确认的商家、起点和阶段含义，怎样在多个应用中持续保持一致？

### P09｜什么是本体（Ontology）

- **本页目的：** 先建立工程本体的直观含义，再简要消除哲学译名的混淆。
- **需要呈现：** “本体是一套可共享的领域定义：明确有哪些概念、它们是什么意思、怎样关联，以及有哪些约束。”以退货申请的定义、针对订单项的关系、政策适用范围和计时起点等条件为例。
- **呈现方式：** 上方为通俗定义，下方三个文字区分别解释概念、关系与条件。末尾仅用一处说明本体论关注存在及其类别等哲学问题，本演示的本体指知识工程模型，不单独展开哲学史。
- **讲解深度：** 依据 Gruber 与 Noy/McGuinness，解释显式、领域及共享的含义；机器可解释的表示支持程序引用。形式化程度按用途选择，业务条件写入模型不自动变成可执行规则。本体是模型产物，建模方法论指导建设、验证与维护；本体驱动 Agent 是架构思路。中文译名存在交叉，这里只是明确演示内用词。

### P10｜Palantir 如何将 Ontology 用于业务

- **本页目的：** 用产品应用建立直观印象，并向不了解 Palantir 的听众介绍公司背景。
- **需要呈现：** Foundry 将分散的数据连接到业务对象、属性与关系，并提供受权限控制的查询和操作，让人员、应用与 Agent 围绕共同含义工作。右侧保留 Palantir 是 2003 年成立的美国数据分析和 AI 软件公司，面向政府与企业；2017 年与 Airbus 合作推出 Skywise，2025 年营收约 44.75 亿美元、同比增长 56%。
- **呈现方式：** 左侧按业务数据、业务含义、应用与操作三层解释产品用法，右侧为公司背景及两项有年份的成果，不再把哲学、工程定义和公司介绍画成一条技术演进线。
- **讲解深度：** 参考 Palantir 2022 官方博客与当前 Foundry 文档，具体产品运行层不能作为所有工程本体的统一定义；Palantir 是应用者而非发明者，OntoWeave 不据此宣称同等能力。主要平台 Gotham、Foundry、Apollo、AIP 放在讲稿介绍。营收说明公司整体规模，不归因于 Ontology 单项技术。
- **承接下一页：** 用退货业务的关系骨架展开刚刚介绍的概念和关系。

### P12｜本体中的基本表达

- **本页目的：** 给出足够专业、又不依赖代码背景的阅读方法。
- **需要呈现：** 概念或类、个体、属性、关系、分类层级。例子包括“退货申请是一类售后申请”“申请 R001 属于退货申请”“申请关联订单项”“申请时间是日期时间值”。再用“RET-DEMO-v1 是一份具体退货政策”说明语义层也可有个体，不必把业务行搬入平台。补充规则说明中的条件、例外、范围与未知。
- **呈现方式：** 在上一页的小范围子图上逐一高亮，每次只解释一种表达；用不同线型区分“属于某类”“是某类的子类”“业务关系”。
- **讲解深度：** 名字相似不等于语义相同；同一资源应有稳定身份；业务角色不等于登录权限。正式分类按实际需要使用，不把每个业务节点都强行设为类。

### P31｜语义怎样连接 SQL 与 API

- **本页目的：** 把语义层与外部执行的接口讲实。
- **需要呈现：** 用数据库查询语言（SQL）取得订单事实：签收时刻映射到 `orders.signed_at`，商品类别映射到 `products.category`，订单项通过 `order_items.order_id` 和 `product_id` 连接。未使用声明来自客户本次输入；验收、审批及退款状态来自外部售后接口。提交退货申请与执行退款分别映射到不同接口。来源与编码使用第 4.3 节的统一定义。
- **呈现方式：** 上半部为“语义字段 → 数据映射 → SQL 查询 → 结果”；下半部为“业务动作 → 前提与权限 → 外部 API → 业务回执”。查询和执行两条线分开，不让一条箭头从本体直接指向退款成功。

- **示例边界：** SQL、工具和 API 均为教学设计，没有实际接入或调用退款系统。

### P35｜FAQ：什么时候值得使用本体

- **本页目的：** 回答技术选型与投入的常见疑问。
- **需要呈现：** 以下 5 问及简短回答。
  1. **已经有 RAG，还需要本体吗？** 如果文档检索已能稳定回答问题，可以继续使用；跨对象、跨任务的关系需要明确复用时，可试用本体作为结构化知识来源，再用同条件对照判断收益。

## 四、模拟业务的一致性底稿

以下仅是演示所用的虚构资料，便于审核前检查逻辑。主体分配到 P27—P34，语义读取样本在 P24 先行展示，维护例另用于 P37；不整表复制到一页。

### 4.1 范围与政策

- 模拟商家：A 店；模拟政策版本：`RET-DEMO-v1`，对本例全部订单适用。仅单件商品整件退货，商品款整额退款；运费、部分退款、促销分摊不在范围内。
- 申请资格要求商品类别为普通商品、客户声明未使用且时间条件满足；定制商品不适用本例政策。申请时采用客户声明，商品实际状态后续由仓库验收确认，二者分别记录。
- 申请间隔 = 提交申请时刻 − 签收时刻；本例要求 `0 ≤ 间隔 ≤ 168 小时`。全部时间为 UTC+08:00；教学比较使用拟提交时刻，真正提交时由业务系统重新检查。
- 必要事实缺失时保留未知，不认定满足，也不等价于确认不满足。
- 可以申请不等于退款获准；退款执行还需退回验收通过、客服批准以及外部系统授权，且不得重复退款。
- 示例假设订单归属、当前可访问范围和无重复申请已经由业务系统确认；本体语义授权不能代替这项检查。
- 事实统一取自模拟判断时点的输入。区分“允许申请／申请已提交／申请已受理／具备退款条件／退款请求已受理／退款已完成”；各阶段由对应事实或业务回执支持，不因前一阶段成立就推断后一阶段。

| 订单所属商家 | `orders.merchant_code` | 教学查询明确返回 A 店归属，用来选择适用政策 |
| 付款时刻 | `orders.paid_at` | P05 对照输入；A 店政策计算仍使用签收时刻 |
| 订单签收时刻 | `orders.signed_at` | 与下单或付款时刻不同；空值按缺失处理 |
| 订单包含订单项 | `order_items.order_id → orders.id` | 解释关联含义和查询连接 |
| 订单项关联商品 | `order_items.product_id → products.id` | 商品分类来自对应商品 |
| 商品类别 | `products.category` | 本例定义 `STANDARD` 为普通商品、`CUSTOM` 为定制商品；不从样例值猜测含义 |
| 拟提交时刻 | 本次模拟输入 `proposed_at` | 本例为 2026-10-06 10:00+08:00；实际提交时由业务系统使用真实提交时刻重检 |
| 未使用声明 | 客户当前输入 `unused_declared` | `true` 只表示客户声明未使用；不等于仓库已核实，缺失时需询问 |
| 售后事实查询 | `GET /order-items/{id}/after-sales-context` | 模拟外部接口，按订单项返回以下验收、审批及退款状态；其合同明确区分未开始与未知 |
| 验收结果 | 响应 `inspection_status` | `NOT_STARTED` 尚未开始、`PASSED` 通过、`FAILED` 不通过；空值表示未知 |
| 客服审批 | 响应 `approval_status` | `NOT_REQUESTED` 尚未申请、`PENDING` 待审批、`APPROVED` 批准、`REJECTED` 拒绝；空值表示未知 |
| 退款状态 | 响应 `refund_status` | `NONE` 无退款、`ACCEPTED` 请求已受理、`SUCCEEDED` 系统确认完成；空值不能解释为无退款 |
| 提交退货申请 | `POST /returns` | 输入订单项、客户声明及申请说明；受理后取得申请标识；重检归属、时间、重复申请及权限 |
| 执行退款 | `POST /refunds` | 输入申请标识；检查业务前提、权限和防重复。`ACCEPTED` 仅表示受理，最终结果由后续状态查询取得 |

这些 API 不是 OntoWeave 新增接口；本次也不实现 SQL adapter、退货系统或支付连接。

### 4.4 从语义读取到 A101 答案的统一样本

供 P24、P30—P32 共用。以下是教学内容与阅读布局，不是实际 API JSON、平台新增字段或运行回执。

| 读取内容 | 教学样本 | 在判断中的作用 |
| --- | --- | --- |
| 身份与结构化关联 | 政策 `RET-DEMO-v1`；关联普通商品、退货申请、退款动作及所需数据映射 | 消费者可从政策找到适用对象及相邻业务前提 |
| 普通业务说明：申请条件 | 普通商品；客户声明未使用；`0 ≤ 提交时刻 − 签收时刻 ≤ 168 小时` | 说明政策口径，未自动编译为可执行规则 |
| 普通业务说明：退款条件 | 退回验收通过、客服批准；执行仍受业务系统授权与防重复检查 | 区分申请资格和退款执行条件 |
| 数据与输入映射 | 签收取 `orders.signed_at`，类别取 `products.category`，声明取客户输入，售后状态取外部接口 | 指明应取得哪些事实及其来源，不把本次订单事实写进语义模型 |
| 适用范围与未知处理 | 本例单件商品整件退货、商品款整额退款，v1 对三例适用；缺失必要信息需补读或询问 | 限定结论范围，说明无法判断时怎样继续 |
| 读取范围与状态 | 展示查询的授权范围、已返回的相关定义、分页／截断提示；教学推演假设已取得上述必需内容 | 指导是否补读，不证明全库完整，也不证明业务判断正确 |

模拟资料由政策说明、业务确认、字段说明和接口合同组成；业务确认补足时间起点、声明口径、状态含义及未知处理。教学材料中的依据标记方便听众逐项核对，不代表平台已提供自动证据追溯功能。

| 步骤 | 执行者及输入 | 本例输出 |
| --- | --- | --- |
| 取得业务依据 | 消费 Agent 按权限读取语义模型 | 上述政策、关系、条件说明与映射 |
| 取得具体事实 | 外部订单／售后查询与客户输入 | A101 的时间、普通商品、未使用声明，以及明确的尚未验收／尚未申请审批状态 |
| 计算时间间隔 | 消费 Agent 调用日期时间计算工具 | 2026-10-06 10:00+08:00 减 2026-10-01 10:00+08:00 = 120 小时 |
| 对照并解释 | 消费 Agent 使用业务条件和计算结果 | 按当前声明可申请；退款前提尚未完成，不能立即退款 |
| 如需实际提交 | 外部业务系统按真实提交时刻重检业务条件与权限 | 本次没有调用或提交；后续回执只能按其合同解释 |

其中“尚未验收／尚未申请审批”由明确状态支持；如果相应读取失败或值缺失，答案改为“暂无法确认”，并指出需要补取的事实。未知与拒绝权限也应区别表达，不能为了补足答案越权读取。

### 4.5 政策变更与维护示例

此例仅用于 P37，独立于 A101—A103 的 v1 判断，不作为已交付的版本管理或自动影响分析功能。

1. **业务负责人确认口径。** 假设 A 店决定将窗口改为 240 小时，并明确从 2026-11-01 00:00+08:00 起提交的申请采用 `RET-DEMO-v2`；此前提交的申请仍按 v1，其余条件不变。生效依据是提交时间，不是签收时间。
2. **维护者与建模 Agent 修订语义。** 将 v2 的时间窗和适用范围明确表达，保留理解旧申请所需的 v1 业务定义；核查申请、退款条件、数据及接口映射的关联。政策版本的业务表达不等于平台支持同一资源的任意历史版本读取。
3. **外部系统负责人对齐执行。** 确认实际申请接口已采用对应政策及生效口径；语义模型更新不会自动更新外部业务规则。
4. **检查影响并验证读取。** 人和 Agent 沿关联核对客服、仓库、财务消费的问题；由独立验证核对新旧适用范围、240 小时与加 1 秒的边界、缺失提交时间等情况。A101—A103 的原有 v1 结论应保持原义。
5. **记录维护成本。** 分别记录业务确认、语义修订、外部系统对齐及验证的投入，与原有文档／规则服务维护方式比较，不预设本体维护一定更省。

## 六、画面与讲解的统一要求

- 延续现有 editorial 视觉风格，重构内容密度与图形，不为换风格重新制作整套设计语言。
- 关系图、流程图、架构图分别使用一致的箭头含义；所有重要关系标动词，分类关系与业务关系使用不同线型。
- 优先单一主图；节点对齐、连线走空白区域，不穿越文字。复杂图按语义层次逐步展开，PDF 展开后仍可阅读。
- 对比页以“同一案例在不同层的表达”说明差异，避免只换名称的装饰图。数据表用于事实记录、明确映射或审核清单；虚构事实始终标为教学输入。
- 页面主层采用“业务问题＋功能说明＋一句结论”，次层保留技术名称、短代码与机制。技术内容服务于已出现的问题，不把框架名称当作解释。详细标准说明、引用和扩展问答进入讲解备注。
- 术语首次出现时说明它做什么：能力问题是检查模型有用与否的业务问题；数据映射连接业务含义与系统字段；受治理读取按权限取得知识并说明读取限制。语言模型与业务语义模型始终区分称呼。
- P11 与 P30、P21 与 P29、P24 与 P32 使用同一骨架并突出新增信息：从认识对象到补齐条件，从方法步骤到实际切片，从读取内容到事实对照与答案。
- 教学案例的政策版本、客户声明口径、时间、外部状态编码和事实来源统一取自第 4 节；P37 的 v2 变更单独标识，不混入三笔订单的 v1 判断。
- 通过演示形态区分“原理示意”“虚构案例”“当前实现”。没有真实读取记录的页面，不制作仿真的运行成功标记。
- 旧 P5 的 SLA 切换、目录描述、图片内文字、讲解备注和 PDF 导出需要一起替换；审核后制作时检查，避免主文改完但隐藏备注仍沿用旧案例。
