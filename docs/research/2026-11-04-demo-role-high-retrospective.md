## 已识别问题逐项定位

### 1. 范围基线、成果引用和完成状态混在一起

**已定位；prompt-contract/技术合同采用问题。** `audit.json` 对照每回合输入和自然 JSON 结果：Coordinator 前两回合、CQ 首回合、Modeler 第二个实际回合，共四次把新计划材料填进输入为 null 的 `basis.scope_ref`。Coordinator 前两次还以 waiting_children 提交已经制作的 scope-plan；当前实现只在 proposed/no_change 路径安装计划。

输入提示有“回显实际 basis”的原则，但没有明确区分“输入执行基线”和“本回合新成果”，也没有清楚给出“计划完成用 proposed，程序接纳后再等待”的状态例子。拒绝仅返回 role_scope_basis_changed，没有附本次 expected/received 和修正位置。GLM 技术字段遵循确有错误，不能全推给程序；但四个回合重复同类错误，说明专业包/反馈不足以稳定自修复。

最小方向：在实际加载的专业包和类型化反馈中明确输入基线、新产物和状态转换，提供一个合法范围提交例子。程序已知且固定的执行元数据不应让 Agent 反复推导；保留真实采用版本、来源和模型基线保护，不以删除版本校验兜底。

### 2. 已存在的公共 CQ 单元被当作冲突身份

**已定位；platform-contract，兼有提示缺口。** `role_work._install_scope` 先拒绝保留身份 cq-public，再检查 prior 的角色/父级是否一致；因此正常复用已有 CQ 身份没有机会走后面的 owner 校验。范围 schema 的 assignment 却允许 competency-question，Coordinator 专业说明又要求“Assign bounded work to professional roles”，未说明 cq-public 由程序另行刷新、不能列入 assignments。

Coordinator 五次结果都保留 modeler/CQ 两项分工，第四个结果通过前置校验后实际触发 work_unit_identity_conflict。其已发消息、已更新工作卡不能替代范围安装。Modeler 收到“进入 propose”的消息，调度绑定仍是 source_intake，所以继续分析而非候选表达；单靠催办不能改变程序阶段。

最小方向：统一 schema、提示与现有身份复用规则；同角色、同父级的已有公共 CQ 应能复用，或在 schema/提示明确由程序另行处理，并给可操作反馈。保留跨 owner/角色冒用和同计划重复 ID 的真实冲突保护，不再以保留名称一刀切挡住合法复用。

### 3. 实际完整读取被判未消费——上一轮归因需要修正

**已定位；确定性平台误判。** `role_work.py` 的 `_read_materials` 先检查成功回执中的确切 reference，再额外要求 `arguments.reference == reference`。真实 MCP 事件中前者为对象，参数仍是 JSON 字符串；工具调用成功并返回同 object_id/revision/digest。额外比较因类型不同失败，丢弃全部字符区间。

role-00004 的两个成功读取回执分别为 offset=0、returned=total=4398 和 2029、next_offset=null。离线调用原校验准确重现 read_characters=0；只在内存中将参数 JSON 字符串解析为等价对象，同一事件/引用/正文随即通过。原始文件和产品代码未改。证据：`read-replay.json`，不是新真实运行或修复已生效的证明。

T0 复核：完整读取和确切版本检查必要，但成功的服务端回执已绑定确切 reference；重复的原始参数表示比较不保护新的不变量，却误拒合法读取。最小方向是删除这项重复比较，或只做等价表示的规范化；继续验证成功回执、摘要、版本和完整字符区间。不是放宽“没有读取也能消费”。

### 4. 公开 CQ 的 seed 被当作另一种 snapshot

**已定位；Host 输入准备与新平台合同兼容问题。** 本轮 public-cq.json 为 `ontoweave-custom-cq-seed/v1`，manifest 标为 competency_goal；Host 直接复用了旧轮材料。`_validate_public_cq` 对所有该类型材料调用 `validate_snapshot`，要求 `ontoweave-cq-snapshot/v1`、snapshot_id 和内部摘要。即使 CQ 全部维持 draft、不申请业务确认，也会先读种子并拒绝。

只读直接校验原文件得到 cq_snapshot_digest_mismatch；生产回执进一步包装为 public_cq_seed_invalid。一般材料冻结只检查文件/摘要，本轮没有在开始时识别“导入 seed”和“项目快照”的差别，故付费 CQ 完成后才发现。不能把此错误解释为九道题本身无效或 CQ 语义错误。

最小方向：任务准备沿已有 seed 导入/项目 snapshot 合同形成正确输入，或明确支持普通公开 draft seed；在必要输入边界尽早给出预期 schema 与路径，不新建导入框架，也不让每个角色用推理修复数据包装。

### 5. 纠错以新上下文重做，成本没有落在目标阶段

**已定位机制；精确节省量待测。** 任务级 fresh run=1、业务初建轮=1；semantic-starts 目录实际保存三个 Modeler source_intake 原生开始记录，不能把“一个 run”当成“只有一次原生语义开始”。12 个原生线程彼此不同，其中生产 10 个（Coordinator 5、Modeler 3、CQ 2）、过程评价 2。`role_work` 拒绝后 round++，生成新的 role-NNNNN；`ExecutionManager.resume_original` 只复用同 execution_id 的已登记执行/回执，不能跨这些不同回合保留同一个原生上下文。

生产共 54 次 read_material（含分页，不是 54 遍完整来源）；本回合 source_refs 又要求本执行实际读来源。未变业务反复进入新上下文，Modeler 的三次执行全为 intake。10 个生产执行用了 3,125,705 token，却没有可执行候选，不能称作有效模型产出。

最小顺序：先修上述确定性拒绝与反馈，消除重复纠错的触发，再决定是否需要改跨回合接续。当前证据不支持先重做记忆框架、增加角色或降低业务覆盖。保持来源实际读取和变更基线约束，不能凭旧摘要冒充当前正文。

### 6. 工程测试覆盖了理想输出，没有覆盖本轮真实表示和输入组合

**已定位覆盖缺口；历史工程 PASS 保留。** 完整角色流夹具直接 deepcopy(prompt.basis)、固定 status=proposed，范围仅分派 modeler；独立递归夹具把 reference 作为 dict 注入读取事件。它们能够证明预定输入下的状态流/作者/原子组合，但不会暴露本轮的字符串参数与对象回执差异，也没有用本轮旧 seed 冷启动验证当前专职 CQ 边界。

非推理加载证明提示/工具被挂载，不能证明模型能按合同操作。已有独立工程 56 passed 不等于真实 Demo L0/L1，原交付文档本身也保留了这条边界。

最小补证：复用本轮原始成功 MCP 事件检查消费判定；加入已有 cq-public 的同 owner 分派、当前真实 seed/快照衔接和准确纠错反馈案例。只修与补测真实暴露的边界，不扩大成全面新 harness。

### 7. Host 监督放大了返工，收口没有完成技术修复闭环

**已定位；Host 操作与流程责任。** 准备阶段 Python 导入路径错误造成 budget_unavailable（未发生模型调用，后已补齐）；第一次技术反馈同时建议“不重读未变内容”，与当前 per-turn source_read 校验不兼容，直接触发 Coordinator source_read_missing，后续才更正。一次 CQ 提交误沿用切片 goal，随后另建准确绑定执行，旧误提交未调用模型、最终取消。

Host 在发现 scope 错误后主要通过 input 指导模型，没有立即完成最窄实现/提示合同复核和复测；更关键的是后来仅看错误信封，将实际已读材料解释成“没读”。本次原始事件复核已推翻该判断，不能让 Agent 继续为错误平台回执兜底。

停止是 Host 的有界测试收口选择，不是预算耗尽：stop 请求时费用约 1.54 元，最终余 1.15205888 元。自然排空用了 666.907 秒，符合不打断在途回合的控制合同；这部分正常机制仍属于全任务成本。清理空项目是收口后的安全资源处理，但此后原 run 不能直接恢复已删除 scope。本轮没有完成“窄修→原错误步骤复测→继续原建模目标”，不能报告为交付闭环完成。

后续监督应在首个可恢复错误时看输入/回执与最窄代码，判断守卫是否误拒，尽快选择可验证的窄修，或在范围确实需要新决定时明确交接；不把反复提示或可恢复标签当已恢复。当前复盘不另授权修复实施或新付费启动。

### 8. CQ 的语义覆盖有局部缺口，尚非模型质量结论

**部分定位；过程评价及公开原文可相互核对。** 原九题复用、新增三题仍为 draft；评价发现未充分探测修改扣额单位的不变量、停用凭证的新请求/回放与重启用不补额度、回放与冲突分支等。相关规则在 business.md 确有原文。CQ 自报部分内容为后续可选，说明全景覆盖还可改善。

切片四维均 4/4，CQ 覆盖/跨单元维度 3/4、低优先级，清晰/源忠实均 4/4。该切片评价只判断语义方案，不负责认证执行器能安装方案，因此方案得分高与 scope 安装失败可以同时成立。两份评分不构成独立最终模型验收；题数也不是质量门。

最小方向：由原 CQ 专职按原文条件簇补足覆盖/显式保留缺口，范围仍由 Coordinator 依据完整来源维护。正式质量判断须在实际应用、治理读回和冻结完整分母的独立评价之后。

### 9. 尾差显示 unknown 不是当前仍有在途调用

**已定位至本地派生逻辑；非主阻塞。** ledger-read-audit.json 显示 87 条尝试全部 completed，12 个原生计量单元全部已知，inflight_count=0；但 tail_bound 仍含 inflight unknown。`TaskBudget` 的后备分支在没有动态在途项时，按“无 has_usage 的捕获尝试存在”加入 `[{}]`，该分支没有过滤已 completed 状态，捕获的 87 条 completed 记录触发了它。

因此先前“过时尾差”应精确改称“派生尾差分支误将已完成无独立用量的捕获记录视作未知在途”。原生累计用量计价与控制停稳另有证据，不据该字段改费或宣称还有运行。后续仅需纠正该派生条件和边界用例；本次不修改账本或代码。
