# v5 下一阶段测试：真实开源系统还是更复杂模拟业务

日期：2026-10-31。类型：路线分析与候选初筛，没有启动下一轮建模。

## 建议

优先采用一个真实开源系统的小业务范围，复杂度仍保持两个相互依赖的切片。现有模拟业务继续作为稳定回归；从真实试验中暴露的问题提炼最小模拟反例。暂不把下一阶段主线改成更大、更复杂的模拟业务。

这个顺序优先补外部一致性证据，同时控制范围。它是本次分析建议，不是已经完成的选型、部署或新需求验收。

## 当前起点与真正缺口

[本轮两切片交付](2026-10-31-v5-two-slice-service-progression.md)已具有初建修后、来源变化后及持久修后默认冷启动各 18/18 独立语义 PASS，原 5/18 PARTIAL 保留；220 项开发回归通过。该证据覆盖我们编制的工程参考材料，未覆盖客户业务盲测、同条件 L2 或净降耗。

本轮较多问题位于技术合同、语义层级、责任完整性和精确读取。下一阶段需要验证的是：面对独立存在的业务材料和可运行产品，Agent 能否发现真实概念、状态、条件、关系与未知，形成可被消费的模型，而不只是重现我们准备好的完整条款。

继续扩大模拟业务可以测试规模和特定约束，但业务材料与预期仍由我们设计，不能直接补足与真实系统行为一致的证据。同时增加切片数量和来源真实性，会使失败归因更难。保持两个切片、先改变来源真实性，更便于定位问题。

| 方向 | 最有价值的新增证据 | 主要局限 | 当前定位 |
| --- | --- | --- | --- |
| 真实系统的小范围 | 文档／界面／实现之间的业务理解、状态与数据对应、实际消费、外部行为核对 | 准备部署和真值需要工作；开源产品不等于真实企业制度 | 下一阶段主线 |
| 更复杂模拟业务 | 递归、跨单元约束、变化传播、长上下文等可控压力与反例 | 与现实产品的外部一致性仍未验证；容易重复相同设计假设 | 保留回归，按真实缺陷定向增强 |

## 优先候选：Snipe-IT 的资产状态与领用归还

[官方仓库](https://github.com/grokability/snipe-it)说明这是 IT 资产管理系统，并提供用户手册及 Docker 部署入口。[API 文档](https://snipe-it.readme.io/reference/api-overview)提供 JSON REST 接口，适合记录可复现的业务操作与结果。项目整体并不是一个小代码库；本建议选择的是其中一个小、完整的业务范围。

建议两个逻辑切片：

1. **资产标识、状态与可用性**：资产、资产标签、状态标签名称与类型、当前占用状态。
2. **员工领用与归还**：领用对象、重复分配限制、归还后状态及两切片共享的资产身份。

第一轮限定资产领用给用户；其他产品支持的分配对象、许可证、配件、耗材等明确留在范围外。两个切片不预先决定 Ontology 数量，也不要求固定 Agent 数量。

[官方概念说明](https://snipe-it.readme.io/docs/overview)给出可核对的规则：资产标签在该系统内唯一；已领用资源需要先归还才能再次领用；Deployable 类型也可能包含当前已分配的资产；归还时应依据资产状况选择状态。因此可以测试以下区别，而不是只识别几个表名：

- 自定义状态名称、状态类型和派生的 Deployed 状态之间的区别。
- 状态类型允许分配与某资产当前可以再次分配之间的区别。
- 归还与重新成为可领用资产之间的区别。

这些事实来自当前官方说明；正式试验仍须冻结选定版本和配置并实际核实，不能把在线文档当作所有版本的真值。

**备选是 InvenTree 的采购收货与库存。** [官方 README](https://github.com/inventree/InvenTree/blob/master/README.md)提供库存管理、REST API 和部署资料；[采购订单文档](https://docs.inventree.org/en/stable/purchasing/purchase_order/)描述收货转成库存项及订单完成行为。它适合下一步增加数量口径、收货与库存关系的测试。我倾向先用 Snipe-IT 降低首次真实业务验证的准备范围，而不是并行引入两个外部系统；这个排序尚无本机部署对照数据。

## 最小试验方式

1. **先限定并核实一个版本。** 固定 release／commit、配置、操作者权限和可重置测试数据。只跑通资产建立、领用、重复领用、归还及状态变化这条闭环。若需要较多上游改造或额外集成，换候选；不要把环境搭建变成平台研发。
2. **给生产侧真实但有界的输入。** 选定版本的业务手册、必要 UI／API 描述、相关 Schema 和少量数据线索；有具体歧义才查对应代码／测试。不先把完整仓库灌入上下文，也不由 Host 预先整理成完整答案教材。Schema、字段和样例是映射证据，不能单独充当业务意义。
3. **在生产前独立冻结问题与行为参照。** 例如 12—20 个问题，覆盖两个切片、共享关系、正反例和真实未知。另由受控测试操作记录外部系统的原始响应与后续状态，独立评价者据此核对；不从待验本体生成正确答案。不得让制作／修复本体的上下文兼任最终评价者。
4. **验证实际模型和消费。** 验收必须读取冻结版本的受治理模型并展开关键关系，不能从原文或项目常识补模型缺失。若评价具体业务数据答案，Consumer 先获取授权语义上下文，再经可复用的外部数据读取能力获取业务行；消费阶段不旁路读取源码、手册或隐藏预期结果。条件允许时在原范围增加少量新问题检验使用效果，不只检验表示完整性。
5. **回到现有回归。** 在同材料／配置／模型与评价条件下做有界复跑；将真实缺陷抽成小反例后再修提示或最窄平台层。记录生产、自查、失败、评价和辅助调用的完整成本，缺测不补零。随后才扩大真实业务范围，或针对已明确的规模／递归问题增加复杂模拟。

外部系统的实际业务行保留在它自己的数据库；OntoWeave 表达意义、关系、条件、规则及必要映射。Snipe-IT 的业务概念不能变成平台专用 API、字段或排序分支。初轮不以前置通用连接器、认证集成或管理 UI 扩大任务；若数据消费需要新增工程，应先判断是否可沿现有能力最小复用，并将额外范围单列。

## 真值与验收边界

- 开源项目能提供真实产品行为参照，不能自动提供某家客户的业务制度。第一轮明确建模选定版本产品的业务语义及行为；定制政策仍需独立业务确认。
- 文档、代码与运行结果有冲突时，分别记录声明、实现观察及未知，先明确评价要核对什么，不能静默选择有利的一侧，也不能把上游问题归因于本体质量。
- Snipe-IT 官方 API 文档说明：某些业务错误也可能用 HTTP 200 返回，真正状态在 JSON 中。因此行为参照须核对业务响应和操作后状态，不能用 HTTP 200 作为成功依据。官方共享演示库会重置，不用它作为稳定重复性基准。
- 开源资料可能已进入模型预训练，不能因来源外部就宣称盲测。使用独立保留的新数据／操作组合、确切模型证据，以及遗漏模型负对照，防止 Consumer／评价者凭项目常识补答案。官方测试若作为生产资料开放，对应的同一断言就不能再称隐藏验收题。
- 资产状态这类业务数据变化不必然是语义规则变化。应验证答案随外部数据更新，而不为每条状态记录重写本体；只有实际业务含义改变时，才验证相应语义重审。
- 简单真实系统的 L1 与更大规模的 L2／产品化分开；本次分析不以增加压力测试作为真实验证的前置门。
