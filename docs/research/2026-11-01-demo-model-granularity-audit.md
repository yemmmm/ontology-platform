## 14 个资源里实际放了什么

重新导出当前实际 RDF：126 个 triple、14 个 subject，规范化内容哈希仍为
`84f8c969ae75542c4f722eba1ecbb6ea72145451f52c61969b64ec3d7f587c42`，与清理前后核对一致。
类型只有 Class、ObjectProperty、TableMapping 和 JoinMapping。

| 内容 | 实际表达 |
| --- | --- |
| 四个 Class | Model、ApiKey、ModelGrant、CallRecord |
| 三个关系定义 | 凭证获准访问模型、凭证发出成功调用、成功调用针对模型 |
| 四个表映射 | models、api_keys、model_grants、calls |
| 三个连接映射 | 授权连接、凭证到成功记录、成功记录到模型 |
| 19 个物理列映射 | 嵌在四个表映射中，均为 role=value，未绑定独立 property IRI |
| 大量处理逻辑 | 集中在四个 Class 的 business_meaning 文本中；CallRecord 单项有 546 字 |
| 业务行为／接口定义 | 没有独立 Operation 或接口映射资源；获准 OpenAPI 中有 11 个接口操作 |

`CallRecord.business_meaning` 一项承载了认证、请求查重、冲突、历史回放、新请求准入、费用比较、
扣额、成功记录原子写入、拒绝、并发和持久化等逻辑。它的业务含义是“成功调用记录”，但适用范围
和 semantic_role 又承担调用处理流程；对象、过程及策略的层级被高度合并。

这是“少量概念＋长文本规则＋外部数据映射”的建模选择，没有被平台自动展开成行为／规则网络。
模型并不是完全没有写业务逻辑，但缺少能单独检索、引用和维护的行为／规则身份与明确关联。
19 个列和每个条件也不应机械地各变成一个节点；只有需要独立身份、复用或关系表达的含义才值得拆分。

原 scope 要求完整业务规则和数据映射，OpenAPI 作接口证据，**没有规定每个端点必须建一个 Operation**。
所以 11 个接口不等于必须新增 11 个资源；零 Operation 是当前表达粒度的事实，不能单凭它判定
违反冻结验收。若目标包含动作输入输出、前置条件和效果的独立消费，应明确这部分目标并检查现有表达。

## 可复核的实际缺口

### 1. 凭证首次创建的非空模型集合条件丢失

公开 business 明确：“首次创建凭证时必须给出非空模型集合及非负整数额度”。冻结 OpenAPI
也为 `KeyInput.allowed_models` 声明 `minItems: 1`。非负额度／零额度已在模型表达，但非空
集合这一条件没有出现在实际 14 个资源的定义、映射或其他 RDF 表达中。

核对了全部 RDF 字面量与结构，`非空`、`non-empty`、`nonempty`、`minItems`、`allowed_models`
均无匹配；同时人工检查了 ApiKey、ModelGrant、授权关系及相关映射，没有等价的创建下界条件。
one_to_many 连接基数不等于“签发时必须至少选择一个模型”。关键词检索只作辅助，不能单独作为
语义缺失判定。

原独立报告写“非空授权集合……均已表达”，所引 ApiKey／ModelGrant／api_keys 映射的实际正文
不支持这一部分答案。此处是**已知来源条件漏表达＋自查和验收漏检**，不是需要用户重新提供的未知。
报告可能混用了来源知识，也可能在分项检查时漏核条件；能确认的是该 PASS 无法由其模型证据复现，
不能凭结果猜测评价 Agent 的内部原因或主观意图。

### 2. v2 增量留下错误的额度单位

v2 来源明确额度为整数调用单位、不再等于调用次数。实际 `api_keys` 表映射的
`mapping_definition.field_meanings[column=remaining_quota]` 仍为：

```text
source_meaning = 剩余次数额度……
source_unit = 次（调用次数）
```

可配置费用大于 1 时，剩余单位不等于还能调用多少次。v2 的实际提案及成功更新只涉及四个资源，
没有更新余额对应的 ApiKey／api_keys 映射。其覆盖记录以“无旧扣一残留”宣称影响检查完成，
却没有闭合额度单位在余额定义中的使用。这是增量影响分析和一致性核对不足。
business v2 自身也留有“次数额度”等旧名称，输入术语可整理，但其边界已经明确“不再等同于可调用次数”，
不能以旧名称保留明确的调用次数单位。

### 3. 成功记录字段与回放响应字段局部混写

实际 calls.charged_units 的字段说明同时写“回放调用为 0”和“历史成功记录不改写”。完整 CallRecord
定义能区分回放响应与数据库历史记录，但单独读取该存储字段会出现歧义。应把“存储的历史扣额”
和“本次响应扣额”清楚分开。这属于局部定义质量问题，不是需要增加业务行实例。

### 4. 其他消费限制需要分开归因

映射仍有旧 `schema_source=@2112c3e` 和空 schema_version；部分关系写基数未知，但连接映射已
给出具体 step cardinality。这些此前已发现的问题仍在当前模型，说明版本／未知／物理映射声明
的一致性也应一起核对，不能只修新字段。

时间格式／时区、凭证启用整数编码在原获准来源中不足以支撑所有 SQL 问题；当前应用代码能提供
部分技术证据，但本次分析不将新读到的代码擅自回填为过去已确认的业务来源。
Q8 的拒绝／回放尝试、Q9 的调价历史没有对应持久化事件源；现有四表和代码只保存成功调用／当前配置。
重建本体不能凭空恢复这些历史数据。它们与“已有来源非空条件漏表达”是不同问题。

## 是否需要完整重建

**建议先按完整来源做一轮完整修模与独立重验，不直接清空当前模型重建。** 现有类身份、三条
关系和七个数据映射大部分可复用；已确认的实际缺口可以在保留身份的前提下修正。需要解决的是
完整性闭环，而不是设定一个更大的资源数量目标。

还有一个已经存在的对照：此前空本体 v2 运行 `v5-llm-access-v2-20261101-fresh` 的保留快照只有
13 个资源，原报告为 29/29 PASS。该模型把授权只用关系表达，少一个 ModelGrant 类；其 ApiKey
正文已经包含非空创建约束，余额映射也没有“次（调用次数）”的旧单位。
这说明从零启动既不保证节点变多，也不是当前缺项不可修的证据；再次使用相同方法和检验方式
启动，很可能仍得到小规模、长文本承载的模型，无法检验当前真正关心的表达质量。

最短纠正顺序为：

1. **来源到表达的完整清单。** 从原业务目标和全部材料列出有意义的命题分组，明确真实未知、
   有源未表达和不适用；落到实际定义／字段／关系，而不是只记“两个切片已覆盖”。
2. **澄清需要独立消费的语义身份。** 对签发、状态切换、调价、新调用处理、回放／冲突等，
   按身份、复用、前置条件／效果及消费需求判断独立行为／规则与其关联；保留适当的自然语言
   条件，不强制每个字段、每条规则或每个端点单独建节点，不恢复 SHACL／自动执行完成门。
3. **完整修模与影响核对。** 补已知漏项，统一所有使用者的单位，分清历史字段与响应字段，
   更新必要的版本／基数声明。公开原文和模型真实差异是生产依据，不传回私有评分或答案提示。
4. **独立重验。** 每个必答条件要能指向实际模型中的具体定义／字段／关系；来源只作忠实度核对。
   加入“空集合签发”“余额不能直接当调用次数”等公开业务反例及跨定义一致性检查，不能因
   某资源已读就直接判其所有条件通过。另查动作／规则的独立检索与关联是否满足已确认目标。
5. **需要比较新方法时再做空白对照。** 先固定相同来源、消费目标及检验标准，保留当前模型和
   失败基线，再在新范围中比较；不把重启本身称为改进，不预设必须产出多少节点。

因此，当前需要一轮完整建模质量纠正；是否采用 fresh start 是后续试验选择，不是当前已证明
必须推倒重来的结论。本次没有启动建模、改预算、写模型或删除唯一保留模型。

## 与 v4“几十个节点”的对照

用户进一步追问 13 个资源能否讲清 Demo，并指出 v4 最小切片曾有几十个节点。
这里应直接区分：当前实际产物不足以作为完整业务语义模型；“少量资源能放下很多文字”
只解释计数，不能证明业务已完整、清晰地建模。此前回答只强调节点数不是质量指标，
没有解释表达方式的变化，容易让人误以为当前 13／14 项已经足够。

实际找到一份 v4 小链快照：`r4009-20261014-glmhigh-smallchain-0657-start1`，
Project `5fa9f983-2ae0-4618-985c-227d89bc3db0`。备份 RDF 有 49 个资源：
7 个 NamedIndividual、41 个 ObjectProperty、1 个 DatatypeProperty。业务定义包括 Customer、
Site、Asset、EquipmentModel、Fault Incident、Work Order、Work Order Status Event；
字段／关系独立资源包括 hasTechnicalIdentifier、hasOpenedAt、hasSeverity、hasResolvedAt、
locatedAt、isOfModel 等。原[复盘](../delivery/modeling-retrospectives/2026-10-14-glm-smallchain-retrospective.md)
也记录 49 资源／245 statements，且该运行仍为 PARTIAL，不能把数量当作质量金标准。

| 比较内容 | 这份 v4 小链 | 当前 Demo |
| --- | --- | --- |
| 资源数 | 49 | 14（另一次从零版本为 13） |
| 业务对象／定义资源 | 7 | 4 个 Class |
| 属性／谓词的独立定义 | 42 | 3 个关系定义，零独立 property |
| 数据字段的主要表达位置 | 具有独立字段／关系资源 | 19 个列映射嵌入四个映射载荷 |
| 大量流程与规则 | 需按该业务另核验，不能由数量推断完整 | 高度集中在 Class 的长段说明 |

这两个范围不是同一业务，不做资源数量的质量倍数比较；49 也包含属性／谓词定义，
不是 49 个可见画布节点，不能直接等同于用户所指那次前端计数。
但对照证实：历史小链确实采用了更细的字段／关系资源表达，当前 Demo 的资源口径更压缩。

以调用为例，当前把成功记录和整段“认证→查重→回放／冲突→新请求准入→扣额／写记录”放在
CallRecord 说明里。若目标是可独立检索、引用和维护的业务语义模型，应区分调用处理行为、
成功记录对象、准入／回放／扣额等规则与适用关系，保留各自条件和例外。
可以使用自然语言定义和普通关系，不要求恢复规则引擎，也不要求每条规则机械地产生一个节点。

因此对用户问题的准确回答是：**当前这份 13／14 项的实际模型不够；它只是压缩表达了很多
逻辑，还存在已证实的漏项。应按完整语义表达目标修模和重验，不能拿资源数量少解释成已经完整。**
