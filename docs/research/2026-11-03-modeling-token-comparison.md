## 2. 与完整 Demo 相差数倍，发生在哪些环节

### 2.1 业务范围与验收任务更小：已定位

本轮只要求两个概念、一种位置关系、方向、非所有权和显式未知，没有具名实例、SQL/API 映射、计费整数单位或多业务切片。Demo 包含模型目录／可用性、凭证授权／整数调用单位两切片，以及数据库与 API 合同；最终51或75个资源、36道题。初始来源字符约为本轮的41.86倍，验收题为9倍；这些比例描述规模，不能直接线性预测 token。

本轮是完成另一个更小的任务，不能把从36题变4题、51资源变3资源解释为同一任务保持范围的降耗。本轮没有删掉自身 Task 要求的业务范围；两个 Task 的授权目标本来不同。

### 2.2 修模、纠错和反复独立验收显著减少：已定位

Demo repeat 共8段建模、3段自查、6段独立验收，包含3轮实质建模；初建经历 source_key、映射列等字段拒绝及租约收尾修复，后续还有公开质量复核、关联与角色／接口表达修订、JSON／label 纠错，以及读取覆盖不完整和报告格式重试。不能把这些真实成本从历史任务中删掉。

本轮共2段建模、2段自查、3段过程评价、1段正式验收；1次初建按端点依赖分两批应用，正式验收一次通过，过程评价无额外纠错执行。其请求总数44，对照 Demo repeat 的180，仅约四分之一。

### 2.3 每次累计输入也更短，但没有显著缩短固定方法：已定位

Demo repeat：180次有数值请求，平均输入42,565 token；本轮44次，平均31,958 token。输入总量约5.45倍差异，在算术上分解为请求数4.09倍 × 平均请求输入1.33倍；这只是计数恒等式，不能把范围、历史重验和方法变化分离成独立因果贡献。

本轮冻结 instructions 为73,119字符，Demo repeat 为69,914字符，今日同范围前轮也是73,119字符。固定方法合同没有缩短，本轮甚至比 Demo repeat 长约4.6%。因此“大幅压缩系统提示”不支持作为本次降耗解释。更小业务材料、模型回执与读取任务、较少重复执行，才与原生用量差异一致。

- **统计少算了评价：未发现。** 3项过程评价和1次正式验收均有完整原生末次用量，计入152万；34段 Demo fixes 的续接基线复算也一致。外部Host与内部辅助缺测是所有组都保留的边界，不能报为零或当完整账单。
- **相同小场景新输入大幅下降：不成立。** 前轮输入减少145,269，其中缓存输入减少145,472；本轮未缓存输入反而多203。输出少29,789。前后 token 和费用下降的构成不同，不能把152万与170万的差额都看成新信息处理减少。
- **high 比 low 更省：无法证明。** 两组Demo是low且业务更大；相同high小场景只有10.31%差异。缺少同来源、同标准、同角色与同代码的effort对照，不建立模型等级因果结论。
- **本轮复用旧答案／旧模型：未发生。** 新Task、新workspace、新Project/Ontology和8个独立原生线程；复用了公开原文与冻结标准，没有沿用旧模型及候选。缓存命中不等于业务成果继承。
