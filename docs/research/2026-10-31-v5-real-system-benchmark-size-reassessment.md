# v5 首次真实系统验证：项目大小复核

日期：2026-10-31。类型：候选规模复核；未部署系统，未启动建模。

后续用户希望采用更熟悉的大模型业务，并提出临时编写测试项目；该方向的[开源比较与小项目实现](2026-10-31-v5-llm-project-benchmark-selection.md)已另行记录。本文保留此前规模判断，Grocy 不再是当前优先推进项。

## 修正结论

Snipe-IT 整体对当前首次真实系统验证偏大，撤回[前一份分析](2026-10-31-v5-next-benchmark-real-system-vs-simulation.md)将它列为优先候选的建议。保留“真实系统、小范围、两个相关切片”的方向；Snipe-IT 留待小型真实闭环通过后，再验证更完整的企业资产业务。

前一次分析已说明项目整体不是小代码库，但主要以选定切片的简单程度排序，对部署配置、周边业务和材料筛选的准备成本估计不足。业务切片小，不自动意味着整个试验便宜。

## 已核实的事实与判断依据

| 方面 | Snipe-IT | 对当前阶段的影响 |
| --- | --- | --- |

## 更轻的下一候选：Grocy 的库存与补货

[Grocy](https://grocy.info/)是真实自托管家庭物资管理应用。[发行分支 README](https://github.com/grocy/grocy/blob/7d15c46bbdc35d4958cae99209ba170667dc1d64/README.md)说明采用 PHP、SQLite，并有覆盖前端主要操作的 REST API。官网链接的 LinuxServer 社区镜像，其[维护者部署示例](https://docs.linuxserver.io/images/docker-grocy/#docker-compose-recommended-click-here-for-more-info)只需要一个容器与配置持久目录，不需要单独数据库服务。

GitHub size 为 25108 KiB，约 24.5 MiB，是 Snipe-IT 同口径数值的约 1/14。这只是辅助信号；更有意义的是内嵌数据库、现成运行镜像、API，以及可缩小操作界面的功能开关。它也有食谱、家务、设备等额外模块，不能把整个 Grocy 都称为很小的建模范围。

建议首次仅覆盖两个相关切片：

1. **库存管理**：商品、库存数量、入库、消耗及操作后的余额。
2. **补货清单**：最低库存设置、库存不足与采购清单的联系。

共享商品与数量，能检验跨切片理解和实际消费。以入库、消耗、观察库存与补货结果构成一个闭环。先固定计量单位和业务配置，暂不纳入食谱、换算、保质期、开封和冻结等变化；这些限制只用于试验范围，不能改写产品已有规则。

[配置文件](https://github.com/grocy/grocy/blob/7d15c46bbdc35d4958cae99209ba170667dc1d64/config-dist.php)提供库存、采购清单及其他模块的功能开关；低库存自动加入采购清单的用户设置默认是 false。因此不能凭“库存不足”就断言清单必然自动变化，必须冻结选定设置并核对实际响应与后续状态。关闭界面功能也不被当作 API 隔离或业务授权证明。

这里仍只把 Grocy 提升为下一候选，没有完成正式选型。若最小版本核查发现数据读取不兼容或必须较多改造，再换候选；不为候选补建连接器框架。InvenTree 不作为本次缩小规模的替代，它的采购／库存业务面仍较宽，前一份分析也没有部署对照证据。

## 当前范围与后续验证

- 优先检查一个固定发行版本能否原样运行、执行并重置上述闭环，再确定模型输入和验收题；不先阅读整个仓库或扩大平台功能。
- 两个切片、模型资源数量、数据表数量与 Ontology 数量分别由业务与实现决定，不为满足数量强制切分。
- 延用原分析中的源材料忠实度、实际受治理模型读回和独立语义验收要求。业务行留在外部系统，不能靠把数据库行复制进本体获得问答通过。
- 本次只读取官方仓库／文档及镜像维护者文档。Grocy 查询时 release 为 7d15c46bbdc35d4958cae99209ba170667dc1d64。未下载镜像、部署、执行业务 API、审计完整 Schema，未核实现有数据读取能力与 SQLite／该 API 的兼容性。
- 仓库体量来自当次在线元信息；未测代码行数、CPU、内存、镜像体积、实际准备耗时或建模 token。更轻、更适合首次试验是当前证据支持的判断，不能升级为运行或模型质量验收 PASS。

本次仅修正调研建议，不改变 v5 需求完成状态，不宣布新建模授权或新验收结果。
