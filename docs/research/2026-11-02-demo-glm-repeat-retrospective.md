## 核心判断

最主要的不足是**语义完成判断缺乏稳定的实际依据，读取合同与覆盖核对又不够可靠**。GLM 在准确反馈后能修出职责角色、字段绑定和关联，但首次建模把已知视角简化成说明文字，自查和独立 Judge 又用标签、局部命中或图连通支持整体结论。结果是宿主反复发现遗漏、再公开澄清、再修模和重验。

后续另有两类技术返工：明确未写入的 Session 没有及时关闭；自然语言最终回复承担大型 JSON 序列化，格式错误后重新创建验收上下文。前者已有窄修并真实采用，后者尚未修。不能把它们全部归因 GLM 建模能力，也不能从一次 low 配置推出提高 effort 必然有效。

建议顺序是：**先纠正工具读取合同与可观察覆盖，再落实已有语义检查方法，同时缩短报告格式纠错路径，最后才做模型配置和输入压缩的单变量比较**。不增加固定 Agent 数量、七类节点配额、全图连通门、独立 dry-run 或新的常驻监督链。

## 建议一：先让“读了什么、读完整个所需范围没有”准确可见

当前工具把精确资源读取和全范围清单挤在同一个必需 IRI 参数里，Agent 又把 complete 解读成全本体。建议先局部对齐工具选择器与实际 API：精确 family 保留 IRI；全清单可明确省略 entity；resource-relations 如实声明全图。返回范围、过滤条件和 paging 的含义应相互一致。复用现有 API，不增加业务专用视图。

在已有 successful_reads／验收校验内，按冻结 material ID＋SHA256 合并已返回字符区间，报告当前必需范围的未读部分；对本轮声明整模型完整性的条件，再核对冻结实际资源的正文及正式引用覆盖。**已返回不等于已理解**，也不要求所有 Agent 全量读所有材料。范围可以有界，但完整性主张必须对应它自己的范围。缺口返回精确补读位置或接受 PARTIAL，不形成永久阻断。

验证先用当前保留的截断源和 list／relations 原响应作合同反例：读前 12000 不能被判全文已读；不同页合并后可完整；旧 SHA256 和旧模型修订不混用；越权不可扩大。只有随后获准的真实独立消费才能判断语义改善。若改动强制无关材料全读或扩大授权，应收窄到原冻结义务。

## 建议二：把已有的多视角方法落到实际表达核对

当前已有命题、coverage、实际表达引用和未决记录；不需要新造七视角输出模板。建模时用它们保存关键条件的去向；S7 和独立 Judge 回读**条件原义、实际字段／关系和处置依据**。关键问题是职责是否真为职责、接口字段指向哪个业务属性、规则适用哪个对象／流程，而不是是否出现相应标签。

对每个实际缺口先区分来源缺失、未表达、未读到和判定错误。合理独立定义允许有源处置，不为消除候选强行补边；自然语言规则合法，但不能用同名文本替代必要结构引用。独立评价仍自己裁决，Host 只提供可公开的原合同、原业务依据及治理观察。

角色澄清已经实现；下一次首先验证其**新绑定冷启动实际采用**，而不是再加一层相同提示。保留原 36 题、原完整范围及真实未知，并核对是否仍需 Host 补位。若声明 ready／PASS 却缺决定性依据，按原质量标准保留 revise／partial；不把计数合格自动变成语义通过。

## 建议三：缩小报告合同，在原独立上下文纠正格式

普通冻结标准只下发 index、passed、actual_answer、reason、evidence_iris 等当前所需字段；确有自定义 CQ 时才加入 CQ／SQL 字段，减少“可选字段出现在 schema、指令却要求不用”的歧义。继续采用用户已确认的自然工具回合＋程序 JSON/schema 校验，不恢复失败的强制 outputSchema 路径，不运行 `.trim()` 或由 Host 改造报告求通过。

优先复用现有独立 Agent 的会话恢复能力：在题集、来源、模型修订和读取权限均未变化时，反馈精确错误，让同一独立上下文补读缺页、修正报告；保留原始失败回合及其引用，不覆盖。语义／模型变化或资格缺口必须按实际范围重新检查。不能把另一上下文的读取伪装成本回合原件。

这需要在现有 evaluator／ExecutionManager 边界细化“报告纠错”用途，核对原上下文的读取与当前冻结身份、按 turn 增量计量，避免累计 usage 双计。不是默认允许任意历史 PASS 复用。若自然最终回复仍反复失败，再评估单一受校验的报告提交工具；不同时建设两套报告通道。

验证分两层：无模型的格式／身份／预算合同检查；下一获准真实评价验证能否在原上下文准确补读和提交。模型修订变化必须失效旧资格；错误修正不能改题、分数或业务理由。实际收益只按减少的重复读取和合格报告完成时间判断。

## 建议四：先清理具体合同歧义，再做输入与模型配置实验

source_key 的非连接串边界和 entity label required 已在原冻结合同中存在，不能把全部错误说成“提示没写”。应优先在确有缺口的字段处补足跨字段约束：例如 field_meanings 的列必须先在 column_mappings 登记，即使不绑定业务属性，也可合法表达物理列；以真实编译器验证一个通用例子。七个根错误与 24 个依赖错误在已有反馈中分清主次即可，不为此新建 dry-run 审批或自动猜语义的修复器。
