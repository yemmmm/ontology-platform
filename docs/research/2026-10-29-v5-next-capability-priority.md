## 建议顺序

1. **先验证当前最终代码冷启动。** 复用最小双成员场景，确认通信、材料、卡片、应用与
   读回能够在没有临场改代码／补技术提示时走通。只修实证问题，不扩成全面审计或治理。
2. **下一项开发：最小共享业务记忆。** 在现有工作空间保存业务判断／决定、未决项及
   来源引用；按身份直接读，未知位置按类型／关键词定位后展开。第一版先覆盖同一建模
   任务内跨 Agent、换会话接续，不前置全项目跨 run 迁移、向量库、自动抽取或摘要体系。
3. **把持久接续放入正常业务验证。** A 留下含条件／例外的判断，B 找到并使用；换新
   会话后仍能继续，修订后能找到当前内容。复用已有版本能力，不新增审批、锁定或终态门。
4. **随后落实新栈金额控制。** 实际验证累计、自然回合边界暂停及恢复；保持既定授权，
   不以开发任务 usage_only 代替正常能力完成，也不先重建完整财务／审计系统。
5. **再进入多工作单元并行。** 验证一个单元等待人工时其他单元继续、共享判断及父级
   整合；递归调度、复杂检索和管理 UI 不成为上述小步的前置条件。

任务卡保存“现在做什么”，材料交接提供“这次交给你的内容”；共享业务记忆补的是
“为什么这样判断、依据是什么、哪些尚未确认”，避免必须再次手工转发才能复用。
记忆不另维护一份已应用本体，实际模型仍通过现有受治理接口读取。
