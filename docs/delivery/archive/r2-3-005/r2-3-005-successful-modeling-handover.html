01

先建立正确的心智模型

这个平台不是“把文档扔给一个大模型，然后相信它的回答”。它是一条把语义判断、确定性写入、独立验收和清理分开的生产线。

一句话：Modeling 负责“理解业务并提出语义模型”，Protocol 负责“把模型可靠写进平台”，Acceptance 负责“独立判断写进去的东西是否忠于来源并能回答问题”，Runner 负责“让所有机械步骤可重复、可追责、可清理”。

语义面

Agent 做需要判断的事

阅读业务来源、识别类/属性/实体/关系、决定哪些事实可以断言、哪些必须保留为“未知”。Agent 不负责生成平台 ID、维护账本、拼接机械请求或决定自己是否验收通过。

机械面

Host 与工具做必须确定的事

冻结输入、检查摘要、建立新 Project/Ontology、按依赖顺序提交 Batch、保存 receipts、分页检索、绑定 ticket、串行 CQ、settlement、终态排序和资源清理。

平台面

平台保存“可复用语义事实”

平台接收通用的 class/property/entity/relation/shape，而不是写死 Dify 业务逻辑。领域含义留在本体数据中，平台只提供通用验证、推理、查询、Evidence 与 lineage。

验收面

Producer 不能自己给自己打分

Acceptance 使用 fresh、隔离、只读的 Source Examiner 与 Platform Examiner：一个只看批准来源，一个只看 ticket 范围内的平台事实。两者报告由 Host 绑定到同一 model state 后才形成 verdict。

02

Start75 到底建模了什么

场景是 Dify Workflow-as-Tool 的 C → B → A 业务切片。重点不是 Dify 本身，而是证明平台能忠实表达版本、调用、输出字段和来源未说明的未知行为。

C被作为 Tool 调用的 Workflow
B调用 C 并消费输出
A发布 B 的结果
显式未知来源没有说明时不猜

业务关系：B invokesTool C；A publishesResultOf B；B 当前 currentlyConsumesOutput Version 2 的 quality_rating:number。

批准来源中可以确认的内容

  • 只有以 User Input 节点开始的 Workflow 可作为 Tool；Chatflow 不能作为 Tool。
  • C 的 Version 2 已发布且标记为最新，输出字段是 quality_rating:number。
  • Version 1 的输出是 quality_score:number；来源没有证明两个字段语义等价或只是改名。
  • B 通过 workflow identity 调用 C，而不是绑定某个 release ID；A 发布 B 的结果。
  • C 的 classifier dependency 不可用时，可以不返回 numeric score 而成功完成，并返回 diagnostic code。

来源不能确认、因此必须显式保留的内容

跨版本字段语义未知

quality_score 与 quality_rating 是否保持相同业务含义，来源没有证明。模型没有建立等价、rename continuity 或 value compatibility。

B 无分数时的动作未知

来源没有说明 B 会 block、continue、retry 还是 mark for review。模型创建 ExplicitUnknown，而不是编造一个看似合理的动作。

平台建模质量的关键不只是“写入正确事实”，还包括“拒绝写入没有证据的事实”。

三条不能混淆的边界

Runner ≠ Agent

Runner 不理解 Dify 业务语义，也不回答 CQ；它只验证结构、顺序、身份、摘要、超时和清理。

Protocol ≠ Modeling

Modeling 不能直接组平台 Batch；Protocol 不能修改候选含义。两者用不可变 candidate digest 交接。

Acceptance ≠ Producer

验收只读取冻结 ticket、批准来源与平台 read-only surface；不能继续修改模型来“修到 PASS”。

02

创建 fresh 平台作用域

Runner 创建本轮独占 Project、Ontology、Build Session/Lease 所需权限。Start75 的 Project 为 7fc146d8…，Ontology 为 fd762f52…。成功后凭据按生命周期撤销，不把旧对象冒充新结果。

03

启动 Proxy、Broker 与四个持久角色

一个共享 loopback provider proxy 持有 DeepSeek key；每个 Agent 使用隔离 home 和 secret-free env。Team Transport MCP 暴露固定通信工具；Platform MCP 只给 Protocol，Acceptance capability 只给相应角色。

04

Coordinator 发出有界任务

Coordinator 不读取原始业务来源，只负责把 Modeling、Protocol、Acceptance 放到正确轨道，并等待 typed ready/silent/verdict 信号。这样它不能在转述时污染来源。

05

Modeling 形成完整候选

Modeling 读取 tools.mdx、release-register、workflow-landscape、exception-handling 与候选写作规范。它发布完整 candidate v2，而不是 patch；每条 relation 有 evidence citation；两处证据不足明确建模为 ExplicitUnknown。

输入批准 sources + staged full candidate
产物candidate digest 7a131d3b…
06

Protocol 验证 Candidate Receipt

Protocol 对整个 candidate 做 schema、平台中立性、引用、label、relation citation 和 digest 校验。receipt=accepted 只表示“候选可翻译”，不等于已经写入或验收通过。

07

确定性翻译为五阶段 Batch

translate_candidate_to_batches 不做业务推理，只按稳定映射把 candidate 拆成 class → property → entity → relation → shape，并把前序生成的 ID/IRI 传给后序阶段。

08

逐阶段 dry_run → apply_atomic

每个阶段先 dry-run，确认不会违反 schema/引用/依赖；再独立 atomic apply。Start75 数量依次为 6、18、10、12、1。一个故意无效的 negative probe 被 validation_failed 拒绝且没有应用。

09

Readback、Validation、Reasoning

Protocol 不相信写接口自报成功，而是重新读取 model state。validation 得到 conforms=true，reasoning 得到 consistent=true，并冻结 workspace version 与 model-state digest。

10

受治理语义检索

候选自己声明 7 条 required path。Protocol 为每条 path 执行 ontology-scoped、单 resource-type、asserted-only 查询；vector index 不可用时用同 path 的 lexical fallback。最终 14 条检索链完整、非截断，并带 Evidence/lineage。

11

Producer 收尾交接

Protocol 完成 Build Session checkpoint/complete/release，向 Modeling 发 gate-complete，向 Coordinator 发 acceptance-stage handoff 与 silent_for_acceptance；Modeling 确认同一 digest 后发 ready_for_acceptance。此后两者不再写平台。

12

构建并发布两张冻结 CQ Ticket

Coordinator 从同一个 handoff 构建 cq-001、cq-002 ticket，各发布一次。Ticket 绑定 run、task、question、批准 sources、model-state digest、quality standard 和允许的只读平台范围。

13

严格串行双 CQ 验收

cq-001 启动两个 fresh Examiner，回收完成并得到 usable PASS 后，Coordinator 才启动已经发布的 cq-002。两轮不重叠、不重建 ticket、不改变 model state，共四个 child。

14

Settlement 与终态链

两个 verdict PASS 后 Carrier revalidate model state，执行 settlement CAS，再读回 workspace version/state digest 确认 matched。Acceptance 先 terminal，Runner 依次发 terminal handoff，Coordinator 最后 terminal。

15

两阶段清理与最终安全审计

先停止所有 Examiner/角色并删除私有 config，再在 proxy key buffer 尚可比较时做一次 run-wide aggregate audit，最后关闭 proxy、验证 thread/socket、覆盖 key。最终 state=CLEANED。

16

独立只读验收

Round 29 不启动模型、不调用平台、不修改账本、不打开 SQLite。它对 804 个文件做前后快照，逐项核对语义、CQ、settlement、terminal 和 cleanup；两次最终 digest 一致后才给 PASS。

每条检索链的冻结参数

10

两轮 CQ 如何独立验收

Competency Question（CQ）是“这个本体是否真的能支持业务问答”的验收问题。每轮都必须由来源侧和平台侧两份独立报告支持。

CQ-001 · PASS

最新发布版本和 B 消费的输出是什么？

答案：最新可确认发布版本是 Version 2（published、markedLatest=true）；B 消费 quality_rating，类型 number。

边界：Version 1 的 quality_score 与 quality_rating 是否语义等价仍未知；Current Draft 不可被其他 Workflow 调用。

CQ-002 · PASS

C 没有 numeric score 时，B 会做什么？

答案：因缺少相关证据无法回答。来源只说明 C 可无分数成功并返回 diagnostic code，没有说明 B 会 block、continue、retry 或 review。

PASS 原因：模型正确保存 ExplicitUnknown，并没有杜撰动作。

每个 verdict 的 8 项检查

source_fidelity

所有断言与答案忠于批准来源。

scope

只覆盖约定的 C→B→A 业务切片。

ontology_structure

类、属性、实体、关系、Shape 结构正确。

explicit_unknowns

证据不足处没有被猜测填充。

validation_reasoning

SHACL/语义验证和推理一致性通过。

governed_retrieval

required paths 可按冻结条件完整检索。

evidence_lineage

事实能回溯到 Evidence、来源和写入链。

competency_questions

CQ 的答案或“不可回答”均被证据支持。

为什么 cq-001、cq-002 不能并行？

它们必须绑定同一个 final model state，同时 Acceptance 的上下文与 child cleanup 必须可判定。cq-001 usable PASS、全部 child 回收且 model-state revalidation 通过后，才允许启动预先发布的 cq-002。这样避免两个 CQ 在不同模型状态上给出看似一致的答案。

新手术语表

先掌握这些词，就能读懂大多数运行证据和错误。

Candidate / Candidate receipt

Candidate 是 Modeling 提出的完整平台中立语义模型。Receipt 是 Protocol/Host 对其 schema、引用和 digest 的机械确认，不代表平台写入或最终验收。

Batch / dry_run / apply_atomic

Batch 是平台写入命令集合；dry_run 只验证，apply_atomic 才写入，且当前 Batch 内要么全部成功要么不写。

Build Session / Lease / Checkpoint

Build Session 记录一次建模会话；Lease 防并发写；Checkpoint 是阶段性保存点。最终必须 complete/release。

Evidence / lineage / provenance

Evidence 是支持事实的来源对象；lineage/provenance 说明某条平台事实从哪份来源、哪次 Batch/关联产生，可用于审计和 CQ 引证。

ExplicitUnknown

来源没有给出答案时创建的语义对象，包含 unknownQuestion、unknownRationale 和它关联的业务对象。它不是失败，而是来源忠实度的一部分。

Competency Question (CQ)

用于证明本体能支持真实业务消费的问题。R2.3-005 有两个冻结 CQ，必须串行并绑定同一个 final model state。

Ticket / verdict / usable PASS

Ticket 冻结一个 CQ 的来源、平台范围、模型状态与质量标准。Verdict 是 Host 绑定两类 Examiner 报告形成的 PASS/FAIL/BLOCKED；usable 表示 ticket、state、epoch、cleanup 仍有效。

Settlement / CAS

Settlement 是 Team 最终接受同一模型状态的机械确认。CAS 确保预期 state digest/workspace version 没被并发改变。

Terminal handoff / terminal result

handoff 是 Runner 对角色发出的“现在可以终止”许可；result 是角色完成报告。二者分离可以保证 FAIL 修订路径在最终 PASS 前仍然可达。

Retained evidence

运行结束后保留、供独立 Tester 只读检查的文件树。失败证据同样保留，不允许事后改写成 PASS。
