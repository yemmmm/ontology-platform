# v0.3 前端构建工作台开发计划

## 目标

补齐 `docs/requirements/requirements-v0.3.md` 定义的治理控制面，使用户可以从平台工作台完成：查看构建
状态、维护 Project Brief、管理和验证 Competency Question、审核 Fact Claim、检查发布门槛、明确
确认发布、通过 Review Batch 深链接进入准确审核范围，以及查看版本谱系与证据。

本计划不实现平台内置聊天，不改变 Agent/Skill 与治理控制面分离的边界。

## 实施原则

- 按治理流程顺序开发：构建概览 → Brief/CQ → Fact Audit → 发布 → Review Batch 深链接 →
  版本与 Evidence Explorer。
- 复用现有 React、TypeScript、Ant Design、Lucide 和 `styles.css`，视觉方向保持当前高密度、
  操作型工作台，不引入新的 UI 框架。
- 新页面必须包含 loading、empty、error、disabled、stale 和只读状态，不能只实现成功路径。
- 已发布版本全部写操作禁用；所有写操作使用后端治理 API，不在前端模拟状态转换。
- 危险操作使用两阶段确认；发布确认必须显示目标版本和当前门槛摘要。
- URL 是深链接的权威状态，`localStorage` 只作为无 URL 参数时的偏好回退。
- 桌面端优先保证审核效率；窄屏下允许左右栏转为上下布局，但不得隐藏关键治理信息。

## 当前基线

现有前端已具备 Projects、Classes、Entities、Sources、Schema Review 和 Graph Review。缺失的核心
页面是构建概览、Project Brief、Competency Questions、Fact Audit、Publication、Versions 和
Evidence Explorer。`App.tsx` 当前同时承载导航、数据加载和绝大多数页面，继续直接追加页面会
提高回归风险，因此先进行非行为性拆分。

现有后端接口可以覆盖大部分功能：

- `GET /projects/{project_id}/build-context`
- `GET|PATCH /projects/{project_id}/brief`
- Competency Question 列表、创建、更新、状态转换和验证接口
- Fact Claim 生成、列表、分层抽样和审核接口
- Publication Readiness 和 Publish 接口
- Ontology Version 列表、创建及 Diff 接口
- Review Batch 列表和详情接口

需要在实现前确认或补齐的 API 契约：

1. Build Context 当前没有完整的完成度、阻塞项和下一步建议。优先由后端返回确定性派生结果；
   如果暂不扩展接口，前端只能展示由现有字段可靠计算的内容，不能自行发明发布规则。
2. Fact Claim 只返回 `evidence_ids`。Evidence Explorer 需要按 ID 批量读取 Evidence，或要求
   Fact Claim API 内嵌 Evidence 摘要。
3. Review Batch 的 `item_ids` 需要明确是 Proposal ID、Fact Claim ID 还是 Conflict ID，并按
   `review_type` 提供稳定映射。
4. Publication Gate 的 `details` 当前为通用 JSON；前端需要固定各 gate 的展示字段或提供统一
   的 `title`、`summary`、`remediation`。

涉及上述后端契约的修改必须增加后端测试并运行 `cd backend && uv run pytest`。

## 阶段 0：前端基础重构与工作台路由

### 目标

在不改变现有行为的前提下，建立后续页面共用的版本上下文、URL 路由和组件边界。

### 工作项

1. 将 `App.tsx` 中页面组件拆到 `frontend/src/pages/`：
   - `OntologyHomePage.tsx`
   - `SourceDocumentsPage.tsx`
   - `SchemaReviewPage.tsx`
   - `GraphReviewPage.tsx`
   - 现有 Classes/Entities/Agent/System 页面可分批迁移，避免一次性大改。
2. 新增 `frontend/src/components/workbench/`：
   - `WorkbenchPageHeader`
   - `StatusSummary`
   - `WorkflowStepper`
   - `EmptyState`、`InlineError`、`LoadingPanel`
   - `ConfirmActionDialog`
3. 新增 `frontend/src/hooks/`：
   - `useAsyncResource`：请求、刷新、取消和错误状态。
   - `useWorkspaceLocation`：解析并同步 `project`、`ontology`、`version`、`tab`、`batch`、
     `proposal`、`claim` 查询参数。
4. 在 `types.ts` 增加 `BuildContext`、`ProjectBrief`、`CompetencyQuestion`、`OntologyVersion`、
   `VersionDiff`、`ReviewBatch`、`FactClaim` 和 `PublicationReadiness` 类型。
5. 工作台顶部增加版本选择器。默认选择 ontology 的 `current_version_id`，URL 指定版本时以 URL
   为准；已发布版本显示只读标记。
6. 调整导航分组：
   - Build：Overview、Brief、Questions、Sources
   - Review：Schema、Graph、Facts、Publication
   - Model：Classes、Entities、Versions
   - Tools：Search、Agent Test、MCP Tools、Settings

### 验收

- 现有页面功能和 URL 参数保持可用。
- 刷新带完整查询参数的 URL 后仍进入相同项目、本体、版本和 Tab。
- 不存在无效项目/本体组合时静默回退到其他本体的行为；应显示明确错误并提供返回入口。
- `cd frontend && npm run build` 通过。

## 阶段 1：构建概览 Dashboard

### 页面结构

新增 `BuildOverviewPage`，作为打开 ontology 后的默认页面：

1. 顶部 Workflow Stepper：`gathering → schema_draft → schema_review → graph_building →
   graph_review → validated → published`。
2. 当前版本卡：版本号、状态、父版本、创建/发布时间和只读状态。
3. 完成度卡：Brief 完整度、CQ 状态、Source 数量、待审核 Schema/Graph 数、Fact Audit 进度。
4. Blocking 区域：按严重度展示确定性阻塞项，并链接到对应页面和准确筛选条件。
5. Next Actions：最多三个按依赖排序的下一步，不显示当前阶段无法执行的动作。
6. Recent Review Batches：批次类型、计数、状态和“继续审核”。

### 数据与交互

- 首次加载并行请求 Build Context、当前版本、Review Batches；发布准备度仅在版本进入
  `validated` 或用户主动刷新时请求，避免把高成本校验当成普通轮询。
- 页面聚合只负责展示；工作流状态和阻塞结论以服务端为准。
- 每个统计项都可以进入对应工作页面，不使用不可点击的装饰性指标卡。

### 验收

- 空项目、Schema 审核中、Graph 审核中、可发布和已发布五种状态均有明确呈现。
- 用户可以从任一阻塞项一步到达处理页面。
- 页面刷新不会丢失所选版本。

## 阶段 2：Project Brief 与 Competency Questions

### 2.1 Project Brief 编辑器

新增 `ProjectBriefPage`：

- 按领域目标、范围、核心概念、粒度、来源、边界、术语和推理范围分组编辑字段。
- 每个字段展示 `missing/answered/confirmed/skipped` 状态及来源数量。
- 提供保存草稿、确认字段、跳过非必要字段和撤销本地未保存修改。
- 右侧显示完整度、缺失字段和 clarification items。
- 离开存在未保存修改的页面前提示用户。
- 后端返回未知字段时放入“扩展字段”区域，避免静默丢失。

### 2.2 Competency Questions 页面

新增 `CompetencyQuestionsPage`：

- 列表按 position 排序，支持 active/inactive 和状态筛选。
- 支持创建、编辑问题、重要度、query definition 和来源关联。
- 支持批准、标记 testable、停用和执行验证。
- 验证结果显示运行状态、passed/failed、结构化详情和是否因图谱修改而过期。
- 排序第一版使用明确的上移/下移操作；确认后端 position 更新语义后再考虑拖拽。
- 状态转换按钮按当前状态和后端规则启用，失败时保留服务端错误信息。

### 验收

- Brief 保存后完整度和缺失字段立即刷新。
- 修改 Brief 后，受影响 CQ 的需重新验证状态可以被看到。
- CQ 的创建、编辑、批准、停用、验证流程均可完成。
- 已发布版本上下文中 CQ 验证可读，禁止不合法的编辑动作。

## 阶段 3：Fact Audit

### 页面结构

新增 `FactAuditPage`，采用“筛选栏 + 事实队列 + 详情检查器”布局：

- 筛选：layer、claim type、audit status、stale、confidence 区间。
- 分层摘要：实体属性、直接关系、推理事实、低置信度、冲突和 CQ 答案。
- 事实队列显示自然语言摘要，但同时展示结构化 subject/predicate/value。
- 详情检查器展示 graph path、generation reason、confidence、Evidence 和审核历史。
- `direct` 与 `inferred` 使用不同且可访问的标签，不仅依靠颜色区分。

### 操作

- 支持 Generate、按配置 Sample、Approve、Reject、Needs correction。
- Reject 必须选择或输入 `linked_fix_proposal_id` 并填写原因；不满足时不提交。
- Stale Fact 只允许查看和重新生成，不允许继续审核。
- 批量批准仅允许同一层级、非 stale 且未审核的事实；拒绝和需修正保持逐条处理。
- 审核成功后局部更新列表，同时重新获取摘要，避免整页闪烁。

### 验收

- 用户可以从任一事实还原结构化事实、图路径和来源证据。
- 所有 claim type 和 layer 均有明确的筛选与空状态。
- Reject 不关联修正提案时前后端均拒绝。
- 图谱变更导致的 stale 状态刷新后可见。

## 阶段 4：发布准备与明确确认

### 页面结构

新增 `PublicationPage`：

1. 目标版本摘要及 workflow status。
2. Gate 列表：Schema validation、pending proposals、conflicts、low-confidence review、evidence
   coverage、competency questions、fact audit。
3. Blocking 和 Warning 分区，每项提供详情和修复入口。
4. Validation Report：结构化详情默认摘要展示，可展开查看原始 JSON。
5. 发布确认区：版本号、快照说明、不可变提示和显式确认控件。

### 操作约束

- 进入页面不自动发布；“重新检查”只调用 readiness。
- `ready=false` 时发布按钮禁用，并说明尚未通过的 gate。
- 点击发布先重新获取 readiness，结果未变化且 ready 才打开确认对话框。
- 确认对话框必须展示 ontology、version、gate 摘要；提交 `confirm: true`。
- 发布成功后刷新 ontology、version 和 Build Context，切换为只读已发布视图。
- 不在 v0.3 前端提供豁免操作，除非后端先提供有审计记录的正式 API。

### 验收

- 任一硬门槛失败时无法从 UI 发起发布。
- 并发状态变化会在最终确认前被发现。
- 发布成功后页面显示 publication report，所有写入口禁用。

## 阶段 5：Review Batch 深链接

### 工作项

1. 扩展 `useWorkspaceLocation`，完整支持后端生成的：
   `?project=...&ontology=...&version=...&tab=...&batch=...`。
2. 新增 `ReviewBatchResolver`：
   - 读取 batch 详情并验证项目、本体和版本绑定。
   - 根据 review type 导航 Schema、Graph 或 Facts。
   - 使用 `item_ids` 限定队列范围，不默认展示整个 ontology 的全部提案。
3. Schema Review 和 Graph Review 同时支持 `batch` 与 `proposal`；Fact Audit 支持 `batch` 与
   `claim`。
4. 页面顶部显示“当前正在审核批次”，包括 counts、状态、创建时间和退出批次过滤按钮。
5. 增加复制当前审核链接操作；复制内容必须包含版本和 batch，不能依赖 localStorage。
6. 对不存在、已完成、跨项目或类型不匹配的 batch 显示明确状态，不静默打开第一条提案。

### 验收

- 在无 localStorage 的新浏览器中打开深链接，仍能进入准确的项目、版本、页面和审核范围。
- Schema、Graph、Fact 三类批次均能正确解析。
- 完成批次后刷新 URL，页面显示 completed 状态而非空白页。

## 阶段 6：版本管理与 Evidence Explorer

### 6.1 Versions 页面

新增 `VersionsPage`：

- 版本时间线显示 parent、version number、status、workflow status 和发布时间。
- 选择任意两个版本查看 Schema Diff 和 Graph 统计 Diff。
- 从 published version 创建后继 draft，确认对话框显示父版本和新草稿语义。
- 已发布快照可查看 publication report；不提供修改操作。
- 切换版本后更新 URL 和全局版本上下文。

### 6.2 Evidence Explorer

新增可独立访问、也可作为 Review 页面 Drawer 打开的 `EvidenceExplorer`：

- 按 Evidence ID、文档、proposal/item 查询来源。
- 展示文档名、页码、chunk、字符区间、quote、content hash 和 source type。
- 在 Chunk 全文中高亮 Evidence 区间，并滚动到定位位置。
- 多来源模式并排展示同一候选的不同证据，支持 conversation/user statement/document 区分。
- 找不到原文或 hash 不一致时显示可追溯性警告，不伪造定位。

### 验收

- 可以查看完整版本谱系、比较版本并创建后继草稿。
- 已发布版本保持只读。
- Schema、Graph 和 Fact 审核都可打开统一 Evidence Explorer。
- 同一候选的多个来源可以比较并定位到原始 Chunk。

## 阶段 7：现有审核页面补强与整体收尾

### Sources

- 增加重新解析、失败重试和解析中状态轮询。
- 增加“该文档生成的提案”入口。
- 上传后保留所选文档，并正确处理 reused 状态。

### Graph Review

- 对齐 Schema Review 的单项选择、批量批准/拒绝、编辑和逐项决策。
- Merge Proposal 使用专门比较视图，明确显示“新建实体”与“合并已有实体”。
- Conflict 支持 keep existing、accept proposed 和 manual value；manual 必须使用结构化编辑器。
- Evidence 使用统一 Explorer，不再只显示孤立 blockquote。

### Schema Review

- 编辑器按 Class、Property、RelationType、Constraint 提供结构化表单；原始 JSON 作为高级模式。
- 明确区分 Class/Entity、Property/RelationType 建模歧义。
- 完善 batch 过滤、Evidence 定位和错误/警告/可豁免项视觉语义。

### 文档与回归

- 更新 `docs/guides/ui.md` 的页面清单、导航、深链接格式和人工检查步骤。
- 为稳定的纯前端状态转换补充组件测试；若当前版本不引入测试框架，则至少增加 Playwright
  mock-API 冒烟场景并配置脚本。
- 冒烟场景覆盖：深链接、Brief 保存、CQ 验证、Fact 审核、readiness 阻塞、成功发布、版本切换。

## 每阶段统一完成标准

每个阶段只有同时满足以下条件才算完成：

1. TypeScript 类型不使用无边界 `any` 绕过 API 契约。
2. loading、empty、error、disabled 和成功反馈均已实现。
3. 所有按钮可通过键盘访问，focus 可见，状态不只依赖颜色表达。
4. 1280px 桌面宽度和 768px 窄屏完成浏览器检查，无横向内容覆盖。
5. 执行 `cd frontend && npm run build` 并通过。
6. 记录人工检查的页面、数据状态和结果。
7. 如果修改 `backend/`，增加或更新测试并执行 `cd backend && uv run pytest`。

## 最终端到端验收

使用 v0.3 需求中的新业务领域场景验证：

1. 从 Overview 识别 Brief 缺失项。
2. 完成 Brief 并维护至少五个 Competency Questions。
3. 上传文档并通过深链接完成 Schema Batch 审核。
4. 完成 Entity、Relation、Merge 和 Conflict 审核。
5. 生成并完成分层 Fact Audit。
6. 运行 CQ 验证和 Publication Readiness。
7. 在所有 gate 通过后明确发布 v1。
8. 从 v1 创建 v2 草稿，确认 v1 仍只读且版本差异可查询。
9. 从任一正式知识跳转到 Evidence Explorer，定位到用户声明或文档原文。
