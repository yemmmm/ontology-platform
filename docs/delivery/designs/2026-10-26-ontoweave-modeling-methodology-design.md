## 1. 设计结论与目标

推荐以持续存在的**语义工作空间**组织建模。工作空间记录业务范围、从材料获得的命题、对命题作出的解释与决定、待解决问题，以及这些内容与实际模型的对应。人和 Agent 围绕同一份可定位的业务认知协作。

主线是：

> 界定业务目标 → 双向拆解业务与材料 → 捕获完整命题 → 解释并对齐语义 → 组装局部业务链与共享定义 → 应用和验证 → 根据新信息持续修订。

这是一组可交错的分析活动。分层总览在过程中持续形成，为理解全局、选择下一步和恢复工作提供入口。领域分析、模型表达、应用结果、验收结果分别有明确依据。

本轮目标：

| 编号 | 目标与可观察结果 |
| --- | --- |
| F1 | 大型业务有可解释的分解结构，切分依据、跨单元依赖和未处理范围可见。 |
| F2 | 保留影响业务判断的命题、条件、例外、否定、时间与口径；能识别发生在捕获之前和表达之后的遗漏。 |
| F3 | 用业务可区分性控制粒度，准确处理同义、异义、局部限制、分类与实例。 |
| F4 | 多轮、多 Agent 对同一业务判断的修改可定位，已确认与未确认含义、目标表达与实际应用不会相互冒充。 |
| F5 | 局部结果能在全局业务链上衔接，条件、状态、身份和指标的跨边界差异得到处置。 |
| F6 | 用户和获准 Agent 能从分层总览逐步深入实际内容，关键未知和跨主题影响不会被摘要掩盖。 |
| F7 | 新增、修订、撤回材料或业务决定后，能够定位并重审受影响内容，复用未变化的有效工作。 |
| F8 | 模型通过真实受治理读取及独立语义检验；捕获、理解、表达、检索、验收、运行故障可区分。 |

实现 effort 不参与本轮方案排序。仍评价语义损失、认知负担、重复状态、运行耗时和长期维护的可理解性；它们属于架构质量。有限输入和开放世界下无法证明绝对零遗漏，因此目标是明确覆盖边界、发现反例、定位损失并允许修正。

## 3. 总体结构与权威边界

~~~mermaid

    B --> C["双向分解与命题捕获"]
    C --> D["解释、身份对齐、粒度判断"]
    D --> E["局部业务链与共享语义整合"]
    E --> F["显式模型变更与确定性应用"]
    F --> G["当前实际语义模型"]
    G --> H["受治理读取与业务验证"]

    G --> I
    H --> I
    I -->|"导航到原记录；不构成业务依据"| C
    J["独立冻结验收"] --> K["绑定范围与时点的验收结论"]
~~~

所有箭头表示明确授权范围内的读取或结果引用，不表示自动授予跨角色访问。独立验收数据只向获准用户视图提供允许的结论；隐藏内容不沿总览回流生产。

采用模块化边界，不预设微服务、通用工作流 DSL 或某个 Agent 框架：

| 边界 | 负责内容 | 明确不负责 |
| --- | --- | --- |
| 材料与范围 | 原始材料修订、获准范围、材料性质、已审阅范围 | 从 Schema 或样本自动确认客户规则。 |
| 语义工作空间 | 命题、解释、业务决定、工作单元、未决问题与对应关系 | 把意图当作已经写入的事实。 |
| 语义建模方法 | 分解、语义身份、粒度、规则与关系、跨单元解释 | 由确定性校验器代替业务判断。 |
| 模型应用与受治理读取 | 验证明确变更、实际应用、资源身份、当前模型查询 | 自动补造业务条件或用摘要改写模型。 |
| 分层认知投影 | 主题组织、范围内摘要、来源导航与新鲜度 | 决定业务真伪、建模完成或验收结果。 |
| 独立验收 | 基于冻结依据、实际读取与独立题目作语义裁决 | 生产、修复或修改被验收的模型。 |

### 3.1 单一含义对应明确状态，而不是多份“当前真相”

权威来源按问题分开：

- “材料说过什么”：不可变材料修订及其定位。
- “我们如何解释、谁确认”：业务解释和决定记录。
- “本次准备表达什么”：同一语义身份下的明确变更候选。
- “当前实际表达了什么”：受治理读取到的已应用模型。
- “验收证明了什么”：绑定模型、范围及题集的独立报告。

工作空间不另维护一份可任意编辑的完整已应用本体。未修改定义引用当前模型；修改部分保存基线引用、目标内容和决定。应用后的实际身份及回执回填引用。摘要和场景地图都是这些记录的视图，不再各自编辑一套定义或完成结论。

外部对模型的修改也作为实际变更被工作空间识别：刷新相关读取、比较受影响决定和候选。无法还原业务理由时标注“实际表达已变化，依据待核对”，不替其编造确认历史。

### 3.2 正交状态

| 维度 | 示例 | 权威维护者／依据 |
| --- | --- | --- |
| 范围与材料审阅 | 范围内、已确认排除；已审阅、未审阅、无法读取 | 业务范围决定；实际材料审阅记录。 |
| 业务认知 | 提议、已确认、明确未知、冲突、已否决／被替代 | 有依据的解释与业务决定；必要时业务负责人。 |
| 表达覆盖 | 未表达、部分表达、已表达及仍缺内容 | Modeling 对具体命题和候选／模型的核对。 |
| 应用 | 未提交、已应用、明确失败、结果待对账 | 平台应用记录；不是 Agent 自述。 |
| 工作 | 可继续、等待某项输入、需要重审、当前范围收口 | 工作依赖与承担者判断；不改变业务真伪。 |
| 验证与验收 | 未验证、自查发现、独立通过／不通过／待复核 | 分别引用自查与独立报告，不能相互升级。 |
| 当前适用性 | 当前、历史、待刷新、范围不完整 | 所引用材料、模型、工作记录与权限的实际变化。 |

一个未知可以被正确表达并通过“应保留未知”的验收，但该业务问题仍未知。一个已确认规则可能尚未表达。已应用也不意味着独立验收通过。这里的示例是状态维度，不要求把所有对象塞入同一个枚举或流程状态机。

## 4. 工作空间中的最小内容对象

对象独立于 Agent 会话和 run 存续；任务、run、应用与验收只引用它们。每个对象具有稳定身份，内容修订与原记录可定位，更新指出所基于的内容。一次简单工作可以同时形成多个对象，不要求多次模型调用或逐项审批。

| 内容对象 | 最少表达的含义 | 为什么需要 |
| --- | --- | --- |
| 材料单元 | 获准材料、修订、相关片段／段落／声明的定位、材料性质与可读范围 | 区分原文与模型改写，能检查未审阅范围及来源变化。 |
| 业务命题 | 材料中一个可独立判断的完整陈述、关联材料、必要上下文及限定条件 | 避免在直接挑选图节点时丢失知识。 |
| 解释与决定 | 命题可能含义、适用范围、选择或未决结论、依据、决定者、替代关系 | 区分材料陈述与认可的业务语义，保持多轮认知连续。 |
| 语义定义／变更 | 概念、关系、行为、规则等的业务含义；身份、范围、引用和目标表达 | 将业务判断准确连接到候选和实际模型，避免副本漂移。 |
| 业务工作单元 | 局部目标、包含的命题和定义、依赖、剩余问题、收口依据 | 形成可推进的大业务分解，而不依赖聊天历史。 |
| 总览主题与摘要 | 主题成员、跨主题连接、可展开引用、当前内容与未决项的派生表达 | 支持从全局到局部的导航和共同理解。 |

CQ、材料支撑、工作依赖、概念复用、规则适用和模型对应使用不同关系含义，不混成一个泛化“related-to”。所有业务术语仍是客户模型的数据；这些对象只定义通用建模工作的组织方式。

来源支撑由工具保留已有材料定位，Agent 提供关键对应与判断；不要求重新摘录全文、每个字段独立生成证据包、增加证据 Agent。该设计对当前仅在 handoff/map note 留定位的做法作明确目标扩展，见第 14 节；不恢复旧 Evidence/Lineage 整套产品合同。

## 5. 流程一：界定目标并双向拆解

### 5.1 从业务问题形成第一版结构

开始时明确本轮获准业务范围、材料、期望支持的使用方式和已有模型。允许存在未知，不把形成完整地图、完整原子命题集或完整层级摘要设为开始语义分析的前置门。

对大型业务按需要递归分析：

> 业务目标／结果 → 端到端场景 → 事件、状态变化与决策点 → 对象、角色、条件、规则、指标 → 必要的数据和接口映射。

这是提问顺序，不是强制固定树或七阶段。一个规则可以跨流程，一个概念可以被多个工作单元引用。初始公开 CQ 帮助定位问题，但不定义完整知识全集；独立隐藏题仍保持隔离。

每个工作单元写清：想解释什么、输入／触发与结果、相关主体和条件、与外部单元的连接、尚未明确的部分。无法合理拆开的紧耦合规则共同分析；工作单元不等于一个 Ontology、文件、Agent 或权限边界。

### 5.2 从材料反向补充结构

按原始材料的可定位单元审阅，捕获获准范围内有业务意义的陈述，再映射到工作单元。无法归入现有结构的命题必须得到处置：补充既有单元、提出新单元、识别重复、保留疑问，或按实际授权确认其不在范围内。

不能因为当前 CQ 不问、图中无节点或主题聚类未收录，就排除某项范围内知识。材料目录与已审阅范围覆盖无命题区域，避免只检查已抽出的内容而漏掉从未进入候选的段落。材料单元分别说明“已审阅且有相关命题”“已审阅且无相关业务内容”“未审阅”“无法读取”或“有授权依据的范围外内容”；“未审阅”和“无法读取”不能充当无命题的结论。

工作单元边界可以修订。若大量解释都需同时反复读取两个单元，优先检查切分是否割裂了一项完整业务判断；若一个单元内部存在互不依赖的决策，可以进一步分解。调整保留原有内容和引用，不重置已经有效的分析。

## 6. 流程二：捕获完整命题，分开观察与解释

### 6.1 原子性按判断边界定义

业务命题是“在相关上下文中能够独立判断的一项陈述”。它可以包含多个实体、合取／析取条件、量词、例外或跨句引用；不等于一个句子或一个三元组。

例如，以下是示意材料，不是当前项目事实：

> 普通工单验收通过后可关闭；返修工单还须填写关闭原因。紧急处置可暂缓原因补录，但不能豁免验收。签收不代表验收。

捕获时分别识别普通关闭规则、返修附加限制、紧急例外的准确作用范围、签收与验收的区别，并保留它们的共同上下文。不能把紧急例外扩大为豁免全部条件，也不能把“签收不代表验收”删成无关说明。

命题内容保留有意义的主体、参与角色、行为／关系、适用范围、条件、否定、数量、时间、指标口径和例外。还须区分陈述性质与模态：定义、状态／已发生事件、规则、意图、计划、预测或建议，以及其中的许可、义务、禁止和可能性。关联谁作出陈述、依据何种材料；引用某人提出的建议不等于该建议已被业务采纳。

例如“经理可以批准退款”不等于“退款只能由经理批准”，“预计周五发货”不等于“周五已发货”，“系统必须保留记录”不证明系统已经执行。对“只有、全部、不得、从不”等表述保留适用总体和时间，不能从几个样本或未出现记录推导全称／否定结论。模态与业务有效时间分别保留，未来计划不会仅因到达日期而自动变为已发生事实。

缺少某个维度并不要求补值；保持未给出的部分。复杂逻辑保留可核对的自然语言和分组，不强制转成可执行规则 DSL。

### 6.2 两次不同目的的审阅

第一次关注材料表达了什么，允许开放术语、重叠表述和未解指代。第二次关注这些命题共同意味着什么，才决定概念身份、关系方向、共享定义和表达结构。

这两种关注可在一次有界分析中完成，也可随复杂度分开；不要求所有材料先抽完、固定两个 Agent 或两轮模型调用。对指代或上下文不完整的命题回读关联原文，不能用上层摘要补造缺失条件。

材料陈述、抽取解释、业务确认分开记录。明确获准作为业务依据的材料可按任务既有规则支持直接陈述，无需逐条请用户重新批准；确认记录标明实际依据和确认方式。模型自己提出的解释不能因为写入工作空间就变成业务确认。数据库主外键、CHECK、样本和 API 字段是相应技术结构的证据，不自动成为业务规则；外部业务行继续留在源系统。

## 7. 流程三：解释、身份对齐与粒度控制

### 7.1 按含义对齐

先从已有模型和工作空间检索相关定义，核对完整含义与周边引用。对开放表达写出必要的自然语言定义，再比较身份、角色、方向、范围、条件、时间和单位。

选择只有六类语义结果：复用同一含义、在既有含义上增加局部限制、建立不同含义并关联、提出共享含义修改、明确未知、保留冲突。不得仅按名称、连接度或向量相似度归并；没有合适候选时允许新建有依据的定义。

### 7.2 粒度的操作准则

| 提问 | 对表达的影响 |
| --- | --- |
| 差异是同一对象在连续生命周期中的状态、参与角色或上下文限制吗？ | 先核对身份连续性，优先表达状态／角色／局部规则；订单草稿与已批准、同一客户作为付款方与收货方，不因此成为不同实体。 |
| 能否找到一个业务情境，A 与 B 会导致不同答案、规则或结果？ | 若成立，应表达区别；例如签收成功且验收失败。此判断决定需要区分含义，不直接决定拆分身份或建立子类。 |
| 它是否有独立身份、独立事件的发生、参与关系或被其他规则单独引用的必要？ | 结合已有身份连续性决定对象、事件、角色或关系的表达；责任或所有者变化本身不证明对象身份改变。 |
| 拆开后是否破坏条件组合、量词作用域或事件参与关系？ | 用完整规则／关联结构保留组合作用，不机械展开为孤立边。 |
| 共性是否在多个真实用途中稳定成立，而且有材料依据？ | 才考虑共享抽象；字段相同或反复出现不构成分类依据。 |
| 继续细化是否增加范围内的业务区分能力或保真度？ | 若没有，停止细化；仍保留完整定义和必要限定内容。 |

规则、指标和复杂关系同样执行此判断。一个指标名称相同但时间窗、分母或排除项不同，必须保留口径区别；不因名称相同复用一个计算定义。

不强制从实例归纳类，也不从类定义虚构具名实例。模型可以表达概念、规则、行为和明确未知，而无需把每个命题都变成独立 RDF 节点。

### 7.3 业务澄清

只有缺失信息会改变当前业务结论时才提出澄清，说明一个具体区别情境、受影响的判断和已有依据。复用已确认答案。未回复不是确认，材料相互冲突时不自动按最新消息获胜。

提问不冻结无关工作。未知应缩到具体业务含义；“已知但尚未表达”“工具不支持”“尚未读取”分别作为表达或工作缺口，不改名为业务未知。

## 8. 流程四：局部闭合与全局整合

### 8.1 局部语义闭合

一个工作单元当前可收口，意味着：

1. 当前单元声明范围内的材料已审阅，关键命题有明确解释或未知／冲突处置；范围外材料有实际范围依据，不能由 Agent 为收口自行排除。
2. 对目标业务判断所需的身份、路径、条件、例外和结果已有足够表达；无法表达的已知内容明确记作缺口。
3. 对相邻单元所依赖的定义和条件已核对，或指出准确的未决连接。
4. 正常、条件不满足及相关例外情境能得到符合材料的解释；自查结论带有本次覆盖边界。

未审阅或无法读取的相关材料存在时，可以交付有价值的局部成果，但该单元的材料覆盖仍为不完整，不能记作范围闭合；下一步仍指向准确的审阅缺口。此要求不阻止开始或应用已安全确认的局部语义，也不要求每次局部推进前通读整个项目。

闭合不等于业务事实全部已知、模型已应用或独立验收已通过。没有材料的部分不能借“闭合”被排除。材料已经审阅但业务本身未给出答案时，保留的是业务未知；材料尚未审阅时，保留的是工作缺口。授权范围仍未处理时项目继续保留剩余工作。

### 8.2 全局整合关注连接语义

局部推进后即检查相关连接，不等待所有单元结束：

- 上游“完成”能否满足下游“允许开始”的条件。
- 两个流程引用的主体是不是同一身份，或者只是同一个角色名称。
- 共享动作的必要条件、失败效果、单位和时间是否一致。
- 某项例外是本地限制还是修改了共享规则。
- 某个指标的输入、去重、空值和计算范围能否跨单元衔接。

如“安装完成”是否足以允许结算，应按材料核对验收、签收等额外条件。图上存在一条路径不等于这条业务链可成立。

遇到冲突先比较两个完整解释及适用上下文，再决定共享、局部化、区分或澄清。缺陷回到相应命题或决定修正，不通过增加同义节点或模糊摘要消除冲突。

### 8.3 持续推进与停止

下一项工作由实际剩余问题和依赖选择，优先解决影响多个单元的歧义、阻断关键业务链的缺口，以及能形成完整验证样例的单元。优先级由建模负责人作可解释判断，不要求算法评分或固定次数。

当继续拆解不能改变范围内的业务理解、已审阅材料有处置、跨单元连接有依据、剩余未知已明确且满足约定交付条件时停止细化。范围或授权改变才扩展目标；不能为了“更完美”无限补充外围知识。

## 9. 共享业务认知如何精确维护

### 9.1 修改的对象是明确判断

每次有实质新信息，指出：涉及哪个稳定语义身份／命题、当前判断、拟改变的部分、新依据、适用范围与时间、影响的使用者和未决问题。聊天可以解释决定，但共同状态从决定记录读取。

| 新信息性质 | 处理方法 |
| --- | --- |
| 重复支持 | 关联新增支撑；含义没有变化就复用已有判断和表达。 |
| 新增局部条件 | 修改该上下文的规则或用途，核对是否影响共享定义。 |
| 对旧解释的纠正 | 保留原判断和纠正依据；重审由旧解释推导的内容。 |
| 真实业务规则变化 | 记录实际生效范围与时间，区分历史仍成立的规则。 |
| 同时有效且相互冲突 | 保留冲突两方、影响与待确认项；不能自动选较新文本。 |
| 来源修订／撤回 | 检查其他支撑与独立确认；失去支撑标记待重审，撤回材料本身不证明业务事实为假。 |

业务生效时间只在材料或业务决定支持时填写。记录时间表示平台何时得知，不能代替业务时间。普通文字修正不制造业务规则变化；规则后来被纠正也不改写旧验收当时采用的依据。

### 9.2 共享维护与并行协作

共享定义有一个负责协调含义的维护方，其他单元提出明确差异。维护方不自动获得业务确认权或平台权限，也不要求一个专职 Agent。

更新指明所基于的定义内容。另一项已确认变化使基线失效时，返回具体差异供重读和合并判断；不采用最后写入覆盖，不永久终止任务。不同单元的独立工作继续推进。

一次决定同时说明需要重审的引用，维护方与引用方分别给出保持、修改、未知或冲突结论。依赖遍历只是候选影响集；语义影响是否传递由含义判断，不能把图上可达的所有节点全部强制返工，也不能仅检查直接边就声称无间接影响。

### 9.3 增量进入同一方法

新任务先查看当前获准总览与实际相关模型，定位变化涉及的工作单元，再进入第 5—8 节的局部循环。不重新理解全部项目，不盲信旧摘要，也不把换 run 视为业务认知清零。

影响链为：材料／决定变化 → 命题与定义 → 使用它们的业务单元及关系 → 受影响验证 → 相关主题摘要。共享定义的跨主题使用同时进入影响集；没有完整依赖记录时主动检索并标注核对边界。

## 10. 分层总览作为共同认知入口

### 10.1 一份内容，多粒度阅读

总览在建模开始后即可逐步生成，既包括当前模型，也包括明确标识的候选、未处理范围和业务疑问。可以从项目进入业务领域／流程，再进入专题和具体定义；层数随内容调整，不要求固定四层。

主组织结构沿已确认的业务范围与解释建立，允许多父引用和跨主题连接。社区算法形成另一种可重建的发现视图，用来提示紧密主题与跨范围联系。发现视图不自动改写业务结构、Ontology 拓扑、共享身份或授权。

例如，“关闭工单”可以同时出现在安装、返修和结算视图中，引用相同的适用定义与不同局部规则。摘要中明确哪些内容共享、哪些条件只在某个上下文成立，不复制三份独立“当前定义”。

### 10.2 每层应呈现什么

| 内容 | 组织方式 |
| --- | --- |
| 业务主线 | 本主题解释什么，主要对象、行为、条件和结果如何连接。 |
| 当前认知 | 已确认判断；重要未知、冲突和适用范围。 |
| 表达与交付 | 已有模型表达、候选修改和待交付内容；应用及验收结论分别引用。 |
| 横向关联 | 共享定义、上下游条件、跨主题依赖与影响。 |
| 深入入口 | 可展开的子主题、具体定义、原始材料或工作记录，在当前读者获准范围内提供。 |
| 当前适用性 | 所依据的内容时点、覆盖范围及待刷新部分。 |

关键未知、冲突和决定结果的例外，必须以可展开条目传播到相关上层；条目过多时可分组分页，但不能因摘要篇幅截断而显示“没有问题”。重要性不能只用出现频次或图连接度决定。

### 10.3 如何生成，如何防止摘要逐层失真

每层输入包含：所覆盖成员的当前内容、可复用的下层摘要、关键未决条目、跨主题连接和相关限定条件。状态值及适用范围来自原记录，LLM 组织叙述；程序不能验证语义忠实度，仍需要对关键条件、结论和反例作内容核对。

上层摘要引用下层摘要用于压缩和导航，同时保留追到原定义或原记录的链。不能把一段无来源的“摘要的摘要”当作确认依据，也不能从摘要重新抽取出“新事实”后写回模型，形成自我证明循环。

摘要不声称完整替代细节。涉及业务修改、条件判断或精确回答时，Agent 必须沿入口读取相关实际内容；仅了解全局和定位工作时可以停留在摘要层。

### 10.4 谁能看到什么

- 用户视图：按用户获准业务和管理范围，组合语义、工作和允许展示的验收结论。
- 生产视图：获准材料、当前模型、公开问题、可见决定及工作状态，不包含隐藏题、答案和私有验收诊断。
- 消费者视图：以获准已应用模型为依据的业务导航；不将内部候选或待确认计划伪装为当前模型内容。
- 独立验收视图：基准验收直接使用冻结模型、获准依据和题目。若要验收“摘要辅助消费”，单列模式，摘要只由冻结获准模型生成，并验证引用；不混入生产工作记录或隐藏答案。

授权范围在摘要生成前确定。不能先对更大范围生成摘要，再尝试删掉敏感名词；权限变化影响已有摘要的可读资格，旧摘要不得越权复用。摘要必须说明可见范围的限制，不能把不可见解释为不存在。

### 10.5 更新与成本

材料、定义、范围、决定、应用、验收或权限发生相关变化时，标记受影响主题及其上层、横向关联摘要需要更新。按需读取或有价值的阶段完成时刷新，合并连续小改动；无变化复用当前结果，不为每个工具调用重生成全树。

语义内容、工作进度与验收状态引用不同截止点，不能只用一个模型修订号冒充全部一致。生成期间输入变化时，新结果可保留为历史，不能标为当前。仅修改工作状态时可复用未变的业务内容摘要。

跨主题结构明显变化时重算相关发现结构，再更新成员与祖先摘要；覆盖检查包括孤立资源和未进入聚类的内容。内部依赖无法确定时，宁可扩大必要刷新范围或披露过期，也不声称已精确增量。

运行成本须记录，收益用实际阅读、续接和判断效果检验。层级更深、摘要更多不自动代表更好，展示可选择最能帮助当前问题的层次。

## 11. 模型表达、应用与验证

### 11.1 表达与执行

Modeling 明确业务含义及变更意图，确定性程序补足执行字段并应用。沿用现有编译器和可恢复应用方法，不恢复独立模型 dry-run、Protocol 翻译审批或专用规则引擎作为默认门。

所需业务语义必须出现在实际模型可读取的定义和关系中，不能只停留在工作空间或摘要。原文支撑、决策历史与模型表达分别定位；表达合同不足时保留已知缺口并修正合同，不把已知内容假称未知。

应用边界要保护共享语义一致性。可在一个原子应用中完成的相关变更成组应用；跨现有原子边界时，采用含义明确的兼容新增及安全引用迁移，或暂缓无法保持一致的变更组。不得假设 PostgreSQL 与 RDF、多个 Ontology 或多个 Batch 天然构成全局事务。

成功回执证明确定性应用结果，相关业务自查通过真实受治理读取核对含义。无需每次成功写入后重复全量读回；在完整业务单元形成、关键共享含义变化及最终验收时进行有价值的读取。

### 11.2 四个不同的质量问题

| 检查 | 要发现什么 | 不能替代什么 |
| --- | --- | --- |
| 材料覆盖 | 相关段落／声明是否被审阅，重要命题是否被遗漏，未审阅范围是否公开。 | 已提取命题自己检查不出未捕获信息。 |
| 解释与表达保真 | 条件、否定、量词、例外、时间、身份和口径是否被正确理解并表达。 | 解析成功、字段齐全不能证明语义正确。 |
| 跨单元一致性 | 定义复用、业务状态衔接、条件组合和共享影响是否成立。 | 存在图路径或局部自查通过不能证明全链成立。 |
| 实际消费与独立验收 | 在获准模型中能否得到完整且正确的业务答案。 | 生产者自述、内部工作笔记、摘要或结构检查不能代替。 |

命题到表达的核对至少双向进行：材料中的重要命题在哪里表达或为何未交付；模型中的关键断言依据什么。另从原始材料审阅范围查漏，防止双向核对的两端共同遗漏同一内容。

关键规则验证包括正常成立、必要条件不满足、适用例外以及容易混淆的概念对照；这是语义情境校验，不要求恢复可执行规则引擎。自查问题可以随理解深化而补充，独立冻结题目及其裁决标准不能由生产方为求通过而修改。

### 11.3 独立验收与修复

独立题目与评分依据先由独立侧根据获准业务范围和原始依据准备，正式生产前完成既有要求的题集冻结，生产侧只接收公开投影。过程中可新增公开自查情境；真实业务范围或依据变化时，由独立侧明确维护对应题集及变化记录，不按候选模型的答案倒改评分标准。

正式验收再绑定实际模型、允许依据、题集和读取条件；已有报告只在其绑定仍适用时用于当前结论。生产不在验收冻结目标上继续修改。

验收发现问题后，按获准公开程度反馈缺口，回到原始材料、解释、模型表达或检索的准确失败层。隐藏题正文、答案和私有理由不进入生产工作空间；如需要真实业务澄清，通过另有依据的业务渠道提出。修复形成新的实际目标后另行验收，旧报告不覆盖。

内容分析中使用捕获、解释、表达、查询等定位；最终失败分类仍沿 modeling-quality、platform-contract、collaboration/routing、runtime/infrastructure。前者帮助定位语义损失，后者避免把平台问题当作模型质量失败。

## 12. 职责与运行组织

方法中的职责包括业务确认、范围与整合、语义分析／表达、确定性执行、独立评价，以及用户沟通。职责可以由少量 Agent 承担，也可以在复杂业务下按工作单元并行；独立评价与生产保持隔离。

单一 Modeling Agent 可以在一个单元内完成捕获、解释、建模和自查。复杂业务的并行单元通过稳定定义、命题及决定协作；不按每一种视角或每一步方法固定设置 Agent。

协调者负责跨单元理解和语义差异的处置；程序负责有明确合同的等待、执行、投影和恢复。会话结束不丢失业务状态，恢复依内容和实际应用结果继续。可修正的格式、缺字段、摘要过期或协作问题不成为 run 永久死亡条件。

分层总览帮助定位下一项工作，但不自动派单或扩大授权。决定使用哪份资料、写入哪个模型、启动哪次修模以及消耗预算，仍在同一获准任务边界内；换工作单元、Agent 或 run 不重置资源授权。

## 13. 贯穿示例：工单关闭规则的理解与维护

以下均为设计示意，用于暴露方法差异，不写入真实模型。

| 环节 | 处理结果 |
| --- | --- |
| 目标 | 理解普通工单与返修工单何时允许关闭，以及关闭是否足以触发结算。 |
| 双向分解 | 形成关闭判断、验收、返修附加要求、结算条件等关联单元；材料中的紧急例外必须有归属。 |
| 命题捕获 | 保留验收必要性、返修原因要求、紧急仅豁免补录时点、签收不代表验收。 |
| 粒度判断 | 用“签收成功但验收失败”区分两个事件；返修要求先作为局部规则，不能直接修改所有工单。 |
| 共享整合 | 关闭与结算分别保留条件；缺少“关闭足以结算”的依据就明确未知，不因图上相邻而建立因果。 |
| 表达与读取 | 模型中能读到准确条件及未知，工作笔记里存在不算已经表达。 |
| 总览 | 项目层提示“关闭条件已有表达，关闭与结算的充分关系待确认”；返修专题展开原因要求和紧急例外。 |
| 新信息 | “11 月起普通工单也须关闭原因”先核对来源和适用时间，判断是政策变化还是对旧解释的纠正。 |
| 影响维护 | 重审普通关闭规则及相关消费问题；返修既有要求未变化部分复用，更新涉及主题及上层摘要。 |
| 独立检验 | 验证条件不满足时不会答成可关闭，紧急例外不扩散到验收，未知结算条件不会被补造。 |

| R4.2-002：介绍、一句话进度、CQ 与验收结果 | 目标扩展为分层业务总览；用户继续能看懂范围、成果和未决内容，技术字段留在展开的依据层。 | [概览页面](../../../frontend/src/pages/OverviewPage.tsx)。 |

迁移按内容连续性组织：先识别现有模型、候选、地图和决定的真实来源；能明确对应的内容导入工作空间，不能追溯的标为已有模型／依据待核对，不要求为历史对象伪造命题。新工作按新方法进行，旧 run 和原验收证据保持。地图或旧摘要在交接前可供读取，主写入口切换后只生成派生视图，避免长期双写。

数据库、Agent runtime 和外部框架选择不由本方法论预设。现有 FastAPI/MCP、PostgreSQL/RDF 和原子执行边界可继续承担职责；任何替换都应解决已明确的内容或一致性问题。无需先更换整个运行框架才能验证方法。

## 15. 实质决策表

以下均为按本轮设计授权采用的推荐方案，除标明沿用者外，不冒称用户逐项确认。

| 编号 | 决策 | 取舍与理由 |
| --- | --- | --- |
| D1 | 以持续语义工作空间和业务工作单元组织流程。 | 内容与决定独立于 Agent 会话，支持局部推进和跨轮接续；不以固定角色链作架构中心。 |
| D2 | 业务目标向下分解与材料命题向上补充双向进行。 | 避免只围绕已知 CQ 建模或按文档切块误定业务边界。 |
| D3 | 捕获完整命题与确定语义表达分开思考，但不固定调用次数。 | 保留限定条件，避免增加无意义阶段交接。 |
| D4 | 以区分性情境、身份、上下文和引用需求决定粒度。 | 能说明为什么拆、为什么合，不靠固定节点数或相似度阈值。 |
| D5 | 语义解释、业务决定、目标表达、实际应用和验收各有依据。 | 避免多份当前真相和一个状态冒充全部结果。 |
| D6 | 共享更新先判断重复、限制、纠正、业务变化或冲突。 | 保护局部用途与历史含义，源撤回先检查剩余支撑。 |
| D7 | 局部闭合与跨单元整合交替，按真实影响重审。 | 既避免全局前置等待，也避免最终才发现业务连接断裂。 |
| D8 | 分层总览是持续派生认知层；业务组织与社区发现分工。 | 同时支持整体理解和细节读取，保留关键未知与横向关系。 |
| D9 | 摘要按授权范围生成、随相关变化失效，不作为语义自证。 | 摘要压缩不能泄露隔离内容、遗忘关键例外或形成循环依据。 |
| D10 | 明确扩展最小命题支撑及变化维护；保留直接应用、未知表达和独立验收。 | 为保真和持续维护提供必要输入，不恢复旧证据、规则引擎或 dry-run 流水线。 |

不宣称存在无权衡的“完美架构”。本提案选择可解释的业务分解、明确的权威边界与可修正的循环，并用下面的反例检查其质量。不存在需要替用户确定的客户业务事实；具体建模任务中的未知仍由获准业务材料和负责人解决。

## 16. 验证设计与效果边界

本轮仅完成设计与审阅。下列验证未执行，不记作功能或真实语义 PASS。

| 编号 | 反例／场景 | 预期与证据 |
| --- | --- | --- |
| A1 | 材料含当前 CQ 未涉及的范围内例外；80 页政策仅阅读了 10 页 | 未读材料阻止“范围已闭合”的结论但不阻止局部推进；完整审阅后例外进入正确单元及表达或明确缺口，不被问题集排除。 |
| A2 | 规则含否定、合取条件、例外及跨句指代 | 捕获、解释、模型和读取保持作用域；正常／失败／例外情境能区分。 |
| A3 | 签收与验收同现，订单有多个状态，同一客户同时担任两个角色 | 区分性情境支持正确表达；不虚构实例、不误归一，也不把状态／角色差异误拆成不同实体。 |
| A4 | 两个业务单元都使用“客户”或“完成” | 比较身份与条件，复用或区分有依据；图连通不冒充业务可衔接。 |
| A5 | 已确认但未表达、已表达未知、已应用未验收同时存在 | 各状态在工作空间、总览及消费结果中保持区别，任何一个不会自动提升其他维度。 |
| A6 | 两个 Agent 基于不同旧定义提出共享修改 | 第二次修改识别基线变化；受影响引用重审，无静默覆盖，无关工作可继续。 |
| A7 | 新资料只新增支持、增加局部限制或改变生效日期 | 三种变化导致不同处置；不会每次重建全模型或把局部规则变成全局规则。 |
| A8 | 唯一来源撤回、多个来源中一个撤回、历史政策仍有效 | 检查剩余支撑和业务确认；不将删除文档直接等同删除真实事实。 |
| A9 | 高频主线正常，低频例外决定能否操作 | 上层总览保留关键例外／待决入口；按频次摘要不会吞掉它。 |
| A10 | 一个共享定义被多个主题使用，有孤立资源 | 修改使所有相关主题和上层待刷新；未进社区的内容仍可定位，不被遗漏。 |
| A11 | 摘要生成期间模型／工作决定变化，或读者权限变化 | 旧结果保留正确时点和资格；不作为当前、完整或越权内容返回。 |
| A12 | 摘要出现推断、候选尚未应用、隐藏诊断存在 | 推断不写回为事实，消费者不误读候选，生产摘要不包含隐藏内容。 |
| A13 | Agent 会话退出后由新 Agent 接续 | 不读完整聊天即可定位业务范围、当前判断、实际应用、剩余工作及必要原材料；不重复已确认应用。 |
| A14 | 外部客户端修改模型，或多 Batch 修改中途失败 | 以实际模型和回执恢复状态；不靠工作空间意图或摘要声称全部成功。 |
| A15 | 模型正确但召回不完整，或运行／平台失败 | 分层定位后沿原失败分类报告，不能推导模型错误或通过。 |
| A16 | 某范围自查通过，独立验收失败或仅覆盖部分 | 保留各自范围、输入与结论；不把局部通过写成项目完成。 |
| A17 | 许可与义务、计划与已发生事件、建议与正式政策并存 | 命题、模型和摘要保留陈述性质、模态、陈述主体及适用范围；不因到达预计日期或出现在建议文件中而升级成事实。 |

实际方法验证应选用包含至少两个相互依赖业务单元、共享定义、条件／例外和一次资料变化的完整场景。先验证模型直接消费，再独立评价分层总览辅助理解；比较范围、材料与难度一致，保留非盲或盲测条件。衡量：遗漏与无依据断言、粒度错误、跨单元衔接、未知保留、接续准确率、修改影响遗漏，以及全过程耗时和用量；不以图大小、摘要字数或缓存率代替效果。
