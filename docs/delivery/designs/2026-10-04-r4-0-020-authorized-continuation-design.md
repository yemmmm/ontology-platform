# R4.0-020 阶段汇报与任务收尾分离及授权内持续推进设计

## 1. 范围、基线与状态

- 权威范围：[R4.0-020](../../requirements/requirements-v4.0.md#r40-020-阶段汇报与任务收尾分离及授权内持续推进)。本设计细化“阶段结果已报告”与“整个获准目标已完成/必须等待”之间的判断，以及资源、监督和交接边界。
- 关联合同：[modeling-dev-loop Skill](../../../skills/modeling-dev-loop/SKILL.md)、[progress report](../../../skills/modeling-dev-loop/references/progress-report.md)、[Team runbook](../../../skills/modeling-dev-loop/references/team-runbook.md)、R4.0-016～019 设计。R4.0-018 决定 production stop 后如何接 acceptance；R4.0-019 决定新入口复用的配置记录；R4.0-017 决定运行故障恢复。
- 当前状态：需求细化与设计；不重开已结束 run、不启动真实建模、不新增额度。现有 `get_pending_actions`、`resume_live_run`、`stop_run`、checkpoint 和 progress report 足以承载大部分行为，暂无证据要求调度框架或后台任务。
- 已知问题：过去的执行记录出现阶段清理后才收到“继续”要求，导致资源恢复和上下文重建。清理本身不自动算错误；本条要求阶段汇报先给出剩余目标、条件和下一动作，再决定继续、等待或收尾。

## 2. 报告用语与停止条件

本条只规定阶段报告中的自然语言字段，不新增平台状态枚举或任务状态机。每次阶段报告回答：

| 报告问题 | 要写的事实 | 宿主动作 |
| --- | --- | --- |
| 本阶段完成了什么？ | 可定位的角色/阶段结果和范围 | 继续检查原目标是否仍有明确待办 |
| 原目标还剩什么？ | 未完成范围、依赖和下一动作 | 判断是否仍在已有授权内且条件已满足 |
| 为什么现在不能继续？ | 缺业务决定、权限、兼容性、额度、截止时间或真实运行状态的具体原因 | 完成不依赖该原因的工作后等待 |
| 是否可以收尾？ | 原获准目标和完成依据是否都满足，或用户明确暂停/取消/到期 | 按资源生命周期停止和清理 |
| 谁接续观察？ | run/process/checkpoint、待办、授权余额和责任 | 没有后台安排就如实交接，不说“持续监控” |

阶段报告不是任务完成证明。`RUNNING`、角色 terminal、进程退出、资源清理和报告落盘也都不能单独证明原目标完成。

## 3. 决策表

| 决定 | 选择 | 原因与边界 |
| --- | --- | --- |
| D020-1 | 每次阶段报告写清已完成范围、剩余范围、下一动作、授权依据和等待原因（无则写无） | 让宿主能从阶段成果直接进入下一动作，避免仅凭“完成”收尾；沿用现有记录，不创建新的任务状态机 |
| D020-2 | 条件满足且在授权内时继续当前目标 | 用户已授权的明确待办不要求重复说“继续”；live resume 和 acceptance continuation 不新增 fresh start，production checkpoint continuation 仍按既有合同消耗 1 次 fresh semantic start |
| D020-3 | 实质缺少业务定义、权限、兼容性决定、截止时间或新额度时等待 | 这些信息会改变范围/语义/授权，不能由宿主猜测；其他独立工作继续完成，具体写明阻塞和影响 |
| D020-4 | 资源按实际生命周期清理或保留 | 结束进程临时密钥及时撤销；仍服务于连续任务的资源按授权保留；已撤销密钥不复活，必要重建如实记账 |
| D020-5 | 不把授权余额当消耗目标 | 额度是上限，不是必须用尽的次数；耗尽后不新开 production，但安全写状态核查、已授权 acceptance 和收尾可以继续 |
| D020-6 | 监督结束时只交接事实 | 交接不创建后台监控或自动恢复；由下一观察者按记录决定是否继续，不能用“已移交”冒充完成 |

## 4. 持续推进流程

### 4.1 阶段汇报后

1. 读取当前 run 的 status/events/pending actions 和实际产物，区分角色结果、handoff、写入和验收结论；不只读最后一句角色消息。
2. 列出原目标剩余项，检查每项是否仍在授权、是否需要已完成的依赖、是否存在 unknown write 或存活 writer。
3. 若可继续，报告下一动作后立即使用已获准入口：存活 thread 用 `resume_live_run`；已停 run 用当前 checkpoint 合同；production handoff 后按 R4.0-018 先 stop/exit 再 acceptance；已定位窄修复用原 issue/recovery 路径。
4. 若必须等待，写清缺失输入、为什么影响下一步、独立可做项和恢复入口；不拆出新的授权范围，也不通过重复询问已确认的配置/业务答案拖延。

阶段报告可由宿主记录，不要求每个工具调用产生新报告；有效进展是完成候选/交接/回执/检索证据或解决问题，重复轮询和重复错误不算进展。

### 4.2 任务收尾与资源

只有原目标完成、用户暂停/取消、截止时间到达、授权边界已到且无可继续的安全动作，或不可恢复的真实阻塞需要停下时，才进入收尾。收尾记录：

- 真实 run/process 状态、root/checkpoint/handoff 和第一阻塞；
- 已执行、未执行和仍待办的范围；
- production/acceptance start 余额及其来源；
- 临时主体、密钥、FIFO、lock、worktree 等资源的保留/撤销/待核实状态；
- 下一责任人和可执行的恢复步骤。

R4.0-018 的生产停止是内部阶段切换，不代表整个任务完成。R4.0-019 的配置改变只影响新启动，不构成自动重启理由。未知写入必须先按既有 Batch/Attempt/receipt 对账，不能因为“阶段完成”直接清理现场。

### 4.3 交接

交接正文先说明业务/语义结果，再给 run id、证据和资源细节。至少链接 progress report、原始失败和下一动作。没有真正安排的后台观察者时写“需后续人工/宿主观察”，不能写“后台持续监控”。

## 6. 验证计划

共享用例见[测试计划](../test-plans/2026-10-04-r4-0-018-021-operations-coordination-test-plan.md)。核心场景：

| 场景 | 预期 |
| --- | --- |
| A1 隐藏验收结束、公开验收仍在原范围且条件满足 | 汇报分段结果后继续，不需重复授权/“继续”确认，不报整体完成 |
| A2 production handoff 后必须 stop/exit 再 acceptance | 停止是内部切换，checkpoint、待办和额度不丢失 |
| A3 缺业务决定/权限/兼容性选择/新额度 | 完成不依赖它的工作，写清 wait reason，不静默扩权或猜语义 |
| A4 用户暂停/取消/到期/目标已完成 | 正确停下并按生命周期清理，剩余额度不触发无必要运行 |
| A5 连续任务资源恢复或监督交接 | 已撤销凭据不恢复；交接能定位真实状态/下一责任，不虚报后台监控 |

设计阶段只做文档结构和链接检查，不运行真实 Team。开发/独立功能验证应分别记录；真实语义和 runtime E2E 仍须另行授权，不能用模拟的“继续”消息宣称完成。

## 7. 设计完成边界

本设计不宣称 R4.0-020 已实现或已证明宿主会自动持续推进。实现后仍须按证据区分“阶段汇报”“授权内继续”“等待”“资源收尾”和“任务完成”；缺少真实运行证据时保留 PARTIAL。
