## 2. 方案取舍

| 方案 | 优点 | 当前问题与选择 |
| --- | --- | --- |
| 平铺步骤列表，名称／文本指定参数 | 文本简短 | 无法可靠区分重复调用、同类对象、循环作用域；不采用 |
| 普通语义节点＋明确关系＋少量标量属性 | 复用现有身份、授权、写入和读取，结构可解释 | 需形成清晰建模词汇和示例；采用 |
| 新增工作流 AST／平台资源类型及流程编译器 | 可集中提供执行结构校验 | 引入未要求的执行语法与平台专属结构，当前没有必要；不采用 |

本设计确定的是语义表达约定。下文英文名字是建议的建模词汇 local name，必须作为普通
predicate／entity 定义随模型声明，并附业务含义；不是保留的 REST 字段、平台命令或七类
固定资源类型。词汇的模型内身份稳定，同义关系按获准定义明确映射，不由平台按名字猜测。

不新增 `process_definition` JSON、`create_process` 命令、数据库表、业务执行器、流程画布，
也不向全平台强制注入一套 Class。现有字段足够时优先只交付方法、合同示例和验证增量。

## 3. 分层与责任

```mermaid
flowchart LR
    A[业务资料与已确认定义] --> B[Modeling：流程、调用、值引用、绑定、转移]
    B --> C[Protocol：既有候选翻译与身份绑定]
    C --> D[既有 Batch dry-run / apply]
    D --> E[普通 RDF 节点、属性、关系]
    E --> F[受治理详情、事实与关系读取]
    F --> G[Consumer：结合可见范围解释业务流程]
```

- Modeling 解释业务含义，选择来源、判断和循环结果语义；资料不足时保留未知。
- Protocol 只翻译获准候选、解析显式身份并按现有依赖阶段写入，不能替 Modeling 补分支或参数。
- 平台验证既有输入、引用、授权、Shape 和写入完整性，不判定某业务动作已满足执行条件。
- Consumer 不把局部可见模型当完整运行方案；独立语义验收根据资料核对流程含义。
- 003 提供共享 Action／参数身份；004 仅创建流程内的使用位置和绑定。011 提供 API 细节，
  007 处理共享定义变更，008 负责未来自动上下文组装。

## 4. 最小图表达

### 4.1 节点与标量

所有下列内容均使用现有普通 `entity`，`class`／`classes` 可省略。通过
`semantic_definition.semantic_role`、`business_meaning`、`applicability` 说明含义；
`unknowns`、`not_applicable`、`conflicting_meanings` 保留已披露状态。

| 语义位置 | 建议 role | 所需内容与身份 |
| --- | --- | --- |
| 流程 | `process` | 稳定身份、名称、目的、范围；明确入口和终点 |
| 业务调用点 | `action_call` | 流程内稳定身份；一个 Action 引用；所属上下文 |
| 流程输入／输出定义 | `process_parameter` | 身份、方向、对象／值含义、必填或出现条件、单值／集合；复用 003 参数说明约定 |
| 值引用 | `value_reference` | 身份、所属作用域、来源种类及对象／值含义；不保存实际实参 |
| 参数绑定 | `parameter_binding` | 身份、输入或流程输出用途、目标位置、来源；条件化绑定有明确适用范围 |
| 控制转移 | `process_transition` | 身份、起点／终点、条件或已确认结果含义 |
| 局部分支判断 | `branch_decision` | 含义、输入引用、选择约定；不默认具有可运行脚本 |
| 循环上下文 | `iteration_scope` | 集合逐项或条件重复、判断时点、体／出口、当前项及结果规则 |
| 流程终点 | `process_terminal` | 结束含义，如成功、拒绝或有待处理；不记录已发生状态 |
| 外部能力组合上下文／步骤 | `implementation_context` / `capability_step` | 归属某个业务调用、已确认能力引用和依赖；按需出现 |

role 是 002 已允许的可解释字符串，不新增后端枚举。不是每个模型都必须包含所有位置，
没有参数／循环／接口的流程不创建占位节点。只有确有局部含义或多元关联时才建上下文节点。

可用普通 fact predicate 承载的最小标量：

| 属性示例 | 含义 |
| --- | --- |
| `sourceKind` | `process_input`、`call_output`、`object_property`、`constant`、`iteration_item`；转换或迭代归约需显式关联其定义，不能伪装为直接来源 |
| `selectionMode` | 已确认的互斥选择／按优先次序选择／未知；不默认选择策略 |
| `priority` | 仅用于业务明确规定的优先选择；非显示顺序，也不使循环或集合自动有序 |
| `loopKind` / `conditionTiming` | 逐项／按条件重复；前置／后置判断，仅在适用时填写 |
| `literalValue` | 获准语义常量的标量值；数据类型由已声明 predicate 表达，空值含义单独说明 |

这些标量放在普通 `semantic.values`，每个自定义属性先声明 fact predicate 和数据类型。
参数的方向／单值集合等优先复用 003 最终 `parameter_definition` 约定，避免两份合同。
已知“无输入／无输出”使用明确业务声明；不以某次查询没有关系边推导。

### 4.2 关系与方向

| 普通 relation predicate 示例 | 方向及含义 |
| --- | --- |
| `inProcess` / `inScope` | 调用、绑定、转移等 → 所属流程／局部作用域 |
| `invokesAction` | 业务调用点 → 共享 Action；不表达实际已调用 |
| `hasProcessInput` / `hasProcessOutput` | 流程 → 本流程的输入／输出定义 |
| `refersToDefinition` | 参数／值引用 → 对象或值的共享定义；不表达实际对象相等 |
| `inputOfProcess` + `forParameter` | 流程输入值引用 → 所属流程、该流程输入定义 |
| `outputOfCall` + `forParameter` | 调用结果值引用 → 指定调用、该 Action 的输出参数定义 |
| `atCall` + `toParameter` + `fromValue` | 输入绑定 → 调用点、该 Action 的输入参数定义、来源值引用 |
| `atProcess` + `toParameter` + `fromValue` | 流程输出绑定 → 流程、其输出定义、来源值引用 |
| `baseValue` + `viaProperty` | 属性值引用 → 对象来源引用、具体属性／关系定义；方向在该取值说明中明确 |
| `entryStep` / `fromStep` / `toStep` | 流程 → 入口；转移 → 起点／终点，分别是明确引用 |
| `guardedBy` / `usesValue` | 转移或绑定 → 局部判断／共享规则；判断 → 其输入引用 |
| `iteratesOver` / `currentItemOf` | 循环 → 集合引用；当前项引用 → 所属循环 |
| `bodyEntry` / `exitStep` / `continuesWhen` | 循环 → 体入口／出口／继续判断；转移按上下文说明回到判断或下一项 |
| `initialValue` / `iterationResult` | 循环传递值说明 → 初始来源／本次迭代的更新结果，明确下一轮读取含义 |
| `collectsValue` / `selectedBy` | 循环外结果引用 → 迭代内结果引用／选择或归约规则 |
| `implementsCall` / `usesOperation` | 实现上下文 → 业务调用点；能力步骤 → Operation |

003 对 Action 拥有参数及结果关联的最终词汇由其交付确定；004 的 `toParameter`、
`forParameter` 指向这些资源本身，不复制参数说明或在引用中拼接参数名称。
关系两端支持普通语义节点与已获准定义，不能为满足 domain／range 强制创建业务 Class。

### 4.3 最小数量与完整性含义

- 一个业务调用点引用一个 Action；动作选择不确定时记录未知，而不是放多个 Action 后默认任选。
- 一个完整直接绑定有一个目标位置和一个来源值引用。集合由一个集合引用表达，不通过重复
  单值来源假装隐式聚合。多条条件化绑定可以指向同一目标，但条件／选择含义必须明确。
- 一个完整输出引用同时有调用点和输出参数；一个完整属性引用同时有基础对象引用和属性定义。
- 一条转移有一个起点和一个目标；多个候选后继用多条转移表达，不按数组顺序选择。
- 未确认部分可保留局部未知，但不能以“完整绑定／完整流程”描述；缺引用的声明不产生
  虚构关系。这些是建模与验收规则，不自动变成全平台硬编码的流程 schema。

## 5. 核心场景与引用规则

### 5.1 同类对象、重复调用

```text
流程 P 的输入 original ──值引用──> V-original
调用 C-create ──invokesAction──> A-create-repair
值引用 V-repair ──outputOfCall──> C-create
                 └─forParameter──> A-create-repair 的 repair 输出

调用 C-close-original ──invokesAction──> A-close
绑定 B1 ──atCall──> C-close-original
        ├─toParameter──> A-close 的 target 输入
        └─fromValue──> V-original

调用 C-close-repair ──invokesAction──> A-close
绑定 B2 ──atCall──> C-close-repair
        ├─toParameter──> 同一个 target 输入
        └─fromValue──> V-repair
```

两个 target 参数引用相同，两个调用和值引用不同。V-original／V-repair 均可引用“工单”
定义；它们是否代表不同实际工单由业务条件说明，而不是由 Class 或 IRI 不同推导。
C-create 仅在特定结果下产生返修工单时，C-close-repair 的转移及绑定必须保留这一前提。

### 5.2 属性取值、集合与转换

“使用原工单的编号”以 `baseValue → V-original`、`viaProperty → 工单编号定义` 表达。
同理，使用前序输出的属性需先明确前序输出值引用。关系取值还需明确方向和结果基数。
多段访问按需要逐段连接普通值引用，不解析一段路径字符串。

集合输入与单个当前项明确区分。单个值转集合、单位转换、枚举映射、排序或归约必须有已
确认含义及输入／输出引用；这些计算定义由 005 或已有可复用业务定义承接，004 不计算。
不能仅凭类型兼容断定语义正确，例如“工单金额”与“已支付金额”均是金额但不可随意替代。

### 5.3 分支与值可用性

互斥／优先判断、默认转移及没有匹配时的后果分别明确。默认路径表示没有其他适用选择
时的业务安排，不等于某条条件未知就自动走默认路径。自然语言判断不交给平台求值。

路径 A 产生 V-a、路径 B 产生 V-b，后续步骤需要一个值时，采用两条有明确适用上下文
的绑定，或引用已有可解释的选择规则；不能把 V-a／V-b 无条件同时连到单值参数。
缺少路径信息保留未知，不复制条件正文绕开规则保护。

多条替代路径指向同一后继只描述可能到达。按用户确认的 D8，本期不纳入并行及等待
全部／任一分支的同步语义；已知业务需要并行时披露缺口，不把它改写成顺序或互斥选择。

### 5.4 循环

集合循环：明确集合来源、当前项引用、循环体入口和遍历结束后的出口。循环体内的调用
保持一个定义身份，结果引用说明“该循环当前迭代的此调用输出”。嵌套循环必须分别绑定
外层与内层 current item，作用域沿显式 `inScope`／`currentItemOf` 关系读取。

条件循环：明确前置或后置判断，继续条件、体与出口；需要更新对象／值时说明第一次
输入来自哪里、后续来自哪个迭代结果。这个传递说明是定义，不保存实际可变变量或运行记录。

循环外：结果是按迭代收集的集合、最后一次成功结果、按业务规则选择的值还是归约结果，
必须由资料确定，并关联被消费的迭代内输出及选择规则。只有已确认顺序时“最后”才有意义。
零次迭代、空集合、失败或缺失输出时不能自动造默认值；明确策略或列为未知。
不新增 token 调度、死循环检测、运行次数上限或终止性求解。

### 5.5 外部能力组合

业务调用 C 引用 Action A。若资料确认 A 在此处由能力 O1、O2 组合实现，建立局部实现
上下文 I，`I implementsCall C`，内部 S1、S2 各引用 Operation，转移描述先后或条件。
只有确认的对应关系才可引用；不把每个能力步骤声明为完整 A，不自动选择替代实现。

已确认“能力 S2 需要 S1 的结果”可关联步骤与已有业务结果定义并保留解释。API 内部
请求／响应字段和参数位置留给 011 的接口映射；若尚无可引用身份，披露这一映射缺口，
不在 004 为它新增参数标识协议。Operation 原有活动状态、工具绑定、风险及凭证类别要求
仍有效；本设计不存凭证、不执行外部调用。

### 6.2 中性候选片段

以下是已有字段的结构示意，**不是可单独提交的完整候选**。完整 fixture 必须包含
envelope、所有 predicate、共享 Action／参数、值引用和关系声明，所有 item_id 唯一。

```json
{
  "item_id": "binding-close-repair",
  "item_kind": "entity",
  "semantic": {
    "entity_id": "binding-close-repair",
    "values": {"label": "关闭返修工单的目标绑定"},
    "semantic_definition": {
      "semantic_role": "parameter_binding",
      "business_meaning": "将本流程生成的返修工单用于关闭动作的目标输入",
      "applicability": "返修工单已生成且达到已确认关闭条件的路径"
    }
  }
}
```

分别用三条普通 relation 表达 atCall、toParameter、fromValue，例如：

```json
{
  "item_id": "binding-close-repair-target",
  "item_kind": "relation",
  "semantic": {
    "predicate": "toParameter",
    "subject": {"definition_ref": "binding-close-repair"},
    "object": {"definition_ref": "close-target-parameter"}
  }
}
```

`definition_ref` 是当前完整候选中的 item_id；Modeling 不拼平台 IRI。复用既存资源时
只能采用所选任务已授权的回执／读取绑定合同，不能把当前候选引用包装成任意外部 IRI。
跨流程复用可以在同一完整候选内证明；不为 004 引入新的跨 Project 或增量资源发现协议。

### 6.3 物化与读取

1. Modeling 形成业务结构及已披露未知，沿当前 Team 交接交付；不安排平台阶段或补证。
2. Protocol 将普通谓词／实体／关系翻译为既有命令，并绑定正式身份。关系创建在依赖资源
   可解析后进行，候选完整性与每阶段原子性维持原有区别。
3. 各阶段使用既有 dry-run、apply_atomic、回执及恢复机制；不要求把所有流程定义塞入
   一次新的全局事务，不因业务流程存在环就拒绝平台的资源先建、关系后建顺序。
4. 读取方按获准 scope 获取流程详情，再读普通关系、节点详情和 statement-list。精确
   `/api/semantic/resources/{resource_iri}` 的 `properties` 是已声明投影字段，不承诺
   自动包含所有任意 fact predicate；自定义标量通过现有 statement-list 等通用读取取得。
5. 遍历时复用现有分页／截断和状态合同；不新增专用流程组装接口。数据流和转移关系分别
   读取，不从三元组返回顺序推导步骤顺序。

重复实例化的 `invokesAction`、`inScope` 等普通谓词不能直接当现有中性候选
`consumer_query.required_paths` 的唯一绑定路径。该旧合同要求每个被列入的谓词只有
一个实例；004 不为满足它给每条流程关系造不同的业务谓词。功能验证使用通用资源／事实／
关系读取，后续真实验收也应选择支持多实例关系的既有查询路径；如发现具体检索阻塞，
记录窄合同缺口并交 008／对应检索合同，不在本条改造整个查询规划器。

## 7. 校验、授权与失败处理

### 7.1 校验职责

| 检查 | 承担方／处理 |
| --- | --- |
| 非法字段、错误类型、重复身份、引用未解析 | 既有候选／翻译合同；定位 item_id、字段与可修正原因 |
| 既有显式 Shape、图版本、授权、dry-run 与写入一致性 | 既有平台机制；拒绝该次不合法写入，保留安全重试路径 |
| 参数属于哪个 Action、来源方向、循环内外引用、分支输出条件 | Modeling 方法与独立语义验收；必要的局部结构可用获准 Shape 表达，不全局强制 |
| 业务含义是否忠实、条件是否足够、单位是否等价 | Modeling／独立语义验收；平台不依据文本猜测 |
| 具体运行是否满足条件、是否授权业务执行、如何调度 | 外部 Consumer／业务系统；不是本平台写入结论 |

不新增全图路径可达性／dominance／静态执行证明器，也不把显式未知升级为整个 run 永久
失败。不能写入的引用先修正，仍有业务未知的合法模型可以保存已知部分并如实披露。
结构可以写入不等于语义正确，也不等于所有必填输入已解决。

### 7.2 授权与敏感语义

流程、调用、绑定、值引用、参数和规则都是普通受治理资源。保护集和 Grant 不变，业务
作用域不产生新的权限作用域。受限端点／谓词关系按既有 access view 隐藏，精确读取与
不存在保持相同响应；不得增加 hidden_branch_count、缺失权限来源等侧信号。

一个绑定节点可见而某条关系不可见时，不返回对隐藏来源的解释；Consumer 仅知道当前
获准结果不足以说明来源，不能得知缺失缘由。模型中原本公开的未知与查询截断可以读取，
不能把授权过滤伪装成模型声明的未知，也不能因此自动断言没有条件或参数。

公开节点上的文字或常量可能直接包含受限业务含义。Modeling 应采用引用并按管理面批准
的范围保护相关资源，不能复制规则阈值绕过权限；现有 IRI 过滤不等于文本敏感性分析。
不为 004 新建敏感内容检测器或自动授权传播框架。

### 7.3 修改与恢复

局部绑定修订不改写共享 Action。复用已有资源更新／关系修改及图版本规则；当前定义
发生变化不能自动认定所有调用仍兼容，已知引用缺口应披露。版本固定和整体重审交 007。
不新增自动级联重绑定或流程版本发布机制。

遇到不确定写入使用既有 Batch／Attempt／回执和恢复路径，不覆盖失败记录；这里的
技术记录与已停用的平台 Evidence／lineage 区分，不让 Modeling 额外整理追溯材料。
