## 1. 目的与边界

本文只冻结 R3.0-002、R3.0-003、R3.0-005、R3.0-006 之间的职责、输入输出和依赖，不提前确定
具体 API、数据库 migration、Agent prompt、运行脚本或逐项验收用例。每项需求进入实现前仍需单独
完成详细设计、计划审查和测试计划。

v3.0 的总体链路为：

```text
R3.0-001 场景资料与关系数据
        ↓
R3.0-002 多切片建模流程 ──→ R3.0-003 业务语义与 Schema 映射
        │                              │
        └──────── 项目级语义视图 ─────┘
                                       ↓
                           R3.0-005 授权语义引导 SQL
                                       ↓
                           R3.0-006 真实端到端验收
```

R3.0-004 提供上述链路使用的语义知识授权合同，但其内部存储、接口和测试设计不属于本文；本次已
确认但尚未写回 R3.0-004 文档的决策，留待后续统一修订。

## 2. 共享设计原则

1. 业务行只存在于关系数据库，RDF 不复制客户、设备、工单、备件请求等业务行实例。
2. Ontology 保存业务概念、关系、规则、指标口径和关系 Schema 映射；保护集属于 Project 级平台
   控制面，不写入 Ontology。
3. 逻辑切片、Ontology 和保护集均不要求一一对应。Ontology 拓扑由语义内聚、复用、变更节奏和
   跨域查询决定，不能由表数量或保护边界直接决定。
4. 建模团队继续采用建模协调 Agent、建模 Agent、平台协议 Agent 三角色。只有平台协议 Agent
   持有 Project-scoped `model` key 并调用平台写接口。
5. Consumer Agent 必须先取得服务端授权后的语义上下文，再生成 SQL；不能绕过语义层直接把原始
   Schema 当作完整业务语义。
6. 语义知识授权与业务数据授权保持分离。外部 SQL 执行器不因消费了授权语义而自动获得行、列、
   租户或组织级数据安全能力。

## 3. R3.0-002 完整场景多切片建模流程

### 3.1 目标

让一个建模团队在保留项目级全局视图的前提下，对完整工业售后场景进行分片建模、复核和整合，
而不是把五个切片当成互不相关的独立任务。

### 3.2 最小输入

- R3.0-001 的 `modeling-input/` 白名单内容；
- 当前 Project、已存在 Ontology 和项目级建模上下文；
- 用户在本次建模访谈中公开确认的回答；
- 平台公开的建模协议，不包括 tester-only 业务真值和验收答案。

### 3.3 最小产出

- 一份项目级场景地图，记录切片、共享术语、跨切片依赖和 competency questions；
- 一次明确的 Ontology 拓扑决策及理由；
- 每个切片的业务语义候选、证据、未知项和与其他切片的连接点；
- 经整合后的项目级模型，不因分批执行产生重复或互相矛盾的术语；
- 需要加入保护集的明确语义资源 IRI 建议，交由获准的保护集流程处理。

### 3.4 角色边界

- 建模 Agent：理解资料、提出语义候选、发现歧义，不拼装平台协议参数。
- 建模协调 Agent：维护项目级视图、切片顺序和跨切片取舍，批准可执行候选。
- 平台协议 Agent：把批准候选转换为 Build Session、Lease、Modeling Batch、验证、推理、查询及
  保护集管理调用；不自行改变业务语义。

保护集与本体发布是独立平台操作。流程推荐先保护目标 IRI 再创建敏感资源，但平台不把该顺序作为
硬校验，也不要求二者位于同一 Modeling Batch。

### 3.5 暂不细化

- 切片是否并行、每个切片使用多少 Agent；
- 拓扑决策的评分公式；
- 中间产物的最终 schema 和 UI；
- 自动重试、长期调度和多项目协作。

## 4. R3.0-003 纯语义 Ontology 与关系型 Schema 映射

### 4.1 目标

建立可由 Consumer Agent 查询和解释的业务语义层，使业务概念、关系、指标与 PostgreSQL 表、列、
主外键和 join path 建立明确映射，同时不把业务行复制为 RDF 个体。

### 4.2 最小语义合同

- 概念和属性到表、列及稳定业务标识的映射；
- 关系到外键或显式 join path 的映射，包括方向和必要连接条件；
- 枚举值和状态值的业务含义；
- 指标名称、粒度、时间字段、过滤条件、聚合方式、空值与分母规则；
- 映射所依据的 Schema 版本和证据来源；
- 每个可查询、可保护的概念、关系、指标和映射具有稳定语义资源 IRI。

### 4.3 边界

- Schema 是建模证据，不是业务真理；未确认的业务含义必须保持显式未知。
- 映射不保存数据库凭证、连接串、生产数据样本或业务行实例。
- 保护集定义、成员清单和 grant 不进入 RDF，也不随 Ontology 导出。
- R3.0-003 产出可供保护集引用的资源 IRI，但不实现主体授权。

### 4.4 暂不细化

- 映射词汇的最终 RDF schema；
- 指标 DSL 或 SQL 模板表达形式；
- Schema 演进和映射迁移策略；
- 自动从数据库 Schema 生成业务语义。

## 5. R3.0-005 Ontology 引导的 SQL 问数链路

### 5.1 目标

Consumer Agent 使用本次请求已授权的项目级语义上下文生成可解释 SQL，并由平台外最小执行适配器
在 PostgreSQL 执行。

### 5.2 最小流程

1. 接收自然语言问题和服务端认证主体。
2. 查询授权后的概念、关系、指标口径和 Schema 映射。
3. 判断当前语义是否足以生成 SQL；不足时返回无法确认，不区分未建模、不存在或无权可见。
4. 仅使用授权语义上下文中出现的表、列、join path、过滤条件和指标规则生成 SQL。
5. 将 SQL 交给平台外最小适配器执行。
6. 使用结构化查询结果回答，并说明采用的业务口径和关键映射。

### 5.3 安全与职责边界

- Consumer Agent 不读取保护集定义、成员清单或 grant。
- 不能因为语义结果缺失而绕过平台读取原始 Schema，或猜测隐藏的表、列和 join path。
- 最小适配器只执行 SQL 并返回列、行或数据库错误，不做授权、SQL 重写、审计或策略解释。
- 生产环境的数据访问必须由外部业务服务、查询网关或数据库权限另行约束。

### 5.4 暂不细化

- NL2SQL 模型和 prompt；
- SQL AST、静态检查、沙箱和资源配额；
- 数据源连接器框架；
- 生产级行列权限和多租户策略。

## 6. R3.0-006 真实建模与端到端问数验收

### 6.1 前置条件

只有 R3.0-002～R3.0-005 分别具备实现和独立测试证据后，才能启动本需求的真实 modeling start。
概要设计、清理成功、服务健康或单独 SQL 正确均不能替代这些前置条件。

### 6.2 验收链路

- 建模团队只能读取 R3.0-001 的建模输入，通过访谈补齐关键业务语义；
- 独立验收方读取 tester-only 业务真值，但不得把答案泄露给建模团队；
- 平台协议 Agent 完成跨切片模型应用、验证、推理和项目级查询；
- 一个 Project 级保护集覆盖多个 Ontology 中的资源，授权与未授权主体得到各自稳定合同；
- Consumer Agent 使用授权语义生成 SQL，并在真实 PostgreSQL fixture 上执行；
- SQL 结果与 C01～C08 业务真值及代表性 competency questions 对照；
- RDF 中不存在本场景业务行实例。

### 6.3 结论必须分层

验收报告必须分别给出：

1. 建模与语义检索结论；
2. 语义知识授权结论；
3. SQL 生成与执行结果结论；
4. 业务数据安全边界声明。

任一层通过都不能替代其他层。数据库 fixture 可被开发者直接查询不构成语义授权失败，但也不能据此
声明业务数据安全成立。

### 6.4 暂不细化

- 代表问题的最终集合和逐项期望输出；
- 真实运行次数、attempt budget 和恢复策略；
- Consumer Agent 的具体运行时；
- 生产数据源安全验收。

## 7. 依赖与停止条件

- R3.0-002 与 R3.0-003 可以在 R3.0-004 外部合同冻结后并行细化。
- R3.0-005 依赖 R3.0-003 的可查询映射和 R3.0-004 的授权读取合同。
- R3.0-006 依赖 R3.0-002～R3.0-005 的已验证实现。
- 本概要设计完成后即停止；不得据此启动真实建模、实现 SQL 适配器、修改授权代码或宣称任何后续
  需求已实现。
