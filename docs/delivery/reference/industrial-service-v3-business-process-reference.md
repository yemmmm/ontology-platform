## 1. 场景边界与项目视图

场景覆盖工业设备客户从服务覆盖、故障报告、工单执行到备件履约和服务绩效分析的完整链路。
业务事实的唯一运行时来源是 PostgreSQL 的 `industrial_service_v3` schema；Ontology 只保存后续
建模确认的业务语义、关系、指标、Schema 映射和语义访问策略，不保存这些表的业务行个体。

包含：客户、区域、现场、设备型号和资产；服务合同、合同覆盖和分级 SLA；故障、工单、状态历史、
工程师、分派和延迟；备件、型号兼容、仓库、库存变动、申请和发运；跨切片的响应/解决、SLA、重复
故障、一次修复和延迟归因指标。

不包含：制造、采购计划、财务结算、开票、客户收费、实时 IoT、预测性维护、生产连接器、SQL
沙箱、数据库行/列权限、语义平台的 RBAC 实现。

项目级视图必须同时保留以下切片的共享术语、依赖和跨域问题。切片不是 Ontology 的同义词，单一或
多个 Ontology 的拓扑在真实建模前仍需通过决策门确定。

| 切片 | 真值边界 | 主要依赖 |
| --- | --- | --- |
| S1 客户与资产 | 区域、客户、现场、型号、安装资产 | S2 覆盖资产；S3 故障对象；S4 兼容型号 |
| S2 合同与 SLA | 合同有效期、覆盖区间、SLA policy 与严重度目标 | S1 资产；S3 发生时点和里程碑 |
| S3 故障与工单 | 故障、工单生命周期、状态事件、人员分派、延迟区间 | S2 SLA；S4 申请与发运 |
| S4 备件履约 | 备件主数据、兼容性、仓库、库存、申请、分批发运 | S1 型号；S3 工单 |
| S5 服务绩效 | 从 S1～S4 派生的 SLA、重复故障、一次修复和归因指标 | 全部切片；不新增事实源 |

## 2. 实体与关系真值

- `service_regions` 是区域字典；客户和现场各自归属一个区域，工程师与仓库也归属区域。
- `customers` 拥有 `service_sites`；现场安装 `assets`，资产引用一个 `equipment_models`。
- `service_contracts` 属于客户，引用一个 `sla_policies`；`sla_targets` 按严重度给出响应和解决分钟数。
- `contract_assets` 把合同与资产关联，并定义覆盖开始/结束；同一资产可以有历史覆盖记录。
- `incidents` 报告资产故障；一个故障对应一个 `work_orders`。工单的里程碑在主表，状态变化在
  `work_order_status_events`，人员历史在 `work_order_assignments`。
- `work_order_delay_events` 只记录工单的延迟区间和被确认的原因。备件申请、库存为零或发运较晚不能
  单独证明因果。
- `spare_parts` 是备件主数据，`part_compatibilities` 表示与设备型号的兼容性。仓库通过
  `inventory_movements` 记录入库、预留、发货和调整；工单通过 `part_requests` 申请备件，申请可以
  通过多条 `part_shipments` 分批发运。

## 3. 主流程与派生口径

### 3.1 服务覆盖和 SLA

1. 以 `incidents.occurred_at` 查找资产当时有效的 `contract_assets`：
   `coverage_start_date <= occurred_at::date` 且 `coverage_end_date` 为空或不早于发生日期，同时合同
   本身在有效期内且状态为 `ACTIVE`。
2. 没有有效覆盖时，SLA 结果为 **not applicable**；不能把没有合同当成自动违约，也不能用客户或资产
   的其他合同替代。
3. 有覆盖时，按合同的 `sla_policy_id` 和 incident `severity` 选择唯一 `sla_targets`。
4. 响应时长 = `responded_at - reported_at`；解决时长 = `resolved_at - reported_at`。目标比较统一
   使用分钟，保留整数分钟；相等算达标。`responded_at` 或 `resolved_at` 为空时，只能报告未完成/截至
   查询时长，不能伪造为 0 或达标。
5. 工单状态和里程碑是事实列；`sla_met`、`response_breach`、`resolution_breach` 必须在查询中派生，
   不在表里保存冗余布尔值。

### 3.2 延迟归因

只有同时满足以下条件才可报告“备件短缺导致延迟”：工单存在 `cause_code = 'PART_SHORTAGE'` 的
延迟事件，且延迟区间与解决目标或实际未解决时段有业务重叠。申请、预留、库存数量或晚到的发运只是
支持证据，不能替换已确认原因。

`DISPATCH_CAPACITY`、`CUSTOMER_ACCESS`、`OTHER` 和 `UNKNOWN` 必须保留为自己的类别。`UNKNOWN`
表示当前记录没有足够信息归入已知原因，不得由 Agent 依据列名、备件申请或样例分布强行猜测。
延迟结束为空表示仍在延迟或工单尚未恢复；计算已用时只允许以查询时点为上界并明确口径。

### 3.3 重复故障与一次修复

- **重复故障**：同一资产、同一 `failure_code` 的两个不同 incident，其 `occurred_at` 相差不超过 30
  个日历日；两个事件均须有独立 incident 标识。未确认是同一未关闭事件时不能合并。
- **一次修复（first-time fix）**：首次现场到达后在该工单最终解决，且没有第二次现场分派或重新打开
  的状态事件。仅有 `RESOLVED` 状态不自动等于一次修复；需要结合分派与状态历史。
- 统计分母必须写清楚：例如“已解决且有有效 SLA 覆盖的工单”；未解决、无覆盖、取消的记录不能悄悄
  进入分母。

## 6. 访谈预期与权限边界

建模 Agent 读到 Schema 和样例时应主动询问而不是猜测：

- `status`、`severity` 和 `failure_code` 的业务词汇是否有正式定义，是否允许新增值；
- 合同和覆盖区间按日期还是时间戳生效，暂停合同如何处理；
- 响应、到场、恢复、解决的指标起点、时区和空值规则；
- 延迟事件是否可以重叠，谁确认 `cause_code`，`UNKNOWN` 的升级流程是什么；
- 重复故障窗口、一次修复的重新打开/第二次分派定义；
- 指标分母、取消/未解决工单处理和跨区域归属；
- 成本语义哪些角色可见，以及语义授权与实际数据授权的系统边界。

权限示例固定为：`ServiceOperator` 可看日常运营语义；`ServiceManager` 额外可看 `standard_cost`、
备件成本指标及其 Schema 映射。后续平台验收中，Operator 查询该受保护语义必须得到 `forbidden` 且
不得泄露存在性、列名、join path 或指标定义。该语义层拒绝不代表数据库列对同一用户已受保护；真实
数据权限必须由外部业务服务、查询网关或数据库策略按用户/组织落实。本轮不实现任何适配器、RBAC 或
行列过滤。
