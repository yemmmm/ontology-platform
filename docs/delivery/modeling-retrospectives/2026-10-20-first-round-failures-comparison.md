## 三次参数问题的共同链路与差异

共同链路为：合法语义意图 → 实际请求带不支持字段或错误嵌套 → 准确可恢复拒绝 →
文字声称纠正／文件正确，但实际参数仍不合约 → 重复提交，部分会话又误判为桥接注入。

- 输入修复组 seq146 的首错为 `slice_ids`，seq151 开始出现字段移位／复制；26 个调用
  各有结果。seq273 还含非对象 change，seq274 是原生能力拒绝，不能漏计或伪称带有
  not_written 结构化回执。后续确实恢复；两个诊断概念写入超出源材料，既有提示修复
  已禁止该做法，本次不将它重新包装成推荐的诊断步骤。
- `140728` 前三次被 CQ 就绪门挡住，其中第一次请求结构正确；冻结后错误结构已在
  原生 tool/call 参数里。相同内容的错误请求最多重复10次；字段拒绝包含“外层已有，
  fields 又复制一份”的情况，不只是漏外层键。
- 本次第一请求外层正确，拒绝 `source` 后出现漏外层 `item_id`、字段移入内层。
  同一参数内容最多重复7次。既有诊断重建了 stream chunks，逐项等于实际 tool/call，
  没有平台桥接移动字段的证据。正确意图文件不等于该文件被实际原样提交。

重复计数按规范化 JSON 内容统计，忽略空白及键顺序，不把它称为逐字节相同。
三个样本的首错不同、错误码不同，但都存在原生发参与纠错脱节；不是三个全新根因。
当前校验拒绝未获准字段并允许同目标纠正，保护写入正确性。按 T0 没有依据删除校验、
静默移动／丢弃字段或新增尝试次数硬门。

## 为什么之前修过，仍然复发

`0083d36` 已将六键同级、以实际发参为准、重复拒绝不证明 bridge 注入及禁止业务
探针写进真正加载的 minimal-chain Modeling 包。原输入修复组使用旧提示 `135daf38…`；
后来的 `103635-r1`、`140728-r1/r2` 和本次 r1 使用的材料 SHA 均为 `8d337982…`。
这次不是修到了未被选用的通用包，也不是仅凭当前源码猜历史已加载。

同一提示下，`103635-r1` 及 `140728-r2` 各4次提交、2次可恢复拒绝、2次成功；前者
确实修正了不支持的 `semantic_role`，没有发展成长循环。故成功样本也证明：一次
完成不等于零拒绝，已有同 run 纠错通路可走；新会话成功不能独立证明提示修订生效。

本次 r2 采用 `c54ff35` 后的新材料 `a53ff681…`，4次提交为范围待绑定、CQ待冻结及
两次成功应用。提示和上下文同时变化，没有单因素对照，不能据此保证下次首轮成功。
`d189006` 的状态反馈增量在验收后交付，旧 run 未热载，不能倒算它已防止本次失败。

因此，**说明已到达，但稳定执行没有闭环**。Modeling 的工具合同遵守／自纠错存在
实际反例；Host／Delivery 重复指导没有及时转化为对实际调用差异的核查，扩大了
无效循环。此前 Delivery 输入、状态和短线程修复解决下游放大环节，不能替代源头
参数纠错。这个判断不推断供应商内部机制，也不从少数会话断言 low 档整体不适用。
