# Codex／DSH 本轮耗时与 Delivery 用量退步复核

结论：资源积压引起启动和验收失败，DSH 的阶段换线程又被一个已清理的失败 run
持续阻断，长上下文重复输入放大了整个恢复过程。旧 Delivery 优化没有被回滚，
但没有覆盖这条失败接续路径。本次仅分析和更新验证记录，没有实施新修复或新增模型调用。

关联 R4.3-030／022／032、原 OPT-20261019-DSH-03／07；最小链独立非盲语义结果
保持通过，不能据此关闭效率或自主交付目标。原始故障、旧报告和各 attempt 不改。
数值与元数据见[证据摘要](../evidence/2026-10-20-runtime-compare-cost-regression.json)。

## 同口径对照

时间为真实 semantic start 到 Runner 接受独立验收结果的墙钟，包含 CQ、等待及恢复，
不是有效语义工时。当前两组并行，不能把它们的墙钟相加。DSH 首次未进入 semantic start
的启动失败发生在表中起点之前，也仍属于本次任务，不能由此重置任务总耗时。

前轮 Codex 的运行链确实在 10M 内；其包含当时已归属 Host 的完整记录为 14,399,757。
本次两条运行链各自已超过 10M，无需分摊 Host 即可判该量化目标未达到。当前合计
96,673,176 还包括两组共享 Host 27,437,981；不将这个双组总数与单组 10M 直接相除。
全部数值为各自留存截止点的已知下界，后续复盘成本另计。

本轮通用生产角色／材料基线也发生变化，DSH 有 2 道公开题而 Codex 有 1 道；
因此不是单因素性能实验。`modeling_team/delivery.py` 在 5135bff 与 54fe708 的 Git blob
均为 `e8d3b7170f9a16dea540b2cb1b916d65d96216de`，Delivery Skill 亦无差异。
不能把本次异常解释为 Delivery 降耗代码回滚，也不能将全部增量归因于通用提示。

## 已定位：DSH 阶段换线程被已清理 run 阻断

1. 第一个 DSH run `minimal-chain-20261020-compare-dsh-low-r1` 因 PostgreSQL
   `too many clients already` 在 semantic start 前失败，随后状态为 CLEANED。
   它没有创建 `control/host-requests.jsonl`，不消费建模轮次。
2. Delivery 在同一 session 中启动获准的 `…-r1retry`；旧 run 仍在绑定列表中。
3. 07:28:23.997Z 与 07:44:12.133Z 的两个真实 `yield_delivery` 已分别明确提交
   production／acceptance `thread_boundary`。这不是 Agent 没有申请。
4. `DeliverySession.maybe_switch_phase_thread` 对所有绑定 run 要求请求账本读取成功、
   coverage 完整。两个请求时的原观察均保留旧 CLEANED run 的
   `requests.ok=false / artifact_unavailable`。该条件足以独立阻断换线程；实际
   `phase_thread_history=[]`，没有原生切换尝试。
5. 因而阶段切换没有减少历史：130 次原生响应留在一个 Delivery native session。
   单次输入从 26,858 增到最大 615,793，平均 321,251，累计输入 41,762,617，
   输出仅 47,336。66 个仅调用 yield 的响应累计输入 21,206,802；21 个无工具响应
   另有 7,807,451。它们不全部是可删工作，但足以说明记录等待仍在反复读取长历史。

主动状态查询合计仅 4 次；本轮核心不是大量主动 get 轮询。前一 DSH 对照留存快照中
有两次原生阶段切换；本轮却是零切换。已确认的请求 ID 修复仍在，但旧修复没有覆盖
“合法、已清理、尚未产生请求账本的启动失败 run”这一条件。

T0 复核方向：请求／写入状态不确定时仍须阻止不安全接续；已证实在语义开始前失败、
已清理且无未知写入的旧 run 没有可消费账本，不应永久阻止另一个获准 run 的 Delivery
上下文切换。优先收窄现有条件，并沿既有 handoff 状态返回实际 deferred 原因；
不是取消未知写入保护、伪造空账本或强制开启新建模。本段是建议，尚未实施。

## 已定位的时间放大与机械返工

- 资源积压：首次数据库接近 100 个连接上限；后续主机仅约 606MiB 可用内存、2GiB
  swap 全满。11 个历史只读生产 run 及 24 个留存验收 owner 尚在运行。用户明确停止
  后，可用内存约 15,021MiB，匹配进程零残留，12 个遗留临时 read key 补撤销，模型保留。
  启动超时有直接证据；不能由相邻时间推导每个底层异常都已证明同一原因。
- Codex Delivery 在 07:18:28 原生 turn aborted，07:28:20 才恢复新 Delivery 线程，
  中断约 9分52秒；期间冻结确认未交回生产，后续出现明确零写入的等待 issue。
  读取截止时刻到 select 之间的竞态已用精确失败回归复现，f4d762b 修复并恢复原 run。
- 一次 GitNexus 影响查询返回 300 秒超时，增加了 Host 修复路径等待；随后已采用直接
  调用点和测试，不应继续把不可用工具放在关键恢复路径。
- Codex 首次公开／隐藏验收均因 canonical MCP forwarder 启动超时失败；恢复后两组
  分别通过。后续部分 `platform-forward-failed` 的具体后端原因仍未证实，Consumer
  自行恢复，最终原件重放稳定；没有据粗粒度错误修改模型。
- DSH 隐藏验收共启动 5 次：第1、3次报告为 initialize 超时、零题执行；第2次错传旧
  handoff，第4次复用已有失败报告的 attempt，被 `cq_handoff_immutable` 正确拒绝。
  Host 在原私有请求内补位申请 attempt-0003，第5次才完整执行3题并通过。
  不能把第2、4次也归成初始化超时，亦不应为这两个拒绝放宽报告不可变性。
- 本轮 Codex 生产阶段有8次明确换线程请求而无实际 production 切换，acceptance
  切换1次，另有一次故障恢复的新 Delivery 线程。留存元数据不能恢复每个瞬间的
  busy／pending-input／decision 条件，精确短时阻断仅部分定位；不能套用 DSH 缺账本
  原因。Codex 恢复及验收失败已能直接解释主要新增关键路径。

DSH 生产交接前 Delivery 输入 15,205,307；交接后还有 26,557,310。资源释放后的
27次响应又累计输入15,021,529：解除机器压力并不会自动清掉已积累的线程历史。
这解释了为什么清理资源之后，token 仍继续很快增长。

## 宿主执行问题与最小后续顺序

本轮有两项监督缺口：初次 PG 耗尽后没有及时联查已出现风险的内存占用；后续看到
阶段交接申请／yield，却没有及时核对实际 native switched，错过 DSH 零切换的信号。
另外 Host 仍多次使用短段等待、重复状态和较长原件读取，本轮共享 Host 27.44M 包含
双组监督、修复及历史资源收口，不能全算浪费，但显然不满足当前总降耗目标。
应充分复用已有异步180秒等待，而非通过更频繁模型往返承载等待；不另建监控框架。

建议顺序仅针对本次证据：

1. 先修原 F3 在“已清理的语义开始前失败 run 无账本”条件下的资格判断及可操作反馈，
   做同一绑定形态的确定性回放；保留授权、未决消息和未知写入检查。
2. 再让重验启动使用实际新分配的 handoff／attempt 回执，任何失败报告发布后都不复用
   旧 attempt。沿现有反馈通道减少重复 Host 诊断，不再仅叠加提醒文字。
3. 新授权运行前做当前已证资源风险的有界检查，及时交用户决定历史待命进程收口；
   未经明确 stop 不自行终止旧团队。监督以实际切换／延后原因核对效果。

本次没有授权实施上述建议或增加 semantic start。OPT-20261019-DSH-03继续待调整，
030整体部分实现／部分验证、每组10M量化目标未通过；既有模型质量证据保持。
不为补精确节省比例或有效工时扩建 harness，不把更少等待调用当作可直接删除的质量工作。
