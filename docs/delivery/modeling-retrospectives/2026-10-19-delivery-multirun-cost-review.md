## 为什么数次调优后仍高

### 1. 主要成本是往返次数乘以累计历史，单包大小只影响其中一部分

累计输入等于各次请求输入之和，也等于响应数乘以平均输入。新送入一个约 10 KB 的
v2 包，并不意味着下一次模型只处理这 10 KB；之前的消息、工具调用／回执和纠错历史
仍随线程进入后续请求。一次无效等待既产生本次请求，也会增加后续历史。

最接近的 Codex C／DSH GLM 对比中，共用 delivery.py、Delivery 指令和 skill 的版本
相同，DSH 已采用稳定内容省略。DSH 平均 v2 包 9,072 字节，小于 Codex 的 10,622；
但响应 49→78、平均输入 141,218→274,591，Delivery 占全链输入增量 98.92%。
因此不能用“优化没移植过去”或“包仍太大”解释主要差额。

已定位到累计请求和历史这个成本面；协议／模型行为的独立贡献尚未通过受控样本分开，
不推测供应商内部机制。[原对比和覆盖补查](../records/2026-10-19-dsh-glm-compatibility-comparison.md)。

### 2. 旧问题确实减少，随后不同失败路径抵消了收益

共用防护组在不删除 GLM 采集器的条件下，将 89 个相同计量告警折叠为每角色首次的
3 条，实际没有只含计量告警的决策输入；Delivery 输入观察下降 43.91%。
所以“完全无效”不符合证据。但未缓存输入反增 33.29%，不能把总输入变化等同费用下降。

下一组修好原件 byte_length 后，读取失败由 12／15 降至 1／10，pending 查询 5→1、
request-result 查询 7→3；这些局部采用也成立。其响应却由 68 增至 117，原因包括
嵌套原生错误去重漏识别、实际恢复与 Host 派生等待矛盾、上游字段返工和排队指导。
F3 虽配置／提示已提供，实际零申请。故降低几个查询没有限制整线程的增长。

这些旧原因已在 0083d36 窄修，不应继续把最新问题归到已删除的 GLM 额外采集器。
各次修复解决的对象不同，调优提交次数不等于已证明的降耗次数。
见[共用防护实测](../records/2026-10-19-delivery-common-wake-guard.md)、
[输入修复采用复盘](2026-10-19-dsh-input-fixes-delivery-retrospective.md)和
[后续修复记录](../records/2026-10-19-delivery-tuning-repair.md)。

### 3. 最新 F3 已有局部采用，但交接意图会在长 turn 内丢失

最新 r1 于 07:13:42Z、07:18:28Z 实际切换生产／验收线程：两处请求输入分别由
129,490 降到新线程 28,621，由 122,560 降到新线程 27,648。这证明自然边界切线程
可以在本次减少已完成阶段历史；不是整轮净节省量，也不证明完整 A3。

最新 r2 并非“Agent 没申请”。原生第三线程明确记录：

| r2 申请 | 原生 tool/call | 到实际 turn/end | 中间后续 yield |
| --- | --- | --- | ---: |
| production | seq517，07:35:45.582Z | seq771，07:44:11.317Z | 20 次，最后 seq765 无 thread_boundary |
| acceptance | seq757，07:43:43.200Z | 同一 seq771 | 1 次，seq765 无 thread_boundary |

代码的 `_yield_delivery` 每次直接覆盖 `last_yield`；监督循环只在 runtime 不 busy 时
调用 `maybe_switch_phase_thread`，后者仅从 `last_yield.thread_boundary` 取申请，且
要求其 input_id 等于最新输入。故等到自然结束时，两项申请均已被普通等待记录覆盖。
这是已定位的 platform-contract／交接状态实现缺口，**不是后续写入安全条件已经被
证明满足，也不能把所有未切换都归为必要安全拒绝**。

对应责任面为 [Delivery 等待与阶段切换](../../../modeling_team/delivery.py) 和
[DSH 活动状态](../../../modeling_team/runtimes/dsh_delivery.py)。前两线程合计输入
3,808,325；最后一线程输入 39,663,067，占 Delivery 91.24%，峰值单次 803,704。
r2 仍在 r1 验收线程中开始，第一请求已是 154,472，而不是新线程约 2.8 万。

最小纠正建议是将已显式提出的阶段交接意图与日常等待记录分开保留，在可安全空闲时
按最新约束、回执和写入状态重核；失效时准确反馈，而非被下一次普通 yield 静默抹掉。
按 T0，最新授权及未知写入保护确有必要；直接删除这些保护不合适。保存原申请并使用
当前账本重核即可处理本次缺口，不需要新增恢复平台或固定 token／次数硬门。

### 4. yield 只是工具回执，DSH 长 turn 与持续输入仍会维持推理

早期 DSH GLM 有 47 次 yield、仅 8 次 turn/end；输入修复组 58 次 yield、18 次
turn/end；最新 76 次 yield、10 次 turn/end。不能将工具成功当成模型已经停止等待。
现有循环在 busy 时仍发送变化，DSH bridge 使用 agent.steer，连续输入可使同一 turn
继续。最新 r2 生产交接申请到结束之间又实际消费 41 个输入包，含 39 个 observation
和 2 个 Host 输入；这些不是 41 次独立模型响应。

最新有 76 个响应只调用 yield，携带输入合计 25,069,851，占 Delivery 57.67%。
这定位了等待相关响应的成本规模，**不能将其全部视为无效或可直接删除**；其中可能
承载实际错误、授权、阶段结果与必要存活变化。首要动作是停止同一已送达指令的重复
催办、修复当前交接意图丢失，再核对必要变化是否仍能及时被处理。

r2 的 Host 原始技术指导已指出，Coordinator 重复追加冻结／终态催办，导致 Modeling
虽然自然结束活动，队列又出现新输入，report_task_result 再被拒绝。两轮分别有 5／7
次明确 unconsumed-input 错误；r2 还受过期地图反馈影响。原守卫保护真实输入，不建议
删除；问题在重复生成输入及旧指导覆盖新回执，属于 collaboration/routing 与
prompt-contract 的纠正面。提示已增加不等于这些实际行为已稳定改变。

### 5. 验收基础设施失败被放大成整轮重做

最新 r1 公开 1／1、隐藏已执行 2／3 均通过，剩余一题原报告记录 platform-examiner
TIMEOUT，首层为 runtime/infrastructure；供应商内部超时原因仍未知，不能归为模型
质量缺陷。随后同模型只读重验未成功：原 Runner `_handle_cq_handoff_complete`
在已交接时只返回旧 handoff，旧报告又不可覆盖；冻结 Task 未启用 checkpoint。
Host 因而在原授权内选择第二轮 fresh 重做。

重验入口缺口属于 platform-contract，证据不可覆盖保护本身应保留。当前 Host 提示
“重发新 handoff”与实际幂等旧 handoff 行为也不一致。无须删除旧证据来恢复；建议先
核对并补齐原模型／freeze 上的新只读验收 attempt 通路，再继续扩展降噪。

在第二次 semantic start 前已有 Delivery 输入 6,892,923、79 响应；之后新增
36,578,469、81 响应，含必要建模、纠错、共享历史及收尾，不能把后者全部算成该缺陷
可删除成本。两轮完整 PASS 直到 07:47:37Z 才取得，从首次 semantic start 起约
38.24 分钟。一次验收故障引入重做，又继承长线程，放大了局部优化的不稳定性。

## 下一步顺序与验证方式

建议先完成两处已经有决定性反例的窄纠正：**阶段交接不被普通 yield 覆盖；验收运行
故障能在原模型上独立重验。** 同时沿原 Coordinator 合同减少已送达催办和过期反馈
重放。F4 可在这之后按既有两种动作实现，但它只减少若干机械往返，不能替代上述问题
处理；继续微调几百字提示或局部字节不能作为主策略。

先用本次保留的 r2 seq517→771 和 seq757→771 事件，验证显式交接在输入插入后仍能
承接，最新用户控制／未知写入仍会延后或取消；验收通路核对旧报告保留、新 attempt
身份及同模型绑定，不重建业务模型。复用现有合同测试，不增加全套 harness。

随后如获准运行，复用唯一 source、同一 Task／DSH 模型／effort、原公开 1／隐藏 3
题、原评分和独立验收。分列实际边界提示／申请／切换、自然 turn 结束、响应数与
平均／峰值输入、未缓存、压缩及所有线程／失败／收尾用量；Host 和全链另外计入。
一次成功只证本切口，复杂场景及重复性另判，不删难题或失败来制造好看分母。

最新组只读模型、冻结池、裁决和凭据处置均按原记录保留。报告 SHA／完整分母核对
不等于重新独立验收。有效语义工时分类不足，保持 unknown。最新输入、未缓存和
input+output 均未达到稳定降低的结论；费用和全任务净收益仍未知。

本次新增报告／数值证据，追加原需求和台账状态；不新增未经确认的 OPT、产品需求
或运行授权。仅文档变更，执行链接、JSON、算术／原件身份和 diff 检查，不运行产品
