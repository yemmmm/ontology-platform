## P1：验收失败的归因与测量目标

### 1. 当前链路实际测量了什么

获准资料 → Modeling 表达为模型 → 平台写入及受治理检索 → Platform Examiner 组织答案 → Judge 对照冻结答案点判定。

一次完整业务问答涉及上述多层。端到端答案不完整，可以合理地判本题未通过；但不能仅凭该结果断言 Modeling 没有表达相应知识。`model-recall-insufficient` 当前覆盖过宽，而 `failure_layer=modeling-quality` 又容易被解读为本体质量缺陷。

### 2. 本次可直接核对的例子

| 题目 | 题干关注点及 Consumer 表现 | 正式失败理由 | 复盘结论 |
| --- | --- | --- | --- |
| C-03 | 是否可把复查故障/工单视为原对象身份；回答明确新旧身份不同、共享定义不等于共享实例 | 未写“不可复制业务行到 RDF”；Judge 明确指出相关响应已经包含 no row/runtime object is stored | 该缺失点不能证明模型未存或检索未返回；题干与附带必答点的对应性需复核 |
| F-04 | 空备件集合、关闭资格不足及重试次数；回答正确处理跳过、回退、未规定上限 | 未写“平台不执行流程”；Judge 指出实际响应明确有 Platform does not execute | 平台执行边界与业务分支回答混合，答案遗漏与模型缺失未区分 |
| G-03 | false/null/true 的判断优先级；回答正确返回 unknown | 未写“资格判断本身不关闭工单”；实际响应有判断、无副作用及不执行说明 | 规则副作用属于真实业务合同，仍需模型表达；是否要求在此题复述，应与题干及 Consumer 合同一致 |
| M-04 | v2 是否可沿用 v1 码义、失效 binding 是否可替换；回答保留版本未知并拒绝自动替换/继续调用 | 未覆盖合成消息、在线可用性及平台对任意图关联的保证边界 | 含不同层次的边界点，不能统一归为码义或 binding 模型缺失 |

G-04 的映射责任遗漏和 M-03 的具体成功判据仍有实质业务消费缺口，需要继续检查关系与响应。不能把六道失败全部改称“只是免责声明漏答”，也不能据本复盘自行改判原报告。

### 3. 高层成因

1. 题干与冻结答案点的信息范围不完全对齐。隐藏答案是合理的；业务问题应足以让独立 Consumer 理解需要回答哪些方面。
2. 一道题混合业务含义、模型构建限制和平台运行边界。漏写一句全局限制可能导致业务含义正确的答案整体失败，而真正需要追查的关系/状态混淆被同一标签掩盖。
3. 已有原始响应足以区分部分失败层，但聚合标签没有提供这种诊断。当前 Judge 合同要求缺必答点失败，又将 model-recall-insufficient 固定映射到 modeling-quality，导致修复对象不清楚。
4. CQ 审核时更关注“答案是否有业务依据”，对“题干是否实际要求此点”“遗漏此点是否造成错误决策”检查不足。宿主本次受托审核冻结，需承担相应的审核改进责任。

### 4. 为什么会影响后续方向

- 为修复答案遗漏而继续增加模型节点、关系或重复说明，未必改善消费质量。
- 将全局平台限制反复写入各业务定义、要求每题都复述，可能增加噪声并鼓励模板式作答。
- 用 2/8 直接表示“本体只表达了四分之一所需知识”没有依据。
- 若放宽所有边界检查，又会漏掉规则副作用、结果身份、授权/执行条件等真实业务错误。

### 5. 已确认的调整方向，具体实现待细化

保留端到端验收结果，先利用已有答案及响应增加诊断说明，无需先建设新评分平台。对每个未满足的必答点依次核对：

| 检查 | 可支持的归因 | 证据限制 |
| --- | --- | --- |
| 题干是否明确或合理隐含要求此点，且答案点有获准依据 | 题目/答案点需复核，或继续后续判断 | 不因事后知道答案而扩大题干含义 |
| 当前已返回的获准响应是否包含此点 | 包含却漏答/误解：Consumer 作答或推理问题 | 响应含义正确仍不证明整个模型完整 |
| 响应未包含时，是否已有受治理证据证明模型存在该内容 | 已存在：检查查询、展开、投影或关系可发现性 | 不凭一次 no_match 断言模型缺失 |
| 获准范围内是否有证据证明必要内容错误或遗漏 | 有依据时才定位到模型表达 | 无法定位则保留原因未确定 |

平台层“不复制业务行”“不执行外部 API”等要求，宜通过模型/调用证据或明确专项题验证；涉及“判断动作是否产生关闭副作用”等业务合同，仍需作为模型含义，并在相关问题中明确检验。必需的安全/业务边界不得因本次分析被删除。

Consumer 的通用作答合同可以要求覆盖：直接结论、支撑依据、影响结论的适用条件与未知；不要求无关模板声明。新题池审核再检查题干与必答点的一致性。若将此建议正式纳入后续验收，应修改相应权威合同并用独立验收验证，而非修改本轮冻结报告或将其人工升为 PASS。

### 6. 本项决策与需求归属

建议继续以完整业务问答作为最终验收对象，同时将“模型表达 / 检索获得 / Consumer 正确表达 / 题目自身问题”作为诊断维度。该维度先落在现有逐题理由与复盘记录，不预设新增平台枚举或强制多轮 Agent。

后续验收应能检出：模型错误、模型已有但查询未取到、响应已有但答案遗漏、题干未要求却被附加必答点这几种不同情况。其改进标准是能明确指向责任环节；本轮 2/8 及所有失败原件继续保留。

2026-10-03 用户回复“同意，请增加一项需求用于修改该问题”，上述目标与方向已登记为 R4.0-013。本次仅登记需求，未开展实现或重新验收。

## P2：跨视角责任与业务结果关系

### 1. 问题边界

本次有证据表明若干视角内部定义有效：C-04 正确区分 API 身份、数据库主键及业务工单号；F-03 正确沿复查调用输出绑定目标，并保留输出缺口。当前问题主要在于，消费者从一个业务问题出发，能否取得解决问题所需的跨视角关系与精确含义。不能仅以每个视角都有实体/说明，判断关联消费已经完整。

### 2. 责任链实例与证据

G-04 中 Consumer 正确说明新旧关闭合同并存、迁移部分完成及目标专属确认，却遗漏技术映射重审和集成维护人员职责。

复核最终 core r3、flow r5、governance r4、mappings r5 四份候选，`integration-maintainer` 只有治理候选中的自身定义，含义为“维护数据库/API 映射，不确认业务合同”，未见其他候选项引用该身份。相较之下，治理候选已有 `assessment-supervision → forRole → service-supervisor` 等职责关系。因此问题具有“角色词义已说明，具体责任关联未闭合”的迹象；这是候选范围结论，不能当成全平台关系不存在的证明，也不能仅凭该事实证明 G-04 漏答的唯一原因。

建议按已确认业务资料表达受影响定义/调用/映射、适用范围、维护职责及角色间关系，使查询能从合同变化到达相应映射与责任方。业务维护责任、Modeling Team 的产物维护责任、平台 Grant 与外部执行授权应继续分开。没有业务依据的责任关系保持未知，不自动按同名角色补连。

### 3. 结果链实例与证据

M-03 的 Consumer 知道 202 受理和 204 无正文不能证明关闭成功，但把后续检查泛称为“关闭进度/工单状态”，未准确说明关闭请求 `status=closed` 的判据。

实际 mappings r5 已有 `closure-request-progress`、`query-close-request-v1` 等定义，明确 accepted 仅受理、closed 表示该请求成功；Judge 也指出该次响应返回了对应含义。因此本例不能直接归为缺少模型节点，需按 P1 区分关系/检索组织与 Consumer 理解。其共同目标是让状态含义绑定精确对象、字段、版本及业务结果，避免把 HTTP 状态、关闭请求状态与工单进度当成同一状态。

### 4. 建议方向，待用户确认

- 以有界业务问题串联视角。例如共享关闭合同新增必填确认时，核对相关调用、参数来源、规则、数据库/API 映射及维护职责；只连接资料确认且该问题需要的关系，不要求每个对象关联全部视角。
- Modeling 表达业务关系与未知；Coordinator 使用现有共享定义/引用重审检查已知跨切片依赖；Protocol 核对关系方向和实际写入；独立 Consumer 从正常问题入口验证能否取得所需含义。不增加逐视角 Agent 或预定 Ontology 划分。
- 分别验证“直接读取定义准确”和“从关联业务入口可发现并正确解释”。前者通过不能替代后者。发现遗漏先核对实际响应，再决定补关系、调整查询或改进作答。
- 区分对象/标识、业务 Action、流程调用、规则、映射及责任的表达职责；同一业务定义跨视角复用，局部参数来源、状态版本和责任适用范围保留上下文。
- 改进效果以跨视角问题能够形成完整且有依据的业务解释为准，不以新增关系数量或模板清单齐全作为质量指标。

### 5. 讨论收束：按既有视角职责定位，不单独增加架构职责

退款例子中步骤顺序、分支、角色分工、参数来源及结果去向，本来就应由流程视角表达，并引用角色、Action、规则及映射的相关定义。先前将流程本身未建完整与跨视角衔接不足合并解释，扩大了问题归属；两类必须区分。引用来自其他视角的定义，不自动构成一个新的视角或额外 Agent 的职责。

讨论结论：P2 作为单独方向性议题收束，不据现有证据新增需求、视角或 Agent。具体缺口继续按流程、角色、映射、检索或 Consumer 的既有职责定位；共同引用的一致性沿现有 Coordinator／引用重审处理。业务定义、关联、授权与执行边界保持原义。原 G-04/M-03 结果及候选检查证据保留，讨论收束不等于这些缺口已经修复或验收通过。

## P3：场景地图中的建模进度与实际产物不同步

### 1. 场景地图的用途

场景地图是 Team 的建模工作总览，记录业务切片、已分析的视角、共享定义及维护责任、依赖与未知；它不是业务流程模型，也不代替平台写入回执或独立验收报告。现有 R4.0-007 F1/F2 已要求这些内容可说明并持续维护。

### 2. 当前可以确认的问题

第四轮已交付最终候选，累计应用 465 条命令，并完成生产交接；最终地图中 object、behavior、process、rule、role、data_mapping、interface_mapping 七项 viewpoint.status 仍全部是 pending。现有合同允许 pending、modeled、unknown、not_applicable，但当前地图不能有效说明哪些部分已有模型、哪些确实尚待分析。

例如退款流程及规则已经完成候选表达，API 某版本的字段含义仍未知。如果总览全部写 pending，接续者无法仅据地图判断下一步应继续完善未知映射，还是重做已有流程。风险是重复分析、遗漏真正待办或依赖对话历史才能交接；本轮发现的是状态与产物不一致，尚未据此量化造成了多少重复工作。

### 3. 不能混同的状态

| 维度 | 应说明的问题 | 判断依据 |
| --- | --- | --- |
| 视角分析/建模 | 是否已有相应模型，哪些范围仍未知或不适用 | 当前候选内容与地图现有 status/note |
| 业务确认 | 该定义是否已由有权来源确认 | confirmed/proposed/unknown/conflict 与实际确认记录 |
| 平台应用 | 是否已写入，写入是否确定 | 实际 Batch/Attempt/回执 |
| 独立验收 | 消费者能否正确理解并完成对应问题 | 独立查询、答案及裁决 |

modeled 不等于业务已全部确认、已应用或验收 PASS；也不能因为最终验收未通过，就把已建模内容统一保持 pending。17 项共享定义仍为 proposed 本身不是错误，需逐项与确认记录对应，不能随交接批量改成 confirmed。

### 4. 对先前覆盖判断的收窄

隐藏题全部标为 slice、公开题中有 8 道 panorama，这是题池组织的事实。R4.0-009 明确允许同一道跨视角/跨切片题承担相应覆盖，不设每视角固定题数。因此缺少隐藏 panorama 标签不自动证明独立跨视角验收不足，不能据此新增强制全景题硬门。实际覆盖仍应按题意、查询及需求验收项逐项核对；它与地图进度过期是两个不同问题。

### 5. 供讨论的最小调整

在现有候选交接、相关修订及生产交接时，由 Coordinator 根据 Modeling 的实际成果核对并更新地图受影响条目，使用已有 status/note 说明 modeled、待处理范围或明确未知；审批、写入及验收结论仍从各自现有记录读取。恢复时让接续者能从地图及这些关联产物识别下一项实际工作。

不预设新 Agent、管理页面、重复状态库或完整性评分；不要求所有条目变成完成，也不因普通进度说明过期就终止安全工作。本项尚在讨论，未新增需求或修改本轮保留的场景地图。
