测试必须分开记录四层证据：

| 层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 文档／机械合同 | 链接、编号、字段、可见性说明和现有入口的静态一致性 | 角色真实推理、平台实际读回或业务质量 |
| 开发回归 | 实现的确定性分支、packet／报告往返、异常处理和入口选择 | 独立测试者输入下的功能独立性或真实模型质量 |
| 独立功能验收 | 未参与实现的测试者以隔离输入验证实际合同、边界和失败恢复 | 当前真实业务语义、源材料忠实度或生产级泛化 |
| 真实语义／运行验收 | 获准 run 中的真实公开反馈、独立 CQ 答案、模型状态和完整范围 | 未执行范围、历史报告之外的推断；机械 PASS 不能替代语义证据 |

整体结论取各项适用证据的最低状态；缺少授权、真实依赖、完整报告或稳定状态时保留 `PARTIAL`／`BLOCKED`，不以受控 fixture 代替真实语义 PASS。

## 3. 设计审阅与实施流程

每条设计先由未参与起草的审阅者只读检查，重点确认：

- 当前需求的范围、基线、相邻条目和明确排除项；
- 现有 CQ／projection／packet／report／checkpoint／handoff 合同是否被复用；
- 公开／隐藏隔离、授权、写入完整性、冻结和历史报告不可变边界；
- 是否把可恢复错误误设成硬门，是否把运行失败误称模型质量，是否引入固定题数、角色或重试；
- 独立功能和真实语义证据是否可达，不能用静态或 mock 断言冒充。

若出现 Critical／High，先修设计并重新审阅；无阻断后才进入实现。审阅不修改代码、模型、冻结池或运行记录，不替代开发测试。

实施完成后顺序为：

1. 开发者运行受影响的合同／回归测试并报告实现差异；
2. 独立测试者使用隔离输入复测关键正例、反例、边界和故障路径；
3. 需要真实业务语义时，由独立验收责任者按授权启动或接续，生产角色不修复正在被验收 run；
4. 宿主汇总分母、范围、visibility、状态绑定、首次失败和未验证项，分别交付 design／developer／independent／real 结论。

真实运行只证明实际执行的范围。受控功能 PASS、role／prompt 装载 PASS、进程正常退出或 report 生成不等于业务语义 PASS；没有完整独立判定的题不能从整体分母中删除。
