## 1. 背景与目标

现有建模验证主要围绕 Dify 业务切片，不能证明平台能够处理一个跨多张关系表、包含多条业务流程、
需要拆成多个逻辑切片的完整业务场景。v3.0 改用“工业设备售后服务运营”作为模拟业务：从客户、
服务站点和设备资产，经服务合同与 SLA，进入故障事件、工单执行和备件履约，最后形成服务绩效问数。

v3.0 的最终目标是：业务事实仍由 PostgreSQL 保存；Ontology 只作为业务语义层，保存业务概念、
关系、指标、规则及数据库 Schema 映射，不保存业务行实例或保护集。平台以 Project 级保护集管理
受保护语义资源，保护集独立于 Ontology 拓扑。Consumer Agent 先以服务端绑定主体查询语义接口，
获得被授权的概念和映射，再生成 SQL，并交给平台外的执行组件到 PostgreSQL 查询。

本版本同时验证两类安全责任必须分离：

1. 平台负责**语义知识安全**。无权限主体查询受保护的业务概念、映射或关联路径时，精确读取按资源
   不存在呈现、宽范围读取返回无痕授权子集、SPARQL 按通用 scope 合同处理；不得通过结果、警告、
   候选项、计数、游标或错误细节泄露受保护知识。
2. 平台不因此获得**业务数据安全**能力。SQL 可查询哪些行、列或租户数据，必须由外部业务查询接口、
   查询网关或数据库权限落实；当前简单 SQL 执行适配器不承担该职责。

## 2. 已确认原则

1. **RDF 不存业务行。** 客户、设备、工单、备件请求等样例行只进入 PostgreSQL；不得为这些行创建
   RDF 个体来完成本场景问数。
2. **Schema 是映射证据，不是业务真理。** 表名、列名、主外键和样例值可支持建模，但不能替代业务
   术语、口径、流程、因果关系和权限含义的澄清。
3. **建模输入刻意保持信息有限。** 输入包可包含简短业务名词、数据库 Schema 和代表性样例数据；
   完整流程说明、查询答案与隐藏规则不进入建模输入，建模团队需通过向用户提问补齐重要语义。
4. **完整场景按逻辑切片拆分。** 当前至少区分客户与资产、合同与 SLA、故障与工单、备件履约、
   服务绩效五个切片；一次场景建模流程应能协调多个切片，而非把完整场景压成一个简单切片。
5. **不预判 Ontology 拓扑。** 逻辑切片不等于 Ontology。最终采用一个 Ontology、多个 Ontology，
   或共享核心加领域 Ontology，必须在真实建模前根据边界、复用、权限和查询需要单独决策。
6. **保留项目级全局视图。** 无论最终拓扑如何，都必须能表达跨切片范围、依赖、共享术语、映射和
   跨域查询，避免各切片形成互不连通的局部模型。
7. **先语义、后 SQL。** Consumer Agent 不得绕过语义接口直接把原始数据库 Schema 当成完整业务
   语义；NL2SQL 可以使用，但 SQL 必须由已授权的语义上下文约束和解释。
8. **当前适配器保持最小。** 本版本不在平台内接数据源；后续最小适配器只负责执行 SQL 并返回结果，
   不添加权限、策略、查询重写、审计或连接器框架。
9. **保护集与 Ontology 拓扑解耦。** 保护集归属于 Project，可覆盖同一 Project 下多个 Ontology 的
   明确语义资源 IRI；逻辑切片、Ontology 和保护集之间均不存在一一对应关系。
10. **平台写入职责不扩散。** 建模 Agent 负责语义判断，建模协调 Agent 负责批准和路由，只有平台
    协议 Agent 使用 Project-scoped `model` key 调用平台建模及保护集管理接口。

## 3. 业务范围

### 3.1 场景边界

覆盖：

- 客户、服务区域、客户现场、设备型号与已安装资产；
- 服务合同、合同覆盖资产、分级 SLA 目标；
- 故障事件、严重程度、工单生命周期、状态事件、工程师分派和延迟原因；
- 备件、型号兼容性、仓库、库存变动、备件申请与发运；
- 响应、到场、恢复、解决、SLA 达标率、一次修复及延迟归因等跨切片问数。

不覆盖：

- 设备制造、采购计划、财务结算、发票和客户收费；
- 实时 IoT 流、预测性维护和机器学习；
- 生产级数据源连接器、SQL 沙箱、查询审计或业务数据权限；
- 把模拟数据或详细流程答案复制为 RDF 业务个体。

### 3.2 逻辑建模切片

| 切片 | 主要内容 | 关键跨切片依赖 |
| --- | --- | --- |
| S1 客户与资产 | 区域、客户、现场、型号、设备资产 | S2 的合同覆盖；S3 的故障对象；S4 的备件兼容 |
| S2 合同与 SLA | 合同有效期、覆盖资产、按严重度的响应/解决目标 | S1 资产；S3 故障发生时点与工单里程碑 |
| S3 故障与工单 | 故障、工单、状态、分派、延迟事件 | S2 SLA；S4 备件请求和发运 |
| S4 备件履约 | 备件、兼容性、仓库、库存、申请、发运 | S1 型号；S3 工单 |
| S5 服务绩效 | SLA、周期、一次修复、重复故障、延迟归因等指标 | 汇总 S1～S4，不新增事实源 |

### R3.0-003 纯语义 Ontology 与关系型 Schema 映射

Ontology 中只建模业务语义以及从语义到关系 Schema 的映射。最低映射能力需表达：

- 业务概念/属性对应的表、列和稳定标识；
- 关系对应的外键或显式 join path，包括方向和必要连接条件；
- 枚举/状态值的业务含义；
- 指标的业务定义、粒度、时间字段、过滤条件、聚合方式和空值规则；
- 语义版本与所依据 Schema 版本/来源的关联。

映射不得包含数据库密码、连接串、真实凭证或业务行实例。平台不因保存映射而成为数据源运行时，
也不得从列名或样例分布自动宣称未确认的业务规则。

Schema 映射自身是可被查询和保护的语义资源，必须具有稳定 IRI，才能被项目级保护集显式引用。
保护集定义、成员清单和 grant 不写入 Ontology，也不进入 RDF 导出；它们属于平台控制面。R3.0-003
只负责产出可引用、可验证的业务语义与映射，不在本需求中实现保护集存储或主体授权。

### R3.0-004 主体绑定的语义知识访问控制

所有 Consumer Agent 可调用的语义读取接口都必须使用服务端认证得到的主体和项目上下文做授权，
覆盖项目范围发现、Ontology/资源检索、Structured Semantic Context、精确 IRI、关系/邻域、指标、
Schema 映射、证据和错误路径。调用方自报 label/role 不能成为权限依据。

受保护语义资源以 Project 级保护集（Protection Set）管理：保护集归属于 Project，成员是明确的
语义资源 IRI，可覆盖同一 Project 下多个 Ontology，禁止跨 Project；保护集、成员清单与 grant 存储
在 PostgreSQL 平台控制面，不进入 Ontology/RDF、语义查询、RDF 导出或 SPARQL。资源未加入任何保护
集时在所属 Project 内保持普通可读；移出最后一个保护集后立即恢复普通可读。同一资源可属于多个保护
集，保护集之间按 OR 授权，保护集内多个 grant 同样按 OR；未加入保护集的授权判定不要求主体满足
任何 grant。保护集允许引用尚未存在的资源 IRI（悬空 IRI 保持保护语义）；保护集变更不要求与语义
资源创建通过同一 Modeling Batch 原子发布。

若主体请求其无权访问的受保护语义资源，接口必须按与资源不存在不可区分的合同拒绝呈现：精确请求
返回与真不存在完全一致的 404/空结果（同一错误码与响应体形状），宽范围查询在分页、计数、排序、
截断和 cursor 计算前无痕过滤、仅返回授权子集；两者都不得通过 warning、cursor、total、计数、排序
差异或错误细节泄露受保护资源的存在、名称、字段映射、join path、邻接关系或证据片段。查询结果
只要通过 subject、predicate、object、关系、路径、mapping、evidence、lineage 或派生内容引用了
无权资源，就必须整体隐藏相关结果。SPARQL 不做任意查询重写：本次解析 scope 与无权保护成员存在
交集时整个请求返回通用 scope 错误，不说明保护集、grant 或受保护资源，也不因 scope 外的保护资源
拒绝查询。语义知识读取面不使用 `forbidden`（403 会成为存在性信号）；项目边界校验的
`forbidden_scope` 合同保持不变。授权和拒绝使用同一套稳定、通用的平台合同，不增加工业售后领域
专属分支。

授权令牌（Semantic Grant）绑定到 API key，由 admin-only 接口分配与撤销（Project Admin 管理本
Project 的 key，Org Admin 管理全部，model 主体不能管理 grant）；grant 更新无需重启即生效。保护集
管理与成员维护复用现有 model scope；普通 Consumer 即使持有 grant 也不能读取保护集定义、成员清单
或授权规则。同 Project 的 Project Admin 绕过本 Project 的保护集，Org Admin 绕过所有 Project；
跨 Project 访问仍按现行边界合同拒绝。授权依赖故障与空 grant 保护集均按 fail-closed 处理，不得
放行或伪装成正常空结果。

验收至少包含一个语义模块示例：备件成本/成本指标语义只对持有相应 grant 的主体可见；无 grant
主体在所有语义读取面得到与该语义不存在不可区分的响应——精确 IRI/精确 label 与真不存在资源逐字节
等价，宽范围检索返回无痕授权子集，SPARQL 整体返回通用 scope 错误，导出、证据与 lineage 不含该
模块内容。该验证只证明语义知识保护，不证明相同用户无法通过其他数据库客户端查询成本列。

### R3.0-005 Ontology 引导的 SQL 问数链路

Consumer Agent 的后续链路为：

1. 接收自然语言问题和服务端绑定的主体；
2. 查询被授权的项目级语义上下文；
3. 使用概念、关系、指标口径及 Schema 映射生成可解释 SQL；
4. 把 SQL 交给平台外最小执行适配器；
5. 适配器在 PostgreSQL 执行并返回结构化结果；
6. Agent 基于查询结果回答，并能说明所用业务口径。

Consumer Agent 只消费授权后的语义结果，不读取保护集定义、成员清单或 grant，也不能根据缺失结果
推断隐藏资源。若授权后的概念、join path、指标口径或映射不足以安全生成 SQL，Agent 必须返回无法
确认，不能区分未建模、不存在或无权可见，也不能退回原始 Schema 猜测查询。生成 SQL 时只使用本次
授权语义上下文中出现的资源与映射。

本阶段允许 NL2SQL。当前适配器的唯一职责是接收 SQL、执行 SQL、返回列与行或数据库错误；不在
适配器中提前实现数据授权、SQL 重写、策略引擎、语义校验或平台 Connector。进入真实生产场景前，
必须把该适配器替换或包裹为由外部系统按用户 ID、租户、组织、行/列策略实施的数据安全边界。

交付状态（2026-08-27）：已实现并通过独立测试 Round 2 PASS。交付物为平台外最小适配器
（`scripts/r3-0-005/sql_exec_adapter.py`，连接级只读 + 结果 JSON 类型合同）、机械授权链
pytest 与 5 轮真实 LLM 冒烟（正向/无 grant/语义缺口全覆盖，Q2 口径对齐业务参考冻结口径：
解决时长 = `resolved_at − reported_at`）。实现含一项已登记窄修复：authorized scope
discovery 本体条目补投影 `graph_set_id`（外部 Consumer 闭环读取所需）。验收结论不构成
业务数据安全成立。

### R3.0-006 真实建模与端到端问数验收

R3.0-002～R3.0-005 实现并分别通过测试后，才可在用户授权的真实 modeling start 中执行：

- 建模团队只读取 R3.0-001 建模输入包，通过访谈获取关键缺失语义；
- 独立验收方可读取业务流程参考文档，核对模型而不向建模团队泄露答案；
- 证明跨多个逻辑切片的模型可被平台协议 Agent 应用、验证和项目级检索，建模 Agent 与建模协调
  Agent 不直接持有平台写接口；
- 证明保护集不依赖 Ontology 拓扑：同一 Project 的一个保护集可以覆盖多个 Ontology 中的资源，
  普通 Consumer 不能读取保护集控制面；
- 证明授权主体可取得足以生成正确 SQL 的语义，未授权主体遵循 R3.0-004 已冻结的不存在/无痕过滤/
  SPARQL scope 合同，且不能从关系、映射、证据或错误侧信道恢复受保护知识；
- 在 PostgreSQL 实际执行代表问题，并将 SQL 结果与业务参考答案比较；
- 证明 RDF 中没有本场景业务行实例，PostgreSQL 仍是业务事实唯一存储。

端到端验收必须把三种结论分开报告：语义模型与检索是否正确、语义知识保护是否正确、外部 SQL
结果是否正确。任何一项通过都不能替代另外两项；直接连接数据库能读取样例列不构成语义授权失败，
但也不能被解释为业务数据安全已经成立。

### R3.0-007 读取模型图限定与 LIMIT 截断修复

状态：已完成（2026-08-26）。实现为 `entity-detail` 模板体新增
`VALUES ?graph { {graph_iris} }` 图限定（唯一缺限定的可执行模板，其余 22 个模板审计合规）；
共享测试计划独立测试 Round 1 全部 PASS（修复前假 404 证据与修复后 200 证据见
`docs/delivery/evidence/2026-08-26-r3-0-007/`）。本节保留原始需求文本。

本需求修复 R3.0-004 独立测试 Round 1（2026-08-26）发现的前置平台缺陷（轮次记录 O-1），基线
`d7f21ca` 即存在，非 R3.0-004 回归。

**问题**：`entity-detail` 等读模型 SPARQL 模板缺图限定（模板体无 `VALUES ?graph { {graph_iris} }`
占位符，见 `backend/app/services/semantic_sparql_templates.py`），查询在共享 Oxigraph 存储上
扫全部命名图（即全部 Project 的数据）后按 `LIMIT` 截断，再由应用层按请求 IRI 后过滤。后果：

1. 存储中有 label 的实体总数超过模板 `default_limit`（如 500）时，目标实体可能落在 LIMIT 窗口
   外，`GET /api/semantic/resources/{iri}` 等面对**任何主体（含 org-admin）**返回假 404；
2. LIMIT 名额被其他 Project 的实体占用（跨项目实体混杂存在于中间结果窗口）；
3. 查询代价随平台总数据量增长，而非随请求 scope 增长。

`rdf_store.query_read_model` 把图列表仅作为查询注释传递（服务测试桩识别用），不构成存储层限定；
真实限定必须存在于查询文本。本项目数据隔离由应用层后过滤保证，因此本缺陷是读取正确性与性能
缺陷，不是跨项目泄露。

**要求**：

1. 全部读模型模板的查询必须经 `{graph_iris}` 替换限定在请求 scope 的图内（对齐 `statement-list`
   现状）；逐个审计 `semantic_sparql_templates.py` 中无图限定的模板并修复。
2. 修复不得改变现有读取面响应合同（字段、错误码、排序），不得影响 R3.0-004 的授权过滤行为
   （过滤仍在分页/计数/排序前）。
3. 验收至少包含：构造跨 Project 合计超过 LIMIT 的实体数据，目标实体位于窗口尾部的回归用例
   ——修复前假 404、修复后正确返回；授权子集断言不回归（R3.0-004 测试计划既有用例全绿）。

边界：图集成员图从未写入时的 export/shape 500（轮次记录 O-2，缺图 404 被映射为
`RdfStoreUnavailable`）是另一独立缺陷，不在本需求范围，另行登记。
