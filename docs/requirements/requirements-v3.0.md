## 1. 背景与目标

现有建模验证主要围绕 Dify 业务切片，不能证明平台能够处理一个跨多张关系表、包含多条业务流程、
需要拆成多个逻辑切片的完整业务场景。v3.0 改用“工业设备售后服务运营”作为模拟业务：从客户、
服务站点和设备资产，经服务合同与 SLA，进入故障事件、工单执行和备件履约，最后形成服务绩效问数。

v3.0 的最终目标是：业务事实仍由 PostgreSQL 保存；Ontology 只作为业务语义层，保存业务概念、
关系、指标、规则及数据库 Schema 映射，不保存业务行实例或保护集。平台以 Project 级保护集管理
受保护语义资源，保护集独立于 Ontology 拓扑。Consumer Agent 先以服务端绑定主体查询语义接口，
获得被授权的概念和映射，再生成 SQL，并交给平台外的执行组件到 PostgreSQL 查询。

本版本同时验证两类安全责任必须分离：

1. 平台负责**语义知识安全**。无权限主体查询受保护的业务概念、映射或关联路径时，精确读取按资源
   不存在呈现、宽范围读取返回无痕授权子集、SPARQL 按通用 scope 合同处理；不得通过结果、警告、
   候选项、计数、游标或错误细节泄露受保护知识。
2. 平台不因此获得**业务数据安全**能力。SQL 可查询哪些行、列或租户数据，必须由外部业务查询接口、
   查询网关或数据库权限落实；当前简单 SQL 执行适配器不承担该职责。

## 2. 已确认原则

1. **RDF 不存业务行。** 客户、设备、工单、备件请求等样例行只进入 PostgreSQL；不得为这些行创建
   RDF 个体来完成本场景问数。
2. **Schema 是映射证据，不是业务真理。** 表名、列名、主外键和样例值可支持建模，但不能替代业务
   术语、口径、流程、因果关系和权限含义的澄清。
3. **建模输入刻意保持信息有限。** 输入包可包含简短业务名词、数据库 Schema 和代表性样例数据；
   完整 tester-only 流程说明、隐藏验收答案与隐藏规则不进入建模输入，建模团队需通过向用户提问
   补齐重要语义。R3.0-011 经用户审核的公开能力问题及答案属于显式建模输入，不得据此泄露同批
   抽出的隐藏验收题或 tester-only 真值。
4. **完整场景按逻辑切片拆分。** 当前至少区分客户与资产、合同与 SLA、故障与工单、备件履约、
   服务绩效五个切片；一次场景建模流程应能协调多个切片，而非把完整场景压成一个简单切片。
5. **不预判 Ontology 拓扑。** 逻辑切片不等于 Ontology。最终采用一个 Ontology、多个 Ontology，
   或共享核心加领域 Ontology，必须在真实建模前根据边界、复用、权限和查询需要单独决策。
6. **保留项目级全局视图。** 无论最终拓扑如何，都必须能表达跨切片范围、依赖、共享术语、映射和
   跨域查询，避免各切片形成互不连通的局部模型。
7. **先语义、后 SQL。** Consumer Agent 不得绕过语义接口直接把原始数据库 Schema 当成完整业务
   语义；NL2SQL 可以使用，但 SQL 必须由已授权的语义上下文约束和解释。
8. **当前适配器保持最小。** 本版本不在平台内接数据源；后续最小适配器只负责执行 SQL 并返回结果，
   不添加权限、策略、查询重写、审计或连接器框架。
9. **保护集与 Ontology 拓扑解耦。** 保护集归属于 Project，可覆盖同一 Project 下多个 Ontology 的
   明确语义资源 IRI；逻辑切片、Ontology 和保护集之间均不存在一一对应关系。
10. **平台写入职责不扩散。** 建模 Agent 负责语义判断，建模协调 Agent 负责批准和路由，只有平台
    协议 Agent 使用 Project-scoped `model` key 调用平台建模及保护集管理接口。
11. **节点一等化、抽象按需。** 业务语义节点、共性节点、规则和正式 Class 角色在同一授权语义图
    中均可拥有稳定 IRI、属性和关系；平台不得要求每个节点必须先归属 Class。共同数据结构只产生
    抽象候选，不能自动证明稳定业务类别、成员关系、继承关系或类型级业务关系。
12. **能力问题先行、验收题隔离。** 先以用户审核的全景及切片能力问题确定模型需要回答什么，再
    进入基础图与正式建模；建模 Agent 可读取公开问题及答案，但不得读取建模前已抽出的隐藏验收题
    或答案。独立验收要求验收角色独立于建模过程，不要求同批验收题之间使用不同 Agent 会话。

## 3. 业务范围

### 3.1 场景边界

覆盖：

- 客户、服务区域、客户现场、设备型号与已安装资产；
- 服务合同、合同覆盖资产、分级 SLA 目标；
- 故障事件、严重程度、工单生命周期、状态事件、工程师分派和延迟原因；
- 备件、型号兼容性、仓库、库存变动、备件申请与发运；
- 响应、到场、恢复、解决、SLA 达标率、一次修复及延迟归因等跨切片问数。

不覆盖：

- 设备制造、采购计划、财务结算、发票和客户收费；
- 实时 IoT 流、预测性维护和机器学习；
- 生产级数据源连接器、SQL 沙箱、查询审计或业务数据权限；
- 把模拟数据或详细流程答案复制为 RDF 业务个体。

### 3.2 逻辑建模切片

| 切片 | 主要内容 | 关键跨切片依赖 |
| --- | --- | --- |
| S1 客户与资产 | 区域、客户、现场、型号、设备资产 | S2 的合同覆盖；S3 的故障对象；S4 的备件兼容 |
| S2 合同与 SLA | 合同有效期、覆盖资产、按严重度的响应/解决目标 | S1 资产；S3 故障发生时点与工单里程碑 |
| S3 故障与工单 | 故障、工单、状态、分派、延迟事件 | S2 SLA；S4 备件请求和发运 |
| S4 备件履约 | 备件、兼容性、仓库、库存、申请、发运 | S1 型号；S3 工单 |
| S5 服务绩效 | SLA、周期、一次修复、重复故障、延迟归因等指标 | 汇总 S1～S4，不新增事实源 |

### R3.0-003 纯语义 Ontology 与关系型 Schema 映射

Ontology 中只建模业务语义以及从语义到关系 Schema 的映射。最低映射能力需表达：

- 业务概念/属性对应的表、列和稳定标识；
- 关系对应的外键或显式 join path，包括方向和必要连接条件；
- 枚举/状态值的业务含义；
- 指标的业务定义、粒度、时间字段、过滤条件、聚合方式和空值规则；
- 语义版本与所依据 Schema 版本/来源的关联。

映射不得包含数据库密码、连接串、真实凭证或业务行实例。平台不因保存映射而成为数据源运行时，
也不得从列名或样例分布自动宣称未确认的业务规则。

Schema 映射自身是可被查询和保护的语义资源，必须具有稳定 IRI，才能被项目级保护集显式引用。
保护集定义、成员清单和 grant 不写入 Ontology，也不进入 RDF 导出；它们属于平台控制面。R3.0-003
只负责产出可引用、可验证的业务语义与映射，不在本需求中实现保护集存储或主体授权。

### R3.0-004 主体绑定的语义知识访问控制

所有 Consumer Agent 可调用的语义读取接口都必须使用服务端认证得到的主体和项目上下文做授权，
覆盖项目范围发现、Ontology/资源检索、Structured Semantic Context、精确 IRI、关系/邻域、指标、
Schema 映射、证据和错误路径。调用方自报 label/role 不能成为权限依据。

受保护语义资源以 Project 级保护集（Protection Set）管理：保护集归属于 Project，成员是明确的
语义资源 IRI，可覆盖同一 Project 下多个 Ontology，禁止跨 Project；保护集、成员清单与 grant 存储
在 PostgreSQL 平台控制面，不进入 Ontology/RDF、语义查询、RDF 导出或 SPARQL。资源未加入任何保护
集时在所属 Project 内保持普通可读；移出最后一个保护集后立即恢复普通可读。同一资源可属于多个保护
集，保护集之间按 OR 授权，保护集内多个 grant 同样按 OR；未加入保护集的授权判定不要求主体满足
任何 grant。保护集允许引用尚未存在的资源 IRI（悬空 IRI 保持保护语义）；保护集变更不要求与语义
资源创建通过同一 Modeling Batch 原子发布。

若主体请求其无权访问的受保护语义资源，接口必须按与资源不存在不可区分的合同拒绝呈现：精确请求
返回与真不存在完全一致的 404/空结果（同一错误码与响应体形状），宽范围查询在分页、计数、排序、
截断和 cursor 计算前无痕过滤、仅返回授权子集；两者都不得通过 warning、cursor、total、计数、排序
差异或错误细节泄露受保护资源的存在、名称、字段映射、join path、邻接关系或证据片段。查询结果
只要通过 subject、predicate、object、关系、路径、mapping、evidence、lineage 或派生内容引用了
无权资源，就必须整体隐藏相关结果。SPARQL 不做任意查询重写：本次解析 scope 与无权保护成员存在
交集时整个请求返回通用 scope 错误，不说明保护集、grant 或受保护资源，也不因 scope 外的保护资源
拒绝查询。语义知识读取面不使用 `forbidden`（403 会成为存在性信号）；项目边界校验的
`forbidden_scope` 合同保持不变。授权和拒绝使用同一套稳定、通用的平台合同，不增加工业售后领域
专属分支。

授权令牌（Semantic Grant）绑定到 API key，由 admin-only 接口分配与撤销（Project Admin 管理本
Project 的 key，Org Admin 管理全部，model 主体不能管理 grant）；grant 更新无需重启即生效。保护集
管理与成员维护复用现有 model scope；普通 Consumer 即使持有 grant 也不能读取保护集定义、成员清单
或授权规则。同 Project 的 Project Admin 绕过本 Project 的保护集，Org Admin 绕过所有 Project；
跨 Project 访问仍按现行边界合同拒绝。授权依赖故障与空 grant 保护集均按 fail-closed 处理，不得
放行或伪装成正常空结果。

验收至少包含一个语义模块示例：备件成本/成本指标语义只对持有相应 grant 的主体可见；无 grant
主体在所有语义读取面得到与该语义不存在不可区分的响应——精确 IRI/精确 label 与真不存在资源逐字节
等价，宽范围检索返回无痕授权子集，SPARQL 整体返回通用 scope 错误，导出、证据与 lineage 不含该
模块内容。该验证只证明语义知识保护，不证明相同用户无法通过其他数据库客户端查询成本列。

### R3.0-005 Ontology 引导的 SQL 问数链路

Consumer Agent 的后续链路为：

1. 接收自然语言问题和服务端绑定的主体；
2. 查询被授权的项目级语义上下文；
3. 使用概念、关系、指标口径及 Schema 映射生成可解释 SQL；
4. 把 SQL 交给平台外最小执行适配器；
5. 适配器在 PostgreSQL 执行并返回结构化结果；
6. Agent 基于查询结果回答，并能说明所用业务口径。

Consumer Agent 只消费授权后的语义结果，不读取保护集定义、成员清单或 grant，也不能根据缺失结果
推断隐藏资源。若授权后的概念、join path、指标口径或映射不足以安全生成 SQL，Agent 必须返回无法
确认，不能区分未建模、不存在或无权可见，也不能退回原始 Schema 猜测查询。生成 SQL 时只使用本次
授权语义上下文中出现的资源与映射。

本阶段允许 NL2SQL。当前适配器的唯一职责是接收 SQL、执行 SQL、返回列与行或数据库错误；不在
适配器中提前实现数据授权、SQL 重写、策略引擎、语义校验或平台 Connector。进入真实生产场景前，
必须把该适配器替换或包裹为由外部系统按用户 ID、租户、组织、行/列策略实施的数据安全边界。

交付状态（2026-08-27）：已实现并通过独立测试 Round 2 PASS。交付物为平台外最小适配器
（`scripts/r3-0-005/sql_exec_adapter.py`，连接级只读 + 结果 JSON 类型合同）、机械授权链
pytest 与 5 轮真实 LLM 冒烟（正向/无 grant/语义缺口全覆盖，Q2 口径对齐业务参考冻结口径：
解决时长 = `resolved_at − reported_at`）。实现含一项已登记窄修复：authorized scope
discovery 本体条目补投影 `graph_set_id`（外部 Consumer 闭环读取所需）。验收结论不构成
业务数据安全成立。

#### 目标与待解决问题

真实 Ontology 建模中，在数据库编码尚未确认时直接创建值节点，会造成因猜测编码而反复删除和
重建资源、物理编码污染业务语义，以及"检索能找到概念却无法生成正确 SQL"的断链。本需求为
受控值定义分级表达合同与映射链，在不复制业务行的前提下改善：

1. **建模速度**：平台侧提供阻止提前物化的确定性校验（分析结论 artifact 的时点管理归
   R3.0-008B）；
2. **建模质量**：受控值表达按业务语义复杂度独立决策，不把编码形式误当成业务边界；
3. **召回与 SQL 可用性**：L3 值既能参与分类、关系和规则检索，也能沿 `EnumValueMeaning`、
   `mappedProperty` 和 `TableMapping` 回到数据库列与原始编码。

#### L1/L2/L3 值表达合同

L1/L2/L3 是按当前业务语义复杂度选择的表达方式，不是成熟度等级，也不要求每个值按顺序升级：

| 层级 | 适用条件 | 正式表达 | SQL 映射行为 |
| --- | --- | --- | --- |
| L1 普通字面量 | 只需保存、比较或过滤，没有独立稳定业务含义 | 属性的字符串、数字或布尔值；不创建独立语义节点 | 通过属性和 `TableMapping` 定位列，直接使用确认后的字面量 |
| L2 枚举含义映射 | 需要解释数据库代码并支持 SQL，但无需分类、复杂关系、规则或跨切片复用 | 现有 `EnumValueMeaning`：`mappedProperty` + `enumValue` + `businessMeaning` | 从业务含义取得原始编码，再由属性映射定位列 |
| L3 一等语义节点 | 值具有稳定身份，并参与分类、关系、规则、多语言或跨切片复用 | 普通一等语义节点与现有 `EnumValueMeaning` 映射节点同时存在 | `EnumValueMeaning` 指向 L3 节点，提供原始编码；L3 节点提供权威业务语义 |

本需求不新增 `ReferenceValueMapping` 或其他映射资源类型。对于 L3，扩展现有
`EnumValueMeaning`，增加可选的 `semanticValue` IRI 引用：

```text
biz:PartShortage
    rdf:type biz:DelayReason
    rdfs:label "缺料"
    biz:belongsTo biz:SupplyChainIssue

mapping:DelayReason_PS
    rdf:type op:EnumValueMeaning
    op:mappedProperty biz:delayReason
    op:enumValue "PS"
    op:businessMeaning "缺料"
    op:semanticValue biz:PartShortage
```

其约束为：

1. L2 的权威含义由 `businessMeaning` 字面量承载，`semanticValue` 不存在；
2. L3 的 `semanticValue` 必须指向同一获准 Project/Ontology 拓扑范围内可读取的一等语义节点；
   `businessMeaning` 可以作为展示文字保留，但分类、关系、规则和跨语言标签以被指向节点为准；
3. L3 普通节点和 `EnumValueMeaning` 是两个资源，不使用同一 RDF 主体的多 `rdf:type` 把业务实体
   与数据库映射记录混为一体；
4. 同一 L3 节点允许被多个 `EnumValueMeaning` 指向，从而表达不同确认编码映射到同一个业务值；
5. 沿用 R3.0-003 当前 `(mappedProperty, enumValue)` 唯一性及 `schemaSource` 边界；超出当前单一
   Schema 来源合同的多源冲突留待发现真实需求后另行细化，不在本需求中预建通用来源模型；
6. `semanticValue`、目标 L3 节点、`mappedProperty` 或 `TableMapping` 任一缺失、无权读取或存在歧义
   时，Consumer Agent 必须返回无法确认，不得退回原始 Schema 猜测编码或物理列。

##### 2026-09-03 细化决策（用户确认）

1. **校验口径**：dry-run/apply 完整性校验对 `semanticValue` 只做结构校验——目标在合并视图中
   存在、位于同一获准 Project/Ontology 拓扑范围内、且不是映射资源类型（`EnumValueMeaning`、
   `TableMapping`、`JoinMapping` 等）。「可读取」不在建模校验中执行，由读取侧既有保护集过滤
   承担：`semanticValue` 指向的 L3 节点未授权时链路断开，Consumer 稳定返回无法确认。
2. **反向链形态**：不新增查询接口。`semanticValue` 投影进既有召回结果（context:query 映射
   候选 data、enum-meaning read-model 行）；L3 节点本身经既有 `rdfs:label` 词法召回为 resource
   候选，Consumer 在同一响应内沿「L3 候选 ↔ 映射候选的 `semantic_value` ↔ `enumValue` ↔
   `mappedProperty`/`TableMapping`」拼接闭环。
3. **接口映射边界**：映射源不限定数据库 Schema；接口信息为同等地位的映射源。该能力的具体
   映射资源、链路与验收另立 R3.0-010，本需求不实现；本需求的机械校验与链路以数据库 Schema
   映射为验收载体。

低影响细节按保守口径执行：每个 `EnumValueMeaning` 至多一个 `semanticValue`；
`update_enum_meaning` 支持增加与清除 `semanticValue`（L2↔L3 升降级）；删除被 `semanticValue`
指向的 L3 节点必须被完整性校验拒绝（悬挂保护）；L1 验收形态为既有属性字面量直接经
`TableMapping` 使用。

#### 最小验收条件

1. 至少各验证一个 L1、L2、L3 示例（fixture 形态）；L3 示例必须证明普通业务节点和
   `EnumValueMeaning` 同时存在且职责分离。
2. 至少验证两个不同 `EnumValueMeaning` 指向同一 L3 业务节点，语义检索不产生两个"同义业务
   节点"，数据库过滤仍分别取得确认的原始编码。
3. 代表问题"查询因为缺料而延期的订单"能够从"缺料"召回 L3 节点及其业务关系，再经
   `semanticValue` 的反向映射取得 `enumValue`，经 `mappedProperty` 和 `TableMapping` 定位物理列，
   生成可解释 SQL；断开链上任一环节时稳定返回无法确认。本条在 008A 以 fixture 独立验收，
   并必须在 R3.0-008B 的真实场景联合验收中复验。
4. dry-run/apply 完整性校验能够拒绝违反上述约束的映射（`semanticValue` 目标缺失或不可读、
   跨 Project/Ontology 拓扑范围、同一 RDF 主体混用业务实体与映射记录等）；对数据库编码未
   确认的候选值，RDF 中不存在对应的猜测 `EnumValueMeaning` 或正式 L3 值节点（分析结论的
   时点门归 R3.0-008B，008A 只承担机械校验与拒绝）。
5. 验收必须继续证明 RDF 未复制客户、设备、工单等业务行。

#### 非目标

- 不新增映射资源类型（含 `ReferenceValueMapping`），不建立通用数据源连接器或多源编码注册中心；
- 不把全部数据库枚举都提升为 L3，也不要求已有 L1/L2 无业务依据地升级；
- 不把业务行、客户清单、工单或设备实例复制进 RDF；
- 不在本需求中建设编排框架、版本治理、管理 UI 或 Agent 工作流时点管理（归 R3.0-008B）。

### R3.0-008B 建模决策分阶段流程与值语义联合验收

状态：第一段机械增量已完成（2026-09-03，独立测试 Round 2；L2 真实 Runner smoke 经用户
裁决跳过）；第二段真实联合验收待 009/011 所需增量和 R3.0-006 新授权。真实运行验收挂在
R3.0-006 的 modeling start 授权体系下，
必须复用 R3.0-008A 已交付的 L1/L2/L3 表达合同与 `semanticValue` 映射链；R3.0-008A 的独立测试
证据不得替代本需求的联合验收闭环，本需求通过也不得追溯解释为 R3.0-008A 的 fixture 验收。

#### 目标与待解决问题

真实 Ontology 建模中，若过早按数据库表拆切片、过早选择单/多 Ontology，或由单个切片自行改变
拓扑，容易造成重复访谈、返工和跨切片术语冲突。本需求把这些判断变为有明确时点、输入、产出和
责任人的建模流程：

1. **建模速度**：未确认事项先保留为分析结论，避免因猜测数据库编码而反复删除和重建资源；
2. **建模质量**：逻辑切片、Ontology 拓扑和受控值表达分别决策，不把表数量、团队数量或编码形式
   误当成业务边界。

#### 分阶段流程与决策时点

建模团队必须按以下顺序推进；后一阶段可以把前一阶段的显式未知项补全，但不得静默改写已批准的
业务语义或拓扑决策：

1. **场景理解与访谈**：确认业务目标、范围、核心流程、已知资料和显式未知项；数据库 Schema
   只能作为证据，不能替代业务确认。
2. **全景能力问题生成与审核**：按 R3.0-011，由能力问题 Agent 根据建模输入和用户回答生成场景级
   全景能力问题及答案，覆盖端到端流程和跨切片关联，经用户审核后作为逻辑切片分析输入。
3. **逻辑切片分析**：在形成项目级场景地图时，依据业务流程内聚、问题集合、跨域依赖、共享术语、
   建模工作量和可独立复核性划分有界工作单元。切片用于组织建模工作，不代表平台存储边界；不得
   按表数量、团队人数或期望并行度机械拆分。
4. **切片能力问题生成、审核与分组**：能力问题 Agent 根据获批切片分别生成问题及答案，用户审核
   后从全景问题和各切片问题中分别划出公开建模集与隐藏验收集。建模 Agent 只接收公开问题及答案；
   隐藏问题和答案在建模开始前冻结并保持不可见。题量范围、角色权限和验收交接归 R3.0-011。
5. **平台中立基础图候选与共性抽象**：在不写入平台、不预设最终 Ontology 的候选图中表达业务
   节点、属性、关系、规则和显式未知，并执行 R3.0-009 的共性识别、关系提升与协调确认。该阶段
   只形成候选及决定记录，不把共同字段、重复样例值或重复样例关系直接物化为类别或普遍关系。
6. **Ontology 拓扑决策**：在切片、共享术语、共性节点、共性节点间关系和跨切片依赖已可见后、
   首次真实 apply 前，由建模协调
   Agent 比较单 Ontology、按领域拆分的多个 Ontology、共享核心加领域 Ontology 三种方案，并至少
   从概念内聚、关系密度、跨场景复用、权限边界、变更节奏、跨域查询六个维度记录取舍。逻辑切片
   与 Ontology 不要求一一对应。建模中发现新证据时可以提议调整，但必须更新决策记录、说明影响并
   重新获得协调 Agent 批准，不能由单个切片自行改变拓扑。
7. **基础业务语义建模**：在获批拓扑中正式建模稳定的概念、属性、关系、规则、指标、已批准共性
   结构和跨切片连接点。
   对经常出现、数量可控、近似受控枚举的候选值，分析其业务含义、稳定性、关系、规则、复用范围
   以及建议的 L1/L2/L3 表达。数据库实际编码未确认时，只产出带证据和理由的
   `analyzed_not_materialized` 分析结论；不得据此创建 `EnumValueMeaning`，也不得提前创建该候选
   值的正式 L3 节点。与候选值无关的核心业务语义可以继续建模。
8. **数据库映射与值语义物化**：数据库表、列、编码和值域经确认后，再统一建立 `TableMapping`、
   必要的关系/指标映射以及 L1/L2/L3 值表达。物化结果必须能追溯到前一阶段的分析结论；实际编码
   与原分析冲突时回到业务确认，不允许按列名或样例分布自动猜测。映射源不限定数据库 Schema：
   建模输入给定接口信息时，接口信息是同等地位的映射源（具体支持归 R3.0-010）；既未提供数据库
   Schema 也未提供接口信息时，直接跳过本阶段，受控值保持为
   `analyzed_not_materialized` 分析结论，其余业务语义不受影响。
9. **联合验收**：按 R3.0-011 使用隐藏能力问题执行批次级平台语义验收，并分别验证业务语义、共性
   节点与关系召回、跨切片/跨 Ontology 召回、值语义召回和 SQL 映射链。只有
   依赖受控值的问题也能从自然语言术语到语义节点、数据库原始值、属性及物理列形成可解释闭环，
   才能声明本需求通过。

### R3.0-009 统一语义图与共性抽象建模流程

状态：细化完成，Round 4 两项修订经 Round 5 专项复审 PASS（2026-09-08）；待实现、待独立验收。此前目标与
最小验收条件保持有效，本次补充可实施的功能、兼容与交付边界。用户授权推荐把握达到 80% 的
决策直接按推荐设计；该门槛用于本轮设计判断，不是平台抽象评分或运行时业务判断规则。
本轮仅交付需求细化、设计与共享测试计划，不实现产品代码，不启动真实 modeling start。
本需求改变业务建模的默认概念与首次 apply 前的阶段顺序，不追溯改写既有 Ontology。

#### 目标与术语边界

当前产品以 Class Diagram 与 Entity Diagram 分开组织建模，并要求 Entity 创建时先指定 Class，容易
把“先建 Class、再实例化节点”误当成所有业务知识的必经路径，也使建模团队在基础业务关系尚未
形成时过早抽象。本需求建立统一的业务语义图视角：

1. **语义节点一等化**：具体业务语义、受控参考值、规则、共性分类和正式 Class 角色都可以作为
   有稳定 IRI、属性及关系的一等节点被创建、查询和关联；用户和 Agent 不需要先创建 Class 才能
   表达一个合法业务节点。
2. **抽象按需**：Class、类型成员和上下位结构仍可在需要集合语义、统一约束或推理时使用，但不再
   是全部节点的默认结构。共性节点只是本需求中的描述术语，不新增平台资源类型；协议层可按获批
   语义选择现有 `rdf:type`、`rdfs:subClassOf`、业务分类关系、规则或 Shape。
3. **统一图不是物理合图**：统一语义图指用户和 Agent 的建模、检索与关系遍历视角，不要求合并
   RDF Named Graph、取消 Evidence/Shape/授权边界或把多个 Ontology 物理合成一个 Ontology。
4. **业务行边界不变**：本场景 PostgreSQL 中的客户、已安装设备、工单等业务行仍不得复制为 RDF
   个体；基础图中的节点必须是获准建模的业务语义资源、受控参考值、规则或测试 fixture，而不是
   借共性抽象流程同步业务数据。

#### 节点、关系与兼容合同

1. **无 Class 的节点是合法状态**：创建时只需现有必需的身份、名称及所属范围，不因未分类而
   隐式创建占位 Class、写空 IRI 或推断业务类型。沿用既有节点标记时，`owl:NamedIndividual`
   不得在产品或检索输出中冒充业务 Class。无类节点仍能读取、命名、赋予合法属性、建立关系和删除。
2. **正式类型为零到多个**：兼容旧单 Class 输入；新输入与读取须完整表达显式类型集合，新增或
   移除一个成员关系不得顺带覆盖其他分类。旧单值展示只能作为兼容投影，不能作为多分类的语义
   真值，也不能令未知类别、隐藏类别或超出当前分页范围的类别被错误解释为不存在。
3. **属性和谓词无需伪造 Class**：当业务未批准 domain/range 时，可以创建和使用没有这些类约束
   的属性/关系类型；已明确提供的约束仍校验。Class 的 domain/range 语义不能等同于普通节点
   之间的一条业务关系，亦不能以业务分类节点替代正式 Class 填入约束。
   放宽写入前置必须同步属性列表、节点列表/词法搜索及混合召回、投影和命令白名单；合法零类
   节点或无 domain 属性不能因缺少类连接而消失。资源自身身份与授权校验仍保留，具体防御收窄
   依设计 T0 五问记录；损坏的已声明类身份不能伪装为“无类”或作为完整写入绑定。
4. **同一图视角覆盖现有资源角色**：无 Class 节点、正式 Class、业务分类、规则等可按 IRI 被
   发现和引用；支持节点到分类、分类到成员、共性节点间的双向关系及适用规则导航。不能要求先
   猜页面归属再访问资源。单个 Ontology 和同 Project 获准多个 Ontology 使用同一语义合同。
5. **完整性与授权先于汇总**：读取保留谓词、方向、来源和必要的 Evidence/lineage；仅在获准范围
   内汇总，分页或截断明确标记，完整性只相对于授权可见集合判断。未授权语义遵循现有
   `forbidden` / 过滤边界，不新增暴露隐藏节点
   数量、类别或关系存在性的旁路。关系可达不等于继承成立，规则可见不等于已经执行。
6. **约束与推理按明确语义适用**：无 Class 不触发虚构的 class Shape。本需求须补齐非 Class
   Shape 的托管创建/更新、读取匹配、guidance 与实际校验，不能宣称这些链路已存在。
   最小支持旧 Class target、显式节点 IRI target，以及使用某谓词的主语 target；“谓词级”不指
   对全图所有节点自动施加约束。没有该谓词的节点不被 subjects-of 选中，缺失必填属性须用明确
   节点或 Class target 检查。多 Class、节点和谓词主体的适用约束不能只取第一项；冲突须可定位、
   可修正，不得静默覆盖。仅明确批准的集合包含使用 `rdfs:subClassOf`；共性描述属性不传播给成员。
7. **兼容现有模型**：既有单 Class 创建、IRI、物理图、规则和映射语义保持可用，不批量迁移或
   重写旧 RDF。新增合同在相应读写与 UI 路径显式接入，不能靠绕过 Modeling Batch、dry-run/apply
   或授权检查实现。001～008A 已验收能力及旧 R2.3 任务须有回归证据。
8. **UI 最小交付**：用户可以不选 Class 创建语义节点、查看其全部分类并导航相关类/节点/规则；
   没有 Class 时表单、详情和图展示均可工作。保留既有页面和必要的分类筛选，不建设新画布框架。

#### 建模阶段与批准合同

R3.0-008B 的逻辑切片分析之后、Ontology 拓扑决策之前，必须执行以下阶段：

1. **形成平台中立基础图候选**：建模 Agent 先以节点、属性、业务关系、规则和显式未知表达当前
   能确认的业务语义；候选不预设最终 Class/Entity 页面归属、Ontology ID 或 RDF 写入结构。
2. **发现共性候选**：识别多个节点重复出现的稳定业务含义、属性、关系、约束或规则。共同字段、
   相同字面量和样例数据中的重复模式只能形成候选，不能自行证明共同类别。
3. **评估抽象价值**：候选至少应能改善一项当前问题——稳定业务命名、重复知识复用、规则/Shape
   适用、能力问题回答、跨切片连接、语义召回或 SQL 映射。没有当前价值的候选记录为拒绝或不物化，
   不得为满足阶段形式而创建空分类节点。
4. **提出关系提升候选**：在已提出的共性节点之间识别上下位、业务关联、适用规则、依赖、兼容或
   约束关系，并明确其适用范围是“全部”“部分”“常见”还是“可能”。多个具体节点出现相同关系
   只能产生关系候选，不能自动提升为普遍关系。
5. **分别确认节点与关系**：建模协调 Agent 分别批准共性节点、成员/多重分类关系以及共性节点间
   关系；批准一个节点不等于批准其成员、继承或对外关系。发现跨切片共享结构时，确认结果作为
   后续 Ontology 拓扑决策输入，单个切片不得自行创建共享核心或复制同义节点。
6. **确定性物化与回归**：平台协议 Agent 只把已批准结果转换为现有平台可接受的节点、关系、Class
   角色、Shape 或规则写入；不得自行补猜类别、关系谓词、适用范围或继承语义。正式 apply 后验证
   从具体节点到全部分类、从分类到成员、共性节点间关系以及适用规则的双向召回路径。

#### 候选、批准与失败恢复细化

1. Modeling 使用稳定候选 ID 表达节点、属性、关系和规则，记录业务含义、证据、显式未知、所属
   逻辑切片及共享范围；不在拓扑批准前强制选定 Ontology ID 或平台载荷。Protocol 后续把候选
   身份映射为既有平台身份，返回可追溯对应关系，不自行补充业务语义。
2. Coordinator 分别记录共性节点、成员关系、共性间关系的 `approved`、`rejected` 或 `deferred`
   决定，绑定对象 ID、当前内容版本、理由和依据。共性间关系额外明确适用范围：全部、部分、
   常见或可能。范围不明确则保留未知，不物化为普遍关系；“全部”本身也不自动批准继承。
   物化的关系须在平台内保留可读取的限定含义、适用范围及证据，不能只将这些内容留在 run
   审批文件中；独立语义验收者仅通过获准平台读取即可理解其含义和边界。
3. 同一批准记录可容纳多项独立决定，但不能以“节点已批准”代替其成员、继承或关联关系批准。
   修改候选内容后，受影响决定须重审；未改变的独立决定可复用。生产场景没有值得抽象的共性时，
   记录有依据的拒绝/不物化决定即可继续，不以类别或关系数量作为通用运行门。
   获批内容按确定版本发布；Runner 校验当前版本并捕获批准快照后接收请求，后续只提交该快照。
   新修订使旧批准不能用于新内容或后续尚未接收的请求，不追溯撤回已经接收的请求；在途写入仍
   必须满足现有 workspace version、lease 和原子 apply 检查，不因快照批准绕过平台完整性。
4. 复用 008B `stage3-neutral-graph` 与批准产物、角色写入归属、既有提交及 intent/receipt 机制，
   回填详细引用与批准合同。向平台提交的实际命令须绑定获批对象和版本；未获批成员或关系不能
   混入已批准节点的属性、类型或其他命令中。校验针对可观察内容与批准一致性，不判断业务好坏。
   此候选批准义务适用于启用 009 的 Team 建模流程；普通用户仍沿现有产品授权、编辑锁与
   确定性写入路径编辑，不新增必须先启动 Team 或经过 Coordinator 的全平台审批机制。
5. 缺字段、引用缺失、旧版本批准、关系范围不明等问题返回准确对象和修复方法，只阻止对应不安全
   批次。修复后允许同一 run 继续；既有不可拆分批次仍保持原子性，不静默应用其中的部分内容。
   若写入结果未知，复用既有对账通路查清结果后再继续，不另建恢复框架。
6. 009 的无 Class 节点路径不得绕过 008B 值物化时点：数据库编码未知的受控值仍只记录
   `analyzed_not_materialized`。通用业务语义和已确认分类可以继续，候选值不得借“基础节点”
   名义提前变成正式 L3。008A 的 `semanticValue` 与 G7 完整性合同继续生效。
7. 正式 v3 阶段顺序以 008B 现行需求为准：011 能力问题阶段插入后，009 对应“基础图候选与
   共性抽象”阶段；既有代码中 `stage3` 是兼容路径名，不据此忽略能力问题或另建一套阶段编号。

#### 多重分类、继承与关系语义

1. 同一节点可以连接多个相互独立的共性节点，例如同时属于产品类型、安全类别和维护分组；平台
   不得强制单一 Class 或单父分类树。
2. 分类成员、上下位、普通业务关联、适用规则和统计/典型关系必须使用可区分的谓词及检索解释；
   禁止用无明确含义的统一 `relatedTo` 代替。
3. 一个共性节点自身的描述属性不自动传播给成员。只有明确批准为成员适用的规则、Shape、默认值
   或推理关系才参与继承/适用计算；具体节点事实可以覆盖默认知识时，必须保留来源与覆盖解释。
4. `rdfs:subClassOf` 只用于确实需要集合包含和传递类型语义的获批关系；普通分类、标签、业务分组
   或“常见/可能”关系不得因结构相似被翻译为子类或确定性继承。

#### 角色职责

- **建模 Agent**：形成基础图、提出共性节点与关系候选，说明成员范围、业务价值、证据、适用程度
  和显式未知；不得直接写入正式图。
- **建模协调 Agent**：分别批准节点、成员/多重分类、共性节点间关系及其拓扑归属，并拒绝只有结构
  相似而无业务含义的抽象。
- **平台协议 Agent**：确定性物化获批表达并回传可检索身份；不承担聚类、业务归纳或审批职责。
- **Runner/工具**：检查阶段顺序、引用闭合和批准完整性；可以提示重复模式，但不得自动创建类别、
  提升关系或把抽象评分作为业务真值。

#### 最小验收条件

1. 一个代表场景先产生不依赖 Class 前置的基础图候选，再产生至少一个获批共性节点；同一业务节点
   能连接至少两个不同分类维度，并能双向召回全部分类与成员。
2. 至少有一个“共同字段或相同字面量但无稳定业务意义”的抽象候选被拒绝且未物化，证明流程不是
   按结构相似自动建类。
3. 至少两个获批共性节点之间建立一条有业务证据、明确谓词和适用范围的语义关系；查询能从具体
   节点经分类节点、共性节点间关系到达适用规则或目标业务概念，并返回来源和关系含义。
4. 至少一个由重复样例事实产生、但不能证明普遍成立的关系提升候选被拒绝；RDF 中不得出现对应的
   类型级确定性关系或错误继承结果。
5. 节点、成员/多重分类和共性节点间关系具有相互独立的批准证据；缺少任一批准时，平台协议 Agent
   不得物化对应结构。跨切片共性关系必须进入拓扑决策输入，不能由单个切片私自复制节点。
6. 统一语义图的建模与查询行为不得泄露受保护语义、破坏现有确定性 dry-run/apply 或将 PostgreSQL
   业务行导入 RDF。既有 Class/Entity 图、R3.0-002 机械流程或 R3.0-008B 运行证据均不得替代本需求
   的专项验收。
7. Agent 与用户均可创建无 Class 节点并建立含义明确的属性与关系；节点在列表、详情、搜索及
   关系导航中均可见。旧单 Class 输入保持可用，多 Class 的全部成员关系、约束和反向成员均能
   被完整读取；分页或受限范围不能被误报为全集。
8. 批准缺失、内容修订后批准过期及候选值提前物化均有负例；失败后修复同一 run 的产物即可
   继续，拒绝项无正式写入。没有有价值共性的场景能够有理由地继续，不能被代表样本数量硬阻断。

交互或持久化方案，也不因本次登记启动真实 modeling start。

#### 目标与适用边界

本需求在正式建模前先形成一组“模型最终应该能够回答什么”的能力问题，使逻辑切片、建模范围和
后续验收共享同一业务目标，同时避免仅用已经展示给建模 Agent 的问题验证模型：

1. 先形成场景级全景能力问题，再依据获批逻辑切片形成每个切片的能力问题；问题和参考答案只能
   根据当前允许的业务材料及用户输入推断，不得引入 tester-only 真值或 Agent 自行补猜的业务事实。
2. 问题及答案先由用户审核，再于正式建模前从全景问题和每个切片的问题中分别划出公开建模集与
   隐藏验收集。公开集用于指导建模，隐藏集用于检验对未展示问题的泛化能力。
3. 本需求调整的是 v3 建模与验收流程。旧 R2.3 中 Source Examiner、Platform Examiner、
   Acceptance Agent 以及逐题 fresh 会话的合同和历史证据保持原样，不追溯修改。
4. Platform Examiner 只验证平台中的语义知识、关系、规则和值/数据库映射能否支撑答案；真实 SQL
   执行及数据库结果比对仍归 R3.0-006，不得用语义回答替代。

#### 固定角色与阶段流程

1. 增加一个独立、固定的**能力问题 Agent** 角色。它复用现有建模团队的 Profile/roster 启动路径，
   资料读取范围与建模 Agent 相同，但提示职责收窄为生成能力问题、参考答案、依据和显式未知；不
   创建 Ontology 候选、不调用平台写入或语义查询接口，也不读取隐藏 tester-only 材料。
2. 该角色是团队 roster 中预先配置的角色，不要求 Runner 在运行中动态创建临时独立会话，也不
   引入新的 Agent 调度框架。Runner/协调 Agent 只负责按阶段启动或继续该角色、交接获批切片及
   记录审核状态。
3. 能力问题 Agent 首先根据场景材料及用户输入生成全景问题和参考答案；用户可批准、修改、删除或
   要求补充。等待用户审核必须是可恢复的暂停，不能因等待或一次修改使整个 run 永久失败。
4. 全景问题获批并完成逻辑切片后，同一角色按切片分别生成问题和参考答案，再接受用户审核。被
   修改或拒绝的问题只回到受影响的问题阶段，不要求重启全部建模流程。
5. 正式建模开始前冻结问题池、答案及可见性分组。建模 Agent 只接收公开问题及其获批答案；隐藏
   问题和答案均不得进入建模 Agent 的上下文。Platform Examiner 只接收隐藏问题、获批模型范围和
   只读语义查询能力，不接收参考答案；Acceptance Agent 持有冻结参考答案及判定依据。
6. 若验收时发现题目或参考答案与获批材料冲突、存在关键歧义或无法由材料支持，该题必须标记为
   “题目/答案待复核”，不得直接计为模型失败；是否修订和重新纳入验收由用户确认。本规则不要求
   当前建设自动问题正确性评分器。

#### 建议题量

题量用于控制覆盖面和人工审核成本，不是平台硬门。当前默认建议为：

| 问题集合 | 建议数量 | 主要覆盖 |
| --- | ---: | --- |
| 全景能力问题 | 5～8 个 | 端到端流程、跨切片关联、共同术语和关键业务结果 |
| 每个切片的能力问题 | 3～6 个 | 切片内核心概念、关系、规则、值语义及对外依赖 |
| 隐藏全景验收题 | 约 2 个 | 跨切片或跨 Ontology 召回 |
| 每个切片的隐藏验收题 | 通常 1 个，复杂切片可 2 个 | 各切片的最低验收覆盖 |
| 当前五切片场景的隐藏题总量 | 通常 6～10 个 | 全景与 S1～S5 的组合覆盖 |

实际数量可以因资料规模、切片复杂度、问题重复或用户判断高于或低于建议范围；只需记录理由并经
用户认可，不得因少于或超过建议数量被平台拒绝，也不得把固定题数写成 Runner 的合法性校验。

#### v3 批次级语义验收

1. v3 不再启动一个重复读取业务材料并回答同批问题的 Source Examiner。能力问题 Agent 生成的
   参考答案、依据和用户审核记录构成验收基线，但能力问题 Agent 本身不参与模型判定。
2. 每个隐藏题批次启动一个独立于建模上下文的 Platform Examiner 会话；不为每道题新建会话。
   Platform Examiner 在同一会话内按顺序调用平台只读语义接口回答全部隐藏题，可以保留本批前题
   的查询上下文，但始终不可读取冻结参考答案、建模讨论记录或 tester-only 真值。
3. Platform Examiner 必须为每道题分别保留回答、所用语义资源/关系/规则或映射证据、无法确认项
   及题目状态，再给出批次汇总。某一题的语义缺失或答案错误不得阻止其继续执行剩余题目；只有
   平台或运行时已经无法继续查询时才可中止批次，并明确已完成题和未执行题。
4. Acceptance Agent 逐题对照冻结答案和依据，区分“通过”“模型/召回不满足”“题目/答案待复核”
   与“平台/运行时未完成”，然后汇总全景和各切片覆盖。实际题数由获批隐藏列表驱动，不再假设
   固定两题或固定会话数量。
5. 这里的独立性是指验收者不参与问题生成和模型生产、且看不到答案，不要求同一隐藏批次的题目
   彼此隔离。若同会话上下文在真实测试中被证明确实造成错误串扰，再以证据决定是否细分批次，
   当前不提前恢复逐题 fresh Agent。

#### 最小验收条件

1. 固定能力问题 Agent 能通过现有团队 roster/Profile 路径启动；能读取获准业务材料和用户输入，
   但不能读取 tester-only 真值、调用平台或产生正式模型写入；整个流程不依赖动态 Agent 创建能力。
2. 一个完整场景存在获批的全景问题和每个逻辑切片的问题及答案，并在正式建模前冻结公开/隐藏
   分组；运行证据证明建模 Agent 只获得公开问题及答案，Platform Examiner 只获得隐藏问题。
3. 建议题量内和经用户认可的建议题量外案例都能继续流程，不存在固定题数硬拒绝；等待用户审核、
   修改或补题后能够从原阶段继续。
4. 一个 Platform Examiner 会话能连续完成包含全景题及各切片题的隐藏批次，为每题保留答案与
   语义证据；它不读取参考答案，且不因单题失败停止剩余题目。
5. v3 运行证据中不再启动 Source Examiner；Acceptance Agent 能逐题判定并汇总，且能把有证据
   冲突的题目标为待复核而不是误判为模型失败。旧 R2.3 合同、测试和证据不被本需求改写。
6. 至少一个代表问题证明平台语义能够支持答案；涉及数据库实际结果的题目还必须继续通过
   R3.0-006 的 SQL 生成、执行和结果比对链路。验收同时证明 RDF 未复制业务行。

#### 当前非目标

- 不建设自动能力问题正确性评分、难度分级、随机抽题、题库版本治理或通用 Benchmark 平台；
- 不建设动态 Agent 创建、通用临时会话服务、新的编排框架或管理 UI；
- 不以固定问题数量、固定切片数量或固定 Agent 数量作为平台写入和验收的硬门；
- 不要求每题启动隔离 Agent，也不在 v3 恢复 Source Examiner；
- 不用本需求替代 R3.0-006 的真实 SQL、授权、RDF 业务行边界和端到端验收。
