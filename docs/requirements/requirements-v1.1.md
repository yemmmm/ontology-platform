## 背景

v1.0 主要解决建模结果如何安全进入平台以及如何被后续 Agent 使用，包括默认语义工作区、
Evidence Reference、Build Session、Modeling Batch、确定性校验、lineage、Context Query 和
Operation 等基础能力。这些能力能够保证建模过程可提交、可恢复、可验证、可追溯和可查询，
但不能保证外部建模 Agent 对业务资料的理解正确，也不能保证最终模型具有实际业务价值。

仓库中的当前 `ontology-builder` 形成于平台早期版本。虽然其中保留了业务访谈、能力问题、
证据、建模和验证等部分概念，并且后续做过接口名称对齐，但整体方法、产物和 eval 仍基于早期
流程，已经不能作为当前可用的建模工作流，也不能作为有效的单 Agent 质量基线。v1.1 需要依据
当前 v1.0 平台能力和本文件确认的新流程重新设计该 Skill，而不是先运行旧 Skill 得出比较结论。

因此，v1.1 不以继续堆叠平台功能为默认方向，而是把“提升建模 Agent 的实际建模效果”作为
总体效果目标。R1.1-002 是围绕该目标首个确认实施的工作流需求；其他优化手段仍应先由实际
建模问题证明价值，不能脱离 R1.1-001 单独扩张平台范围。

## 与 v1.0 的关系

1. v1.1 建立在 v1.0 已有建模、证据、验证、存储、查询和治理能力之上，不重新定义这些基础
   协议。
2. 外部建模 Agent + Skill 继续承担资料理解、业务澄清、知识提取和建模判断；平台继续承担
   确定性验证、持久状态、证据、版本、审计、查询和治理。
3. v1.1 不要求把通用大模型或 Agent 运行时放入平台核心，也不允许为了 Dify 场景加入 Dify
   专用的平台分支。
4. v1.0 的 R-008 已完成；R-009 挂起；R-010 原独立量化验收套件不再作为
   v1 P0，其效果目标由 R1.1-001 接续，首轮具体工作流由 R1.1-002 承接。
5. v1.0 其余 P1/P2 需求默认 Pending。若建模实践证明其中某项是改善建模效果的必要条件，
   可以恢复该需求、调整范围并在本文件记录原因。

## 用户、建模 Agent 与平台的目标交互

```text
用户提供业务目标、资料范围和必要澄清
  -> 建模 Agent 读取资料、理解业务、提出问题并形成模型
  -> 平台提供当前语义状态、确定性预检、证据和写入反馈
  -> 建模 Agent 根据业务反馈和平台反馈持续修正
  -> 用户结合真实业务用途判断模型是否有价值
  -> 平台保存最终结果、证据、版本和建模过程记录
```

这里的“建模”不是流水线中的一次生成步骤，而是 Agent 围绕业务知识反复理解、建模、检查和
修正的核心过程。平台反馈可以帮助 Agent 发现结构错误和已有知识冲突，但不能替代 Agent 对
业务含义的判断。

## R1.1-001 优化外部建模 Agent 的实际建模效果

当前状态：`未实现`

### 要解决的问题

在给定外部业务资料和有限用户澄清的情况下，现阶段没有足够证据证明建模 Agent 能够稳定地
把资料整理成符合业务认知、能够支持真实使用的本体和知识模型。当前平台更擅长判断“提交内容
是否合法”，而不是判断“这个模型是否建得好”。如果建模效果不足，即使后续写入、治理、查询
和审计流程全部正确，平台也难以产生实际业务价值。

### 目标行为

持续优化外部建模 Agent，使其能够更好地理解外部业务资料、识别和澄清关键业务含义、形成
适合当前业务目标的模型，并根据用户反馈、已有语义状态、平台校验结果和实际使用结果修正
模型。优化后的结果应形成可复核、可重复的质量改善证据，更有助于用户沉淀业务知识，并更有助
于消费 Agent 理解业务和完成相关任务。

本需求不预先限定实现路径。允许采用的手段包括但不限于调整模型、Prompt、Skill、参考材料、
上下文组织、建模步骤、候选方案比较、自我检查、多 Agent 协作、人机澄清方式、平台反馈、
工具接口、工作台或其他代码能力。这里列举的是可能的优化手段，不是独立子需求，也不要求
全部实现。

### 实施原则

- 当前旧 Skill 已失去有效基线条件，不要求在实现前重新运行；先记录其已知限制和不可用原因。
- 按已确认的 R1.1-002 实现新工作流后，再使用真实或具有代表性的业务资料观察结果和主要问题。
- 优先修正对最终业务价值影响最大的建模问题，不为覆盖所有可能情况而提前建设通用框架。
- Skill、Agent 工作方式或平台代码都可以修改，但每次修改应能说明它针对了什么实际建模问题。
- 若修改平台代码，继续遵守 v1.0 的确定性平台边界，并按仓库规范补充测试、文档和运行时验证。
- Dify 是首个深入分析和试用场景，不把 Dify 特有概念硬编码进平台通用模型或接口。
- 在形成足够实践经验前，不预设固定任务数量、百分比阈值或单一“标准本体”作为版本完成条件。

### 已确认实施方向

分阶段建模、角色化子 Agent、业务知识结构化交接、覆盖检查、质量门禁和执行过程留档已经形成
明确的工作流合同，不再只作为 R1.1-001 下的候选实验。具体范围和验收标准由 R1.1-002 定义。

### 验收方式

v1.1 通过实际建模过程和结果评审验收，而不是只检查 Agent 是否调用了正确工具，也不在当前
阶段预设细粒度量化指标。至少需要留下以下可复核证据：

- 记录旧 Skill 的历史设计、已知问题和不再适合作为有效基线的原因，不要求为了比较而重新运行。
- 记录所采用的优化手段、相关代码或 Skill 变更及其原因。
- 新工作流实现后，使用 Dify 资料完成一次可复核的端到端建模过程，并展示模型如何支持业务理解
  或后续使用。
- 由用户或领域评审者结合业务目标评审新流程结果，确认其具有实际价值；后续工作流版本之间的
  改善再使用同条件运行或受控消融验证。
- 记录仍然无法可靠处理的场景和已知限制，不能仅凭流程成功或平台校验通过宣称建模效果达标。

当上述证据能够证明建模 Agent 对外部业务知识的整理效果已有实际改善，并且相关变更可重复
使用时，可以将本需求更新为 `已实现`；若仍处于试验和迭代阶段，则保持 `进行中`。

## R1.1-002 分阶段、可追溯的建模工作流

当前状态：`已实现`

方案状态：`已确认`

阶段性完成确认：2026-07-18，用户确认当前本体已具备一定使用价值，同时仍有优化空间。本确认
关闭 R1.1-002；持续效果对比、推理血缘增强和更多真实业务场景验证继续由 R1.1-001 承接。

依赖：R1.1-001，以及 v1.0 的 R-002、R-003、R-004、R-006、R-008

### 要解决的问题

一次性读取整个项目并直接生成完整本体，容易因上下文过载、未经澄清的假设和过大的审核范围
产生连锁错误；只读取局部资料便开始构建核心本体，又可能缺少项目全局认识，形成术语冲突、
边界错误和后续大规模返工。早期 Skill 的单 Agent 自我检查还可能继承前序建模假设，难以独立
发现遗漏，但该 Skill 已不具备有效基线条件，不要求在本需求实施前重新运行验证这些已知问题。

现有 Build Session、Build Checkpoint、Modeling Batch、Evidence Reference 和平台审计能够记录
当前进度、已提交批次和确定性平台事实，但不能完整回答建模过程中读取了哪些资料、做过哪些
业务判断、问过哪些问题、用户如何回答、形成过哪些中间产物以及评审为何要求返工。依赖聊天
记录或本地文件无法稳定支持不同 Agent 恢复，也无法为后续比较和优化工作流提供统一样本。

### 总体工作流

采用“先全局扫描、再核心建模、随后分批扩展”的流程。业务理解先宽后深，模型写入从能够支持
高优先级业务问题的最小纵向切片开始，而不是一次生成追求表面完整的全量本体：

```text
恢复 Project / Build Session 当前状态
  -> 全局扫描资料和业务范围
  -> 形成 Business Knowledge Pack 与 Modeling Coverage Matrix
  -> 用户确认业务摘要、高优先级能力问题和关键歧义
  -> 选择核心纵向切片
  -> 建模子 Agent 生成模型及 Modeling Batch 草案
  -> 平台 dry-run
  -> 独立评审子 Agent 审核业务覆盖、模型和平台 Findings
  -> 必要时返工
  -> 主 Agent 获取 Lease 并 apply
  -> 通过 Context Query / SPARQL / validation / lineage 反向验收
  -> 根据 Coverage Matrix 扩展下一批知识
```

“核心纵向切片”不是若干高频名词或孤立 Class，而是回答一组高优先级能力问题所需的最小业务
闭环，可以包含概念、身份、生命周期、关系、事实、规则和 Operation。每次扩展继续使用同一套
业务确认、证据、dry-run、独立评审、apply 和查询验收流程。

### 结构化业务产物

业务整理阶段必须先生成可版本化的 `Business Knowledge Pack`，至少包含：

- 业务目标、成功条件、范围和明确非目标；
- 资料清单、资料边界、权威优先级、新鲜度以及已扫描状态；
- 术语、定义、别名、参与者、对象、事件和业务记录；
- 主要流程、状态变化、规则、约束、例外及其生效范围；
- 身份、生命周期、时间、区域和版本边界；
- 可执行操作的目的、输入、输出、副作用和约束；
- 能力问题、优先级和具体成功条件；
- 相关原文证据索引；
- 歧义、资料冲突、知识缺口、待澄清问题，以及已发现但暂不建模的内容。

业务整理角色不得在该产物中提前决定 Class、Property、RelationType 或 Modeling Batch 结构。
建模角色负责把已确认的业务语义转换为模型，避免两个角色实际重复执行同一建模判断。

同时维护 `Modeling Coverage Matrix`，形成以下可追踪关系：

```text
资料或用户声明 -> 业务知识项 -> 能力问题 -> 模型元素 -> Evidence Reference -> 当前状态
```

每个重要知识项必须具有 `MODELED`、`DEFERRED`、`AMBIGUOUS`、`UNSUPPORTED` 或 `MISSING`
之一，不能在整理、建模或返工过程中静默丢失。覆盖检查至少分别检查资料覆盖、业务覆盖、能力
问题覆盖、证据覆盖和生命周期覆盖；这些状态用于暴露遗漏，不等同于宣称绝对完整。

Business Knowledge Pack、Modeling Coverage Matrix、模型草案、评审报告和验收报告应作为
Build Session 下的版本化 `Modeling Workflow Artifact` 持久化。每次更新创建不可变新版本并
记录产物类型、内容格式、内容哈希、创建角色、创建时间和被替代版本；平台只保存和返回这些
结构化工作产物，不对其业务结论作智能判断。执行事件必须引用确定的产物版本，不能只引用某个
Agent 本地可能丢失的文件路径。

### 业务提问方向

`ontology-builder` 应预置业务信息检查方向，但不把它变成一次性固定问卷。Agent 先从资料和
现有平台状态中寻找答案，只向用户提出会改变模型语义、优先级或验收结果的问题。检查方向至少
包括：

- 业务目标、使用者和需要支持的决策；
- 范围、非目标、参与者、对象、事件、文档和系统；
- 流程顺序、状态变化、身份与去重规则；
- 业务规则、例外、冲突及来源权威性；
- 时间、区域、版本、有效期和知识更新责任；
- 外部操作的输入、输出、副作用、幂等和约束；
- 需要回答的业务问题、成功条件和当前无法回答的问题。

每轮最多询问三个阻塞问题。已确认答案、显式跳过项和仍不确定项必须进入业务产物与执行记录；
除非来源变化、用户重新打开问题或模型冲突暴露新含义，恢复后的 Agent 不应重复询问。

### 角色化子 Agent 与职责边界

首轮使用当前 Runtime 的通用子 Agent 能力，由主 Agent 注入角色提示词，不安装或生成
OpenCode、Codex、Claude Code 等 Runtime 专用 Agent，也不要求平台托管或启动外部 Agent：

1. **业务整理子 Agent**：读取业务资料和用户目标，生成 Business Knowledge Pack、Coverage
   Matrix 和待澄清问题；不提前设计本体。
2. **建模子 Agent**：读取已确认的业务产物、证据和当前 Modeling Context，生成模型草案及
   Modeling Batch 草案；不获取 Lease，不执行 apply。
3. **建模质量评审子 Agent**：独立检查资料与业务覆盖、概念和身份边界、关系含义、证据充分性、
   能力问题支持度、可维护性及过度建模风险，输出 `PASS`、`REVISE` 或 `BLOCKED` 和结构化
   Findings；不修改或提交模型。
4. **主 Agent**：协调产物交接、向用户提问、调用 dry-run、组织返工、记录执行事件，并且是唯一
   可以获取 Ontology Lease 和执行正式 apply 的角色。

三个子角色必须使用相互独立的新上下文，通过主 Agent 显式传递版本化产物。评审角色不能只看
业务整理结果，还必须看到原始资料清单、Coverage Matrix、关键原文或可访问的原资料，以及平台
dry-run Findings，从而发现业务整理阶段已经发生的遗漏。若 Runtime 不支持子 Agent，必须明确
回退到单 Agent 流程，不得将同一上下文中的角色切换记录为多 Agent 实验。

### 建模质量门禁

正式 apply 前至少通过以下门禁：

1. **业务门禁**：目标、范围、非目标和高优先级能力问题已经确认，或用户明确接受带不确定性继续。
2. **语义门禁**：身份、生命周期、关系含义和关键术语不存在未处理的阻塞歧义。
3. **覆盖门禁**：重要知识项均有显式状态，核心纵向切片能够支持目标能力问题。
4. **证据门禁**：重要建模项具有原文 Evidence Reference；无证据内容明确保留其状态和原因。
5. **平台门禁**：Modeling Batch dry-run 已完成，所有确定性 Findings 已处理或明确接受。
6. **评审门禁**：独立评审返回 `PASS`；`REVISE` 必须返工，`BLOCKED` 必须先补充资料或澄清。
7. **验收门禁**：通过当前读模型、Context Query/SPARQL、validation 和 lineage 证明核心能力问题
   可回答且来源可追溯。平台校验通过不能单独代表业务质量通过。

### 建模执行记录留档

一个 Build Session 下应具有一份追加式 `Modeling Execution Record`，由按时间排序的
`Modeling Execution Event` 构成。它与现有能力的区别是：

- Build Checkpoint 表达“当前处于哪里、下一步是什么”；
- Modeling Execution Event 表达“实际发生过什么、输入输出是什么、为什么形成该显式决定”；
- Modeling Batch、Validation、Evidence、Audit 和当前读模型继续是平台事实的权威来源；执行事件
  只引用这些资源，不通过复制或回放替代当前平台状态。

每个执行事件至少记录：

- 所属 Project、Build Session，可选 Ontology，以及发生时间；
- 工作流名称与版本、执行阶段、事件类型、状态、执行者角色、角色提示词版本和
  Agent/Runtime 标识；角色提示词只记录可追踪版本，不默认复制完整系统提示词；
- 简明动作摘要、输入资料或产物引用、输出产物引用及其版本或内容摘要；
- 提出的问题、问题状态，以及用户回答、Interview Answer ID 或其他回答引用；
- 显式业务决定、采用理由、被否决方案、未解决问题、阻塞项和下一步；
- 相关能力问题、Evidence Reference、Modeling Batch、Attempt、Finding、Lease、Validation 或
  Lineage 标识；
- Runtime 能够提供时的耗时、模型和 token/成本摘要，用于比较工作流效果，而不是作为质量结论。

外部上报事件必须使用稳定的 `client_event_id` 或等价幂等键，网络重试不得产生重复记录；平台
为事件分配 Session 内稳定顺序。记录错误时追加更正或 supersedes 事件，不允许静默改写已有
历史。事件还应区分 `agent_reported`、`user_reported` 和 `platform_observed` 来源，避免把 Agent
摘要冒充为平台已验证事实。

首版至少支持 `source_scanned`、`artifact_created`、`question_asked`、`answer_recorded`、
`decision_recorded`、`dry_run_completed`、`review_completed`、`rework_requested`、
`batch_applied`、`verification_completed`、`phase_completed` 和 `blocked` 等事件类型。外部主 Agent
显式上报业务理解、问题和决策类事件；平台已经持久化的批次、验证和审计事实应通过稳定 ID 关联，
不得维护一份可能冲突的第二真相。

评审、返工和阻塞事件还应记录结构化质量问题，至少包含：

- `issue_category`：知识遗漏、术语冲突、身份错误、关系错误、粒度错误、证据不足、能力问题缺口、
  过度建模、知识过期或其他明确类别；
- `introduced_phase`、`detected_phase` 和 `detected_by_role`：问题最可能在哪个阶段引入、在哪个阶段
  被发现，以及由用户、业务整理、建模、评审或平台哪个角色发现；
- `severity`、`rework_cost` 和 `preventable_at`：影响程度、实际返工次数或耗时，以及理论上最早可
  发现该问题的阶段。

这些字段用于复盘流程瓶颈，不把 Agent 对根因的判断伪装成平台事实；无法确定时应明确记录未知。

执行记录归属 Project 并复用 R-008 权限边界，支持按 Build Session 分页查询、按阶段或事件类型
过滤，并至少能够导出结构化 JSON 和便于复盘的 Markdown 时间线。不同的已授权 Agent 恢复同一
Session 时，应能够据此识别已完成工作、已确认问题、当前产物版本、未解决事项和下一步。

执行记录不是完整聊天记录，不保存模型隐藏推理或 chain-of-thought，不默认保存系统提示词、
完整原始资料、凭证、密钥或其他秘密。问题和用户回答需要留档时，应保存用户可见内容或引用
现有 Interview Answer，并支持提交前脱敏。`.ontology-build.md` 仍可作为 Agent 本地工作缓存，
但不能替代平台持久执行记录和当前平台事实。

### 首版实现边界

- 依据当前 v1.0 REST/MCP、R1.1-002 工作流和质量门禁重构 `ontology-builder`；旧 Skill 只作为
  历史材料，不要求先运行，也不能因部分提示词或接口仍可复用而被视为当前有效实现。
- 在新 Skill 中先实现角色提示词、Business Knowledge Pack、Coverage Matrix、评审输出和执行
  事件格式，不先建设固定 Runtime Agent 配置或通用编排引擎。
- 平台首版只需提供 Build Session 下工作产物和执行事件的持久化、REST/MCP 写入与查询以及
  JSON/Markdown 导出；不要求新增复杂可视化工作台，后续是否接入 R-107 由实际使用决定。
- 平台不解析业务资料、不判断本体质量、不自动生成问题或下一步，也不托管 Agent Runtime。
- 只有主 Agent 可以执行需要 Lease 的正式写入；子 Agent 产物和执行事件本身不授予写权限。
- 当前仓库可使用 repo-local Codex Harness 记录每个主 session 的增量建模复盘，用于本地测试和后续
  优化分析；Harness 不作为平台 API、Plugin 或已发布 `ontology-builder` Skill 的运行依赖。raw 事件
  和游标仅保存在 gitignored workspace，只有 completed/cancelled 且已完整总结、脱敏的复盘进入
  `docs/modeling-retrospectives/`；首次使用前必须显式 trust 当前项目 Hook。

### 验收标准

- 不要求运行当前旧 Skill 建立单 Agent 基线；需求交付的第一次实际建模运行发生在新 Skill 和
  必要平台能力完成之后，并使用 Dify 资料验证完整流程。
- 首轮 Dify 运行能够复核知识遗漏、错误概念或关系、术语一致性、能力问题支持、评审发现、用户
  返工、耗时和模型消耗，并由用户或领域评审者判断结果是否具有实际业务价值。
- 建模前存在版本化 Business Knowledge Pack 和 Coverage Matrix；核心模型由高优先级能力问题
  驱动，重要知识项没有被静默忽略。
- 业务整理、建模和评审使用独立上下文；评审能够抽查原始资料并发现业务整理阶段的遗漏，而不
  只是验证本体结构或重复平台 dry-run。
- 每批正式写入均经过业务、语义、覆盖、证据、平台和评审门禁，并在写入后完成查询、验证与
  lineage 验收；只有主 Agent 获取 Lease 和 apply。
- Build Session 能够按时间查询和导出完整的结构化执行时间线，至少覆盖读取资料、创建或更新
  产物、提出问题、记录回答、业务决定、dry-run、评审、返工、apply、验证、阻塞和阶段完成。
- Business Knowledge Pack、Coverage Matrix、模型草案、评审报告和验收报告具有可读取的不可变
  版本；事件引用具体版本，另一个 Agent 不依赖原 Agent 的本地文件即可获得交接产物。
- 执行事件具备幂等上报和稳定顺序，更正通过追加事件保留历史；记录中能够识别工作流、角色提示
  词和 Runtime 版本，以支持后续按版本比较质量、返工、耗时和成本。
- 评审、返工和阻塞事件能够按质量问题类别、引入阶段、发现阶段、发现角色、严重程度和返工成本
  进行复盘，并允许根因未知，不以未经验证的 Agent 判断替代平台事实。
- Agent 中断后，另一个已授权 Agent 能够依靠 Build Context、当前 Modeling Context、版本化业务
  产物和执行记录继续工作，识别一个明确的下一步，并且不会无原因重复询问已经确认的问题。
- 执行记录能关联现有平台事实但不会覆盖它们；不保存隐藏推理、秘密或默认完整聊天记录，跨项目
  访问按照 R-008 失败关闭。
- 工作流能力和首轮 Dify 端到端验收全部通过后，可以将 R1.1-002 更新为 `已实现`；R1.1-001
  仍需等待后续同条件运行、受控消融或更多场景证明建模质量能够重复改善后再更新为 `已实现`。

### 实施与后续迭代决定

当前不新增 R1.1-003，也不在 R1.1-002 实现前继续扩张方案。先完成新 Skill、工作产物、执行
记录和必要的平台接口，再运行 Dify 场景并复盘质量问题。旧 Skill 的重新运行不在实施顺序内。

若首轮完成后需要比较某项机制的实际贡献，应基于新实现做受控消融，例如在相同新 Skill 和资料
下比较单 Agent 与角色化子 Agent、启用与不启用独立评审，不能把已失效旧 Skill 的结果作为
对照组。

以下方向暂作为观察清单，不是当前独立需求：

- 能力问题本身的质量和对真实业务目标的代表性；
- 来源权威性、冲突、新鲜度和资料缺失；
- 身份、生命周期、时间、区域与版本语义；
- 反例、异常和边界条件下的对抗验证；
- 来源变化后的增量更新、删除和重新审核；
- 本体边界、模块化和跨本体复用；
- 消费 Agent 的检索与真实任务完成效果；
- 子 Agent 上下文交接、用户提问负担、耗时与模型成本；
- 从 Dify 扩展到第二个领域时的泛化能力。

只有执行记录显示某类问题重复发生、影响实际业务价值，并且不能通过 R1.1-002 的 Skill 或流程
调整解决时，才恢复 v1.0 Pending 需求或提出新的 v1.1 需求。例如来源采集、增量更新、持久召回、
本体组合和质量可观测性问题可分别重新评估 R-101、R-102、R-103、R-104 和 R-108。

## R1.1-003 建模子 Agent 大体量结构化产物的可靠交接与恢复

当前状态：`未实现`

方案状态：`已确认，下一项主要需求`

确认日期：2026-07-18

依赖：R1.1-001、R1.1-002，以及 v1.0 的 R-003、R-004

### 现状与本次暴露的问题

首轮 Dify 基础功能建模已经完成资料扫描、业务确认、Evidence Reference、Business Knowledge
Pack、Modeling Coverage Matrix、能力问题和第一版草案评审。返工后的 v2 建模子 Agent 也已经
成功生成 27 项候选模型，但完整七字段 JSON 通过统一执行终端的 PTY 文本返回时被截断，主 Agent
只能取得输出头尾，无法无损恢复完整草案。

这不是 Dify 资料无法理解，也不是建模模型没有生成结果，而是子 Agent 到主 Agent 之间缺少可靠的
大体量结构化产物交接协议。当前流程实际依赖终端输出、聊天上下文或 rollout 日志承载完整 JSON；
当输出超过显示或上下文限制时，即使子 Agent 已成功完成，主 Agent 仍无法确定内容是否完整，也
无法继续执行 Schema 校验、Evidence Reference 核验、平台 dry-run、独立评审、Lease 和 apply。
为了避免残缺数据进入 Ontology，本次运行只能安全停止，最终没有完成正式建模交付。

这次运行还暴露了以下连带问题：

- 主 Agent 曾把“产物没有被当前上下文保留”误判为“建模子 Agent 没有生成产物”，之后又从
  rollout 中恢复过一次结果，说明执行状态与产物状态没有被明确区分；
- 为恢复被截断的输出而重复读取日志、启动替代评审或重新运行模型，会增加 token、耗时和状态
  分叉，并可能产生需要追加更正的错误阻塞记录；
- repo-local Harness 能够捕获部分 PreToolUse/PostToolUse 和阶段事件，但旧 Harness 中断后只保留
  `interrupted/local_only` 原始记录，不能替代平台中的版本化模型草案和权威 Execution Events；
- 本次使用的 Dify 官方文档只由外部 Agent 在线读取并以 Evidence Reference 原文片段进入平台，
  仓库内没有可供另一 Agent 直接复用的完整官方文档离线副本。资料可恢复性和模型产物可恢复性
  需要分别处理，不能把 Evidence Reference 摘录描述成已下载完整资料。

### 目标行为

建模子 Agent 生成的完整结构化结果必须先写入一个可寻址、可校验、可恢复的受控产物通道，再向
主 Agent 返回简短交接信息。PTY、聊天消息和终端展示只用于返回产物定位符、格式版本、内容哈希、
大小、项目数量和摘要，不再作为完整 Modeling Draft 或 Modeling Batch JSON 的唯一载体。

首选路径是在 Runtime 提供的受控工作目录中原子写入结构化文件，由主 Agent 读取、校验并持久化为
版本化 Modeling Workflow Artifact；若平台提供符合角色权限边界的受控 Artifact 上传通道，也可
直接返回 Artifact ID。无论采用哪条路径，都不得让建模子 Agent 获得 Ontology Lease 或执行 apply，
正式写入仍只能由主 Agent 在全部质量门禁通过后完成。

可靠交接至少包含以下合同：

- 使用临时文件加原子重命名或等价机制，避免主 Agent读取到尚未写完的 JSON；
- 产物具有稳定定位符、内容格式与 Schema 版本、字节数、项目数和强内容哈希；
- 子 Agent 完成后只在标准输出返回有界的交接清单，不复制完整大 JSON；
- 主 Agent 必须重新读取完整产物，验证文件存在、大小、哈希、JSON 解析、Schema、客户端标识唯一性、
  Evidence Reference 可访问性以及必要的跨项引用，再创建平台 Draft Artifact 和 Modeling Batch；
- Build Checkpoint 和 Modeling Execution Event 分别记录“生成是否完成”“交接是否完成”“校验是否
  完成”和稳定产物引用，不能把传输失败记录成模型生成失败；
- 主 Agent 或 Runtime 中断后，新的 Agent 能从 Build Context、Execution Events 和稳定产物定位符
  恢复，不需要重新调用建模模型，也不依赖从截断的 PTY 或 rollout 文本中猜测和拼接 JSON；
- 若完整性、哈希或 Schema 校验失败，流程必须失败关闭并保留明确 blocker，不得 dry-run、评审或
  apply，也不得自动制造多次无边界重试；
- 受控产物不得包含密钥、Lease token、Authorization header、隐藏推理或不必要的完整对话；临时
  文件的权限、保留和清理规则必须明确。

### Dify 资料输入边界

本需求首先解决建模产物交接，不能用“先下载整个 Dify 站点”掩盖输出链路问题。Dify 官方资料可
继续由外部 Agent 在线读取并提交精确 Evidence Reference；如果为了可重复验收需要本地资料集，应
单独保存一份有来源 URL、抓取时间、文档版本或更新时间、许可说明和内容哈希的受控快照，并明确
它只是验收输入，不是平台通用来源采集能力，也不是最新官方文档的永久替代品。

### 验收标准

- 使用本次 Dify 场景规模不小于 v2 的 27 项结构化候选模型完成交接；即使终端输出被主动限制或
  截断，主 Agent仍能从受控产物取得字节完整、哈希一致且通过 Schema 校验的 JSON。
- 子 Agent 标准输出只包含有界摘要和产物定位信息；验收能够证明完整草案不依赖 PTY、聊天上下文
  或 rollout 日志回捞。
- 在“子 Agent 已生成但主 Agent 在读取前中断”和“主 Agent 已读取但尚未持久化平台 Artifact”两种
  故障点上，新的 Agent 均能识别准确阶段并继续，不重新生成草案、不重复评审、不重复创建 Batch。
- 完整性或 Schema 校验失败时，平台中只出现准确的 blocker 和追加式更正记录，不申请 Lease、
  不执行 apply；修复后可以沿同一 Build Session 继续。
- Modeling Draft、Modeling Batch、dry-run Attempt 和 Review Artifact 之间能够通过稳定 ID、哈希和
  supersedes 关系追踪，平台 Execution Events 仍是权威记录，repo-local Hooks 只作为补充复盘。
- 交接链路通过秘密扫描和权限检查，不在文件、终端、事件或回顾文档中泄露管理密钥、Lease token
  或其他凭证。
- 修复后重新执行 Dify 基础功能场景，完成 Draft 持久化、dry-run、独立评审、必要返工、主 Agent
  apply、能力问题查询、validation 和 lineage 验收，并正常完成 Build Session。
- 若建立 Dify 本地验收资料集，能够列出快照文件、原始官方 URL、抓取时间和内容哈希；若未建立，
  文档和执行记录必须明确资料仍为在线读取加平台 Evidence Reference 摘录，不得声称已离线下载。
