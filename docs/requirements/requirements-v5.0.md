### R5.0-001 可控编排与有界 Agent 执行

**目标**：将流程控制变为可检查、可测试的程序行为；Agent 在有界目标和权限下作语义判断。

- **F1** 明确执行位置、正在处理的工作单元、下一项依赖、首阻塞与所需输入；程序负责已确定的路由、等待、结果归属和恢复，Agent 提供需要推理的判断及理由。
- **F2** 在 LangGraph 编排下使用有界自定义 Agent，执行基础暂定 Codex harness；优先验证官方 Python Codex SDK，必要控制使用 app-server 公开协议，不要求继承旧适配器。输入、工具与输出有明确合同，执行器内部会话与外层业务流程职责分开。实际 SDK／CLI、provider、模型、effort、工具行为及用量必须核对，不因默认值静默改变配置。最终采用以 F8 验证为据。
- **F3** 每个有长等待需求的工作单元可独立暂停与接续；无关工作继续。程序不因普通心跳、日志增长或计时到期无条件唤醒模型。
- **F4** 用户输入、暂停／停止、预算变化与关键事件即时登记，目标忙碌时排队，当前原生 turn/activity 自然结束后处理，沿 R4.4-002／003 的 2026-10-22 最新规则。下一原生回合开始前检查控制及预算；已开始回合内的工具后续、重试、压缩和获准应用允许自然完成并计量，尾差如实披露。queued、delivered、consumed 与 effective 分开；所有在途成员可核对停稳后才报告任务已暂停。正常控制不对 busy turn 使用 steer／interrupt；即时中断能力不成为当前默认暂停的前提。
- **F5** 执行控制与业务状态分离；错误、字段缺失、暂时等待和技术运行上限允许准确修正及继续，不因角色数量或固定尝试数永久终止目标。
- **F6** 不保留常驻 Delivery LLM 作为机械推进或转交用户的必需条件。Agent 的人工请求由程序 HITL 通道直接呈现给用户，答复直接关联原请求及工作单元；确需推理的语义协调可由有界助手承担，但不成为提问、答复或恢复的必经中转。该项是 v5 对旧职责合同的目标调整，实施时同步活跃提示与工具入口。
- **F7** 业务工作单元、一次执行尝试、LangGraph thread、Codex thread／turn、平台操作与原预算可明确关联。恢复先核对原执行、业务版本和实际副作用；不因节点重执行就重复启动仍在运行或状态未知的有副作用工作。完成本次 Agent 工作不自动证明业务收口、应用或独立验收通过。

- **F9** 动态 HITL 同时覆盖 Agent 按实际需要发起的业务澄清／决定请求，以及用户主动补充、纠正和任务控制。请求保留稳定身份、原工作单元／步骤、相关内容版本、问题、依据及影响范围；答复保留主体、来源与适用范围。人工等待采用持久工作流等待点，当前 Codex 原生回合自然结束后进入等待或消费新输入，不使用原生 steer／interrupt 实现日常人工介入。答复只恢复或重审匹配部分；未答复、部分答复、版本已变化均保持准确状态，不自动选默认含义。重启后可定位原请求、答复和待恢复点，不重复提问、消费或已确认应用；只挂起依赖该输入的部分。无需人工判断的正常步骤不增加固定审批。

### R5.0-005 分层总览与增量认知维护

### R5.0-006 独立语义验收与冻结交接

**目标**：新流程不降低生产与评价的独立性，并支持大型业务分层评价。

**验收**：隐藏材料不流回生产；评价无修改能力；旧报告、追加报告和新模型结论绑定准确；模型直接消费与摘要辅助消费分别报告，不能互相代替。

  仅借鉴思想的部分，记录依赖、许可、集成成本与取舍，不预设整体引入其技术栈。
- **F2 — Schema 材料组织。** 研究将表、列、键、约束、注释及获准样本证据组织为
  可定位、带来源／版本且可按需读取的材料。通过既有工作空间保留已知结构与待确认
  业务含义，支持与业务文档、术语和澄清对应；业务行继续留在外部数据库。
- **F3 — 候选生成与跨材料理解。** 研究概念、属性、关系、编码含义和未决问题的
  辅助发现与整合。Schema 和样本用于提出、支持或反驳假设，不自动证明业务身份、
  粒度、基数或规则；冲突和未知保留，必要澄清进入现有 HITL。允许跨表概念及同表
  多种业务角色，不将“一表一个概念”或表数固化为工作单元／Ontology 的划分规则。
- **F4 — 关系、指标与映射。** 借鉴外键、桥接表、连接路径及已有 SQL／查询历史的
  处理方法，研究复用关联方向、物理定位、记录粒度、指标表达式、单位、时间、过滤、
  聚合和空值口径。覆盖连接基数、重复计数及错误重聚合，明确哪些有业务依据、哪些
  仍为候选；语义资源沿现有数据映射合同表达，不为参考场景加入平台专有业务逻辑。
- **F5 — 消费反馈与质量验证。** 研究可回答性、语义检索、实际 SQL 和结果检查如何
  帮助发现遗漏、歧义与错误映射。Consumer 仍先取得获准语义上下文，SQL 执行成功
  不等于业务问题已正确回答；模型自查与独立语义验收分别记录，不扩展外部执行适配器
  的业务数据授权或查询网关职责。
- **F6 — 有界对照与完整成本。** 优先复用已有获准场景和测试模式，形成同范围、
  同 Schema／业务材料、同模型／effort 及评价条件下现有流程与借鉴流程的对照计划。
  检查概念／关系／映射正确性、材料覆盖、未知与冲突保留和实际消费效果，同时统计
  候选生成、澄清、检索、修正、验证的总 token、调用与耗时及成本转移。额外 SQL
  示例或值锚点的贡献单列，外部 Host 用量沿现有口径单列，不据局部耗时或厂商数字
  承诺净收益。
- **F7 — 最小落地建议。** 输出方法对照、可复用点、职责映射、推荐改进及其取舍、
  未决项和有界验证计划；选出最值得落地的少量改进，再同步到所属需求和实施阶段。
  具体存储、工具、提示或流程变化以研究结论为据，不先扩建独立建模系统。

完整 Demo 语义验收、Judge 通用可靠性或净降耗通过。

| 子阶段 | 本段交付 | 本段通过依据 |
| --- | --- | --- |
| **P1.1 最小建模流程** | 将已验证接入整理为 v5 入口，从一条有界业务输入，经 Agent 建模、真实应用、治理读回到独立评价；持久保存最低限度的来源、候选、工作及应用引用。 | 同一小范围真实链独立通过；不依赖全项目记忆、动态 HITL 或完整上层方法重写。缺失业务输入仍须准确等待，不得猜测。 |

P0 后先推进 P1.1，再按 P1.2→P1.3→P1.4→P1.5 逐段集成；每段可以独立交付，后段不成为前段验收前置，前段的局部 PASS 也不替代后段证明。底层版本、身份、输入控制与写入安全从首次真实链就保留，完整上层建模逻辑在 P1.4 收口；P2 的递归并行与跨单元整体规则、P3 的增量和分层总览仍由原阶段承担。详细拆分与决策见改造计划 §6、§9。

默认入口切换前，在当次获准范围和预算内至少完成两次达到同一冻结业务标准的独立完整运行，并包含持久接续，分别报告 L1 与 L2；这不成为生产尝试次数守卫。完整版本还须覆盖 R5.0-001—007 的必需行为和方法验证条款，以及 R5.0-008 的研究交付；008 选定的落地范围同步到对应主线阶段，不要求实现全部候选方案。原型、小链或局部 PASS 不关闭未验证范围。维护性、净成本和质量分别报告，无法证明收益时保留未验证，不编造比例。

验收沿 `L0 Runtime`、`L1 Modeling quality`、`L2 Repeatability`、`L3 Productization` 分阶段，后一阶段不成为前一阶段前置门。真实建模一经获准，按仓库要求在 20 分钟内进入第一次真实 semantic modeling start，不用扩大框架准备来推迟。任何真实效果结论都需匹配当前代码、配置、材料和实际运行证据。
