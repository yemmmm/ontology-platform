## 本次讨论的范围与边界

- 面向通用业务场景，从对象、行为、规则、角色、流程等视角建模；同一业务定义通过稳定身份
  和明确关系复用。视角与业务切片是两个维度，不据此固定 Ontology 数量或 Agent 数量。
- 增加数据映射与接口映射视角，分别连接外部数据库和外部 API；共同引用已确认的业务定义。
  独立分析职责、模型产物与验证内容，不要求每个视角单独存储或配置 Agent。
- Ontology 作为语义层，实际业务动作由外部系统执行。业务行与运行记录仍保留在外部系统，
  不要求增加流程执行引擎；平台已有的图校验、推理与实际业务执行保持区别。
- 规则需要保留脚本形式及自然语言说明，供外部 Consumer 理解和使用；脚本语言与执行约定尚未确定。
- 业务角色描述职责，平台权限控制语义可见范围；二者可显式关联，授权仍由管理面确认。
- 本次不考虑页面位置、颜色、折叠状态等视图配置，也不引入面向软件生成的 UI 模型。
- v4.0 阶段性停用证据追溯并解除建模、检索和验收主流程对它的依赖；建模 Agent 不承担
  证据留存职责，具体范围与验收约束见 R4.0-012。

### R4.0-002 多视角语义组织与共享定义

状态：2026-10-01 用户已授权按 F1—F6 与 A1—A7 开发及功能测试；需求细化独立审阅
Round 2 PASS（0 Critical／0 High）。功能开发及开发验证通过，A1—A7 独立功能验收 PASS；
A8 真实建模和独立语义验收未授权、未执行，整体 PARTIAL。

**目标与范围**：围绕对象、行为、规则、角色、流程组织业务语义；不同视角引用同一份已确认
定义，不分别维护相互脱离的模型副本。明确对象类别、属性、关系和业务角色职责；需要共性时
使用分类，同名不直接认定为同义。业务含义、适用范围和未知项应能随资源及关系读取。
各视角保留可供大模型理解的自然语言说明，并与结构化语义关联。

以下条目已由本次开发测试授权纳入实施范围；沿用后续统一真实语义验收安排。
重点关联风险 K1、K2、K7。

#### 1. 最小范围与术语

以“工单”为例：对象视角说明工单是什么及其属性，流程引用该定义描述处理对象，数据和
接口映射也引用该定义描述外部表示。不能因出现在不同视角就创建几份互不关联的“工单”。
流程同时出现“原工单”和“返修工单”时，二者可以引用同一个工单类别，但调用上下文必须
区分；这种区分不自动产生新类别，也不意味着把两张实际业务工单写入语义层。

| 概念 | 本条含义与边界 |
| --- | --- |
| 视角 | 分析和组织业务语义的关注点，包括对象、行为、规则、角色、流程、数据映射、接口映射；不等同于 Ontology、逻辑切片、Agent 或权限边界 |
| 语义角色 | 某项内容表达的是对象定义、行为定义、规则、业务角色、流程或映射等何种业务语义；读取方应能识别，不等同于平台存储类型或权限角色 |
| 共享定义 | 业务含义和适用范围一致、被多处引用的同一语义定义；名称相同不足以证明应当共享 |
| 局部含义 | 某个业务上下文中的用途、责任或限制；必须能辨别其适用上下文，不能静默覆盖共享定义 |
| 对象类别 | 已确认的业务共性；承接 R3.0-009，按实际需要选择普通业务分类或正式 Class，不因出现一个名词就建立 Class |
| 业务角色 | 对业务职责和参与关系的描述；不等于实际用户、API Key、建模 Agent 角色或授予权限的管理面角色 |

本条先确定各视角共同使用的语义组织约定，并细化对象、属性、关系、分类和业务角色职责。
其他视角在本条中只确定共享引用边界，其专属表达由对应需求细化。

#### 2. 功能要求草案

**F1 — 共享身份与明确引用**

- 同一获准 Project 范围内，已确认含义与适用范围一致的定义使用同一稳定身份；在不同视角、
  逻辑切片或获准 Ontology 中引用时，不另建只因展示位置不同而产生的副本。
- 候选中的语义身份和物化后的资源 IRI 应可明确对应；不能由 Modeling Agent 猜测平台 ID，
  也不能仅凭同名、别名或相似描述自动合并资源。沿用现有 Protocol 翻译与回执绑定职责。
- 含义不同的同名定义保持独立，并说明差异或范围；是否同义尚未确认时保留未知，不默认合并。
- 不增加跨 Project 共享、全局定义注册中心或自动实体消歧服务。稳定身份也不替代版本兼容判断，
  共享定义变更及引用重审流程归 R4.0-007。

**F2 — 对象、属性与关系的最小业务含义**

- 对象定义能读取名称、业务含义及适用范围；属性说明其值代表什么，关系说明两端含义、
  方向及适用范围。必要的单位、取值或多值含义应明确，未确认部分保持未知。
- 结构化关联应能解析到所引用的定义；自然语言说明用于解释含义，不能用一段同名文本替代
  本应明确的对象引用，也不从数据库字段名自动生成已确认的业务定义。
- 只表达语义知识、受控参考值和映射意义，外部业务行仍留在外部系统。

**F3 — 分类与局部差异**

- 继承 R3.0-009：语义节点可以没有正式 Class，也可以有多个正式 Class；普通业务分组、
  正式类型成员和子类关系必须区分。不得把“同一视角”自动解释为共同业务类别。
- 只有明确的集合包含含义才使用正式子类关系；状态、合同和场景差异不自动变成子类，
  已确认的稳定类别仍可采用分类。Action 的子类适用和条件差异交 R4.0-003 细化。
- 可共享的定义与特定上下文中的用途、附加条件分别表达；局部说明不能悄悄重写共享含义。
  如果差异改变了定义本身，应作为独立的有范围定义处理；不确定时标明待确认。
- “属于同一类别”不能证明是同一对象引用。原工单／返修工单等调用位置及参数绑定的具体
  表达归 R4.0-004，本条不预定调用节点、变量或绑定语法。

**F4 — 业务角色与职责**

- 业务角色具有可引用的身份和职责说明，并通过明确的业务关系关联其负责、参与或审核的
  业务内容；关系表达的职责含义需可读，不强制所有场景使用相同职责清单。
- 同一业务角色跨流程或视角使用时沿用共享定义；局部职责需保留适用上下文。
- 创建业务角色或职责关系不会授予语义读取或外部执行权限。用户／Key、权限角色、Grant
  及业务角色的管理面映射归 R4.0-006，不由本条引入。

**F5 — 说明、范围和未知项可读**

- 对象、分类、属性、关系和角色定义的自然语言说明须与对应资源或关系明确关联；范围和
  未知项在获准读取时能够取得，不只存在于 Agent 对话或未交付的分析文件中。
- 在授权可见的模型内容中，已知冲突不静默任选一份解释，缺少说明、显式未知和明确不适用
  应保持区别。未返回某项内容仅表示当前获准结果不足以确认，不能据此推断不存在约束或职责。
  本条不增加语义评分器或要求平台自行判断业务同义。
- 无权资源继续遵循 [R3.0-004](requirements-v3.0.md#r30-004-主体绑定的语义知识访问控制)
  的不可区分合同：精确请求与真实不存在返回相同的 404／空结果；宽查询在分页、计数、排序和
  cursor 计算前无痕过滤。不新增资源级“无权读取”状态、提示或其他存在性信号。
  既有 Project 边界及 SPARQL scope 错误合同保持不变。
- 复用现有受治理资源读取和关系读取作为最小验证路径；跨视角自动召回、上下文组装和
  专门筛选能力归 R4.0-008。
- 继承 R4.0-012：不增加 Evidence、lineage、来源摘录或逐资源补证义务；业务资料忠实度和
  独立语义正确性要求继续生效。

**F6 — 读取时识别语义角色（用户已确认的目标）**

- 读取模型时，Consumer 应能明确识别相关内容表达的是对象、行为、规则、业务角色、流程、
  数据映射还是接口映射。不能要求仅凭名称、所在页面或 Agent 曾经的对话猜测。
- 例如“工单”是对象定义，“关闭工单”是行为定义，“允许关闭的条件”是规则定义；三者
  通过含义明确的关系关联。工单被流程或接口引用后仍是同一对象定义，不因此变成流程或接口。
- 实现建议：通过明确、可读取的语义声明表达上述区分，并关联自然语言解释。具体可采用
  现有类型、关系或其他合适的语义表达，由详细设计核对；业务语义角色不要求与平台内部
  resource kind 一一对应，也不强制全部内容新增正式 Class。
- 本次确认的是读取方能识别业务含义，并未决定额外的“视角标签”字段、固定七类平台资源、
  互斥分类或任意多标签机制。同一资源是否承担多种语义角色，按其已确认业务含义决定，
  不能把“被多个视角引用”直接当成“具有多种角色”。
- 本条先形成共同表达约定并验证对象／分类／业务角色的适用路径。Action、流程、规则和映射
  的专属合同在对应需求中接入同一约定；不要求在 002 中提前实现其全部专属结构。

### R4.0-003 可复用业务 Action 与外部能力关联

状态：需求细化完成（2026-10-01）；D1—D3 由用户明确确认，D4 按用户的决策授权采用。
独立需求审阅 Round 1 PASS（0 Critical／0 High）。本轮用户已授权开发和测试，功能开发与
开发验证完成，A1—A9 独立功能验收 PASS；A10 未授权、未执行，整体 PARTIAL。设计表达与
实现选择、验证及清理证据见[交付记录](../delivery/records/2026-10-01-r4-0-003-action-semantics-delivery-record.md)
及[独立功能测试记录](../delivery/test-plans/2026-10-01-r4-0-003-action-semantics-test-plan.md)。不启动真实建模或外部业务调用。

**目标与范围**：从行为视角定义可复用业务 Action，描述适用对象、输入输出、前置条件、
预期业务效果及角色关联，供不同流程引用。业务 Action 与外部可调用能力 Operation 分别定义，
通过明确关系关联；人工动作或尚未接入系统的动作也可独立成立。重点关联风险 K1、K2、K6。

#### 1. 最小范围与术语

以“关闭工单”为例：Action 描述关闭的业务含义、处理对象、条件和预期效果；某系统的关闭
接口由 Operation 及 Tool Binding 描述。人工关闭也可以具有完整的业务定义。某流程两次
关闭不同工单时，引用同一 Action，但各次调用的对象与参数绑定由 R4.0-004 表达。

| 概念 | 本条含义与边界 |
| --- | --- |
| Action | 可复用的业务动作定义；有稳定身份、含义与适用范围，不以已有外部接口作为成立条件 |
| Operation | 外部可调用能力的语义描述，沿用既有目标类型、参数、声明式条件和效果、工具绑定等合同；不因关联 Action 而与它成为同一资源 |
| 适用对象 | 动作在业务上针对的对象定义或类型；不等于某次调用的实际业务对象 |
| 业务参数 | Action 定义中的输入或输出位置，具有可区分的身份和业务含义；同类对象可以承担不同参数角色，不是数据库行或流程调用变量 |
| 前置条件 | 动作在某适用范围内成立或允许执行所需满足的业务条件；类型适用本身不证明某次调用已经满足条件 |
| 预期效果 | 动作在声明的成功或其他结果条件下应带来的业务变化；不表示该变化已经发生，也不等同于接口返回字段 |
| 外部能力关联 | Action 与已确认的 Operation 之间可读取的明确关系，说明对应含义和适用范围；不自动表示能力之间等价或有调用顺序 |

继承 R4.0-002 的共享身份、共同语义声明、Class 可选、自然语言说明和未知项约定。
本条不预设新的平台资源类型、表、路由、Ontology 或 Agent；实现表达由详细设计确定。
实际业务行、调用和运行记录仍在外部系统，平台不增加业务执行引擎。

#### 2. 功能要求

**F1 — 独立的业务动作定义与共享引用**

- Action 具有稳定身份、名称、业务含义和适用范围，并接入 R4.0-002 的共同语义声明，
  使读取方能识别其表达行为定义。不同流程或获准视角引用同一已确认动作时不复制定义。
- 业务含义不同的同名动作保持独立，未知是否相同的动作不得按名称自动合并。
- Action 可以没有 Operation 关联；人工动作或尚未接入系统的动作不因此被判为无效，
  也不要求填写虚假工具绑定、凭证需求、接口风险或幂等性以满足 Operation 的合同。
- Action 与 Operation 保持分别可识别的身份。已有活动 Operation 的工具绑定要求继续
  生效；Operation 的执行风险、幂等性和凭证需求不能未经业务确认成为所有关联 Action 的属性。

**F2 — 对象适用、子类与局部条件**

- Action 明确引用其适用的业务对象定义；不强迫对象定义具有正式 Class。
  对普通业务分组不自动推导正式子类或类型继承。
- 当 Action 关联正式 Class 时，默认适用于其子类；类型关系及该动作的共同条件应能
  通过获准读取辨明，不要求在每个子类复制动作或条件，也不据此新增业务执行判定器。
- 子类保留共享动作的共同前置条件，局部限制在其明确适用范围内追加，并与共同条件
  同时满足。例如维修工单关闭时既需“已验收”，也需局部的“维修报告已提交”。
- 稳定特殊类别可按业务共性建立中间类并关联动作；状态、合同或场景条件不自动变成类别。
  某类工单若确实免验收，应明确修订共同条件的适用范围，或在动作含义确实不同时定义
  独立动作；不允许子类静默取消共同条件，也不引入自动覆盖或例外优先级。
- 多分类对象涉及多个适用限制时，不自动选取更宽松的一份；已知冲突保留可读的范围与
  冲突说明，业务判断由建模及独立语义验收完成，不要求平台理解文本后裁决业务冲突。
- 实际调用是否满足条件由外部消费或执行方结合业务数据判断。平台返回动作定义不表示
  已满足条件、已被授权执行或业务动作已经发生。

**F3 — 结构化输入输出与业务参数身份**

- 输入输出以可区分、可引用的业务参数表达，至少明确名称及业务含义、输入／输出方向、
  对象引用或值类型、必填性或结果出现条件、单值／集合含义；未确认的内容显式保留未知。
  已确认的单位、枚举及缺失含义随相应参数读取，不从字段名猜测。
- 参数关联对象、属性或共享定义时使用明确引用；“保留工单”和“待合并工单”即便引用
  同一对象类别，也必须保持不同参数身份。参数身份不代表两个实际对象必然不同；确有
  “不可是同一工单”等限制时应作为业务条件声明。
- 输出应说明其代表的业务结果。已确认是某输入对象的更新结果、新对象或计算值时，
  保留该含义及必要的参数引用；未确认时不能推定新建对象或默认覆盖输入。
- 支持明确表达无业务输入或无返回值；无返回值不代表无业务效果，未提供输出说明也
  不能被解释为明确无输出。声明参数不要求将实际参数值或业务记录写入 Ontology。
- 本条定义可供后续引用的参数合同；流程中的实际对象、参数来源、前序输出、循环变量
  和集合遍历绑定归 R4.0-004。外部请求响应字段与参数的映射归 R4.0-011。

**F4 — 可解释的条件、效果与职责**

- 前置条件、预期效果分别记录自然语言说明和适用范围，明确关联涉及的参数、对象、
  属性或已建模的共享规则，不仅存放在 Agent 对话中。
- 本期不要求所有条件和效果具有机器可计算表达式；引用共享规则时保留可解析关系，
  规则分类、脚本、输入输出及说明一致性由 R4.0-005 细化，不为本条预设脚本语言。
- 效果明确其成立的结果条件，例如“成功关闭后工单状态为已关闭”；只保存动作定义或
  关联 Operation 不会自动写入“该工单已关闭”的业务事实，也不触发状态推进。
- 已知的拒绝、失败或部分完成情形影响结果含义时应说明；未确认部分保持未知，不要求
  枚举所有可能运行故障。结构化输出、自然语言效果之间的已知冲突不得静默任选一份。
- 负责、参与或审核等职责通过明确业务关系关联共享角色定义，保留局部职责的适用范围；
  职责关系不授予语义读取或外部执行权限，管理面角色映射归 R4.0-006。

**F5 — 与外部能力的明确关联及范围**

- 一个 Action 可以关联零个、一个或多个已确认的 Operation；不强制一对一，也不要求
  外部能力只能被一个业务动作引用。每项关联保留可读取的对应含义和适用范围。
- 关联多个 Operation 仅表示存在多项能力关联。只有在业务上确认可替代且适用条件明确
  时才声明可选实现；不能从相同名称、接口路径或共同目标类型推导等价。
- 需要多个能力组合才能完成一个动作时，不将每个步骤误标为独立完整实现。003 保留关联
  的已知含义及缺口，组合调用、顺序与数据依赖归 004，参数映射和接口版本归 011；本条
  不建设能力选择器、调用编排器或外部执行适配器。
- 接入、更换或解除外部能力关联本身不改变共享 Action 身份和业务含义；如果实际改变了
  输入输出、条件或业务效果，应作为业务定义变更处理，不能仅凭稳定 IRI 宣称兼容。
  本条不新增版本固定或自动兼容判断机制，变更影响与引用重审归 R4.0-007。
- Operation 的条件、效果与 Action 的业务定义分别保留，关联不自动证明二者一致，也
  不覆盖任一方的含义；已知对应冲突或尚未确认之处随关联说明读取。
- 不保存真实凭证，不授予外部业务调用；平台只描述与检索这些关联。

**F6 — 候选、写入与受治理读回**

- 候选、Protocol 翻译、平台命令、RDF 和读回需承接本条实际语义增量；不能要求 Modeling
  Agent 自行追加合同不支持的字段，也不能只改提示而使输入输出或关联在物化后丢失。
- 复用现有稳定身份、通用资源和关系、Batch dry-run／apply 及受治理读取。通过现有
  资源详情和关系读取应能取得动作、参数、条件／效果及适用关联，不要求 008 的自动
  跨视角召回或专门上下文组装先行完成。
- 正式 Class 可选的 Action／对象路径不得被 Operation 现有目标 Class 要求间接阻断；
  Operation 继续按自身合同验证，二者关联不等于继承彼此的平台字段要求。
- 无权资源继续遵循 R4.0-002 F5 与 R3.0-004 的不可区分合同：精确读取与不存在资源
  返回相同的 404／空结果，宽查询在分页、计数、排序和 cursor 计算前无痕过滤；不返回
  隐藏参数、规则或 Operation 的引用、名称及资源级拒绝提示来暴露其存在性。
- 在获准可见内容中区分缺失说明、显式未知与明确不适用；获准结果未返回条件或外部能力，
  不能被 Consumer 解读为没有约束或没有实现。不增加新的视角权限边界。
- 继承 R4.0-012 的追溯停用约束，不新增 Evidence、lineage 或逐资源补证要求；保留
  dry-run／apply 完整性和必要恢复机制。说明中复制敏感语义的风险沿用 K5，不把 IRI
  过滤描述为自动防止文本泄露的能力。

### R4.0-004 流程语义、动作调用与参数绑定

状态：需求细化与详细设计中（2026-10-01）。用户授权本轮需求和设计工作，Agent 对选择有
超过 85% 把握时可以自行决策；其余交用户决定。D8 待确认；其余决策见下表。未实施，未做
独立审阅、功能验收或真实语义验收。本次不启动真实建模、业务调用或流程执行。

**目标与范围**：流程组织可复用 Action 的调用；明确每个调用点的处理对象、输入来源、输出
去向、先后顺序、条件分支及循环。Consumer 从获准模型内容能解释“在什么上下文中，哪个
动作使用哪个对象与值，产生的结果供哪里使用”，不能靠同名、同类或列表位置猜测。
继承 002 的共享身份和语义声明、003 的动作与参数合同、012 的追溯停用范围。重点风险 K2、K6。

#### 1. 最小范围与术语

例如：流程先处理“原工单”，再处理该次处理产生的“返修工单”，之后分别调用同一个
“关闭工单”Action。两个关闭调用引用同一 Action 和同一输入参数定义，但绑定不同的对象
引用；“返修工单”来自哪个调用的哪个输出必须明确。模型保存这一业务安排，不保存实际
工单行、调用实参、每次循环记录，也不表示关闭已经发生。

| 概念 | 本条含义与边界 |
| --- | --- |
| 流程定义 | 有稳定身份、业务目的、适用范围、输入输出和步骤关系的语义定义；不等于流程运行 |
| 调用点 | 流程中一次使用某个 Action 的位置；不同位置有不同身份，同一位置在循环中多次执行不复制定义 |
| 参数定义 | 003 定义的 Action 输入／输出位置；流程自己的输入输出也具有明确身份；不是调用值 |
| 值引用 | 某个流程或局部作用域内的对象／值位置，例如流程输入、指定调用的输出、循环当前项；不是实际业务行或运行变量值 |
| 参数绑定 | 某调用的某输入参数从哪个值引用取得内容，或流程输出来自哪个值引用；绑定具有明确上下文 |
| 转移 | 从一个步骤到另一处步骤或终点的流程关系，按需附条件、结果或局部说明；不是实际运行事件 |
| 局部作用域 | 某流程、分支或循环中引用成立的上下文；不等于 Ontology、Project、权限边界或新 Class |

Class 继续可选。同类值引用可指向不同实际对象，也可能是同一实际对象；只有已确认的业务
规则才能声明相同或不同。不同引用身份本身不证明两个对象不同。

#### 2. 功能要求

**F1 — 共享动作与调用位置分离**

- 流程及调用点均有稳定、可引用身份和可读含义。每个业务调用点明确引用一个 Action；
  同一 Action 可被多个流程或同一流程多个位置复用，不复制或局部改写共享定义。
- 调用点明确所属流程及必要的分支／循环上下文。显示名称、编号或数组顺序不能代替身份
  与流程关系；调整展示顺序不得改变业务先后关系。
- 调用点的职责、局部限制和结果说明保留其适用范围，并引用共享角色／规则。共同前置条件
  继续生效，局部条件只能按 003 已确认约定追加，不能通过流程分支静默免除。

**F2 — 明确值来源与参数目标**

- 绑定分别指出调用点、目标参数定义和来源值引用；目标参数必须属于该调用引用的 Action。
  流程输出绑定指出所属流程及对应输出定义，不能把 Action 的输入和输出方向混用。
- 本期覆盖流程输入、指定调用的指定输出、明确对象引用的属性、已确认的语义常量和循环
  当前项。值引用指向共享对象／值定义，并说明单值／集合和必要的单位、枚举、缺失含义。
- 指定调用的输出由“调用点身份＋输出参数定义”区分；仅引用共享 Action 的输出参数不能
  区分两次调用。对象属性来源同时引用对象位置及属性定义，不用 `工单.编号` 文本代替。
- 属性多段访问须逐段明确对象来源与属性／关系方向及集合含义。本期不增加通用表达式语言、
  SQL／JSONPath 解析器或脚本求值器；必要转换引用可解释的规则或转换定义及其输入输出，
  计算与接口字段映射分别交 005／011。不能用自由脚本掩盖缺失的来源关系。
- 明确常量限于业务语义或受控参考值；不得以常量绑定保存真实凭证、业务行快照或运行实参。

**F3 — 缺失、结果条件与流程输出**

- 区分未说明、显式未知、明确不适用、明确无输出，以及仅在特定结果下出现的输出。复用
  003 的参数结果含义，不能将无返回值解释为无业务效果。
- 在完整的调用说明中，每个必填输入有明确来源或显式未知；条件性必填按已确认条件表达。
  可选输入未绑定时说明省略含义；未知可作为已披露缺口交付，不能据此宣称可执行或绑定完整。
- 仅在某分支、成功结果或循环迭代中产生的值不能默认为后续一定存在。下游需要明确适用
  条件、选择／汇总规则或已确认缺失处理；没有业务信息时保持未知，不自动取空值、首项或末项。
- 对流程结束及对外输出，明确其来自哪个调用／上下文及出现条件；成功、拒绝或部分完成等
  已知结果按业务资料记录，不要求枚举所有基础设施故障，不引入自动重试或补偿机制。

**F4 — 顺序、条件分支与局部判断**

- 流程入口、步骤转移和终点须可明确读取。控制先后关系与参数数据依赖分别表达；“使用某
  输出”不能自动补成一条流程边，图中有边也不能证明下游所需值一定存在。
- 条件分支的转移分别关联条件及必要的结果上下文。简单局部判断可有自然语言解释和明确
  参数／属性引用；可复用判断引用共享规则，不要求等待 005 的脚本合同完成。
- 已知的互斥选择、按优先次序选择、默认路径及无匹配结果按实际业务明确声明；平台不默认
  采用第一条，也不负责证明自然语言条件互斥或穷尽。未知选择方式必须可读。
- 多条替代路径回到共同后续步骤，只表示各路径可能到达；后续值采用哪一路结果需明确
  条件化绑定，不能将互斥路径返回同一步骤解释为等待全部路径完成。
- 并行分支与同步汇合是否进入本期由 D8 决定，未确认前不以替代路径或多条普通边冒充。

**F5 — 循环及迭代内外引用**

- 支持表达集合逐项处理和按条件重复的业务循环；明确所属流程、循环体、进入／继续／退出
  含义。条件循环需区分前置判断与后置判断，不能默认执行至少一次。
- 集合循环明确集合来源与当前项引用；当前项表示任意一次迭代中的对象位置，不创建实际
  集合成员、迭代实例或执行次数记录。嵌套时每层当前项的所属循环明确，不能只按名称解析。
- 循环内输出引用保留调用点、输出参数和迭代作用域。循环外消费应明确是结果集合、按已确认
  规则选择的结果或汇总值；循环零次、某次缺失／失败时的含义需声明或保留未知。
- 条件循环需要前轮结果作为下一轮输入时，明确初始来源、迭代结果与下一轮引用关系；不静默
  改写原输入。具体结果选择与转换仍是业务定义，平台不执行迭代、不判断终止性或调度策略。

**F6 — 外部能力组合的描述边界**

- 业务调用点首先引用 Action，人工／未接入接口的动作照常成立。已确认某处采用具体
  Operation 时保留明确关联；仅有关联不表示已获得调用权限、能力等价或全部前置条件满足。
- 一个 Action 需要多个 Operation 组合时，以该业务调用的局部实现上下文描述能力步骤、
  顺序及已知依赖；能力步骤不冒充独立完整实现，不改变共享 Action 身份。
- 004 负责组合上下文与依赖的表达；API 请求响应字段、Operation 内部参数位置及版本对应
  由 011 细化。未有稳定参数身份时，保留依赖含义与映射未知，不发明 JSONPath 或参数 IRI。
- 本条不增加外部调用器、能力选择器、运行记录或业务执行引擎；流程图不授予执行权限。

**F7 — 受治理读回、未知与修订**

- 候选、翻译、dry-run／apply 和读回需保留流程、调用、值引用、绑定、转移及作用域身份。
  现有资源、属性／事实与关系读取应能逐步取得这些内容；008 的自动组装不是本条前置。
- 所有资源引用以普通图关系承载，不将隐含 IRI 列表、参数路径或受限正文塞进不透明 JSON
  规避治理。无权与不存在遵循 002／003 及 R3.0-004 的相同 404／空结果合同，宽查询在
  分页、计数、排序前过滤；不返回“隐藏了一个参数／分支”等存在性提示。
- 获准模型中的显式未知与查询分页／截断分别表达；未返回的来源或条件不能解释为无约束、
  无输出或不存在绑定。只就实际可见内容作解释，不声明已获得完整可执行流程。
- 稳定身份不证明版本兼容。本期引用当前受治理定义，沿用既有图版本／读取状态；共享
  Action 或参数变更后的兼容判断、版本固定及跨引用重审机制归 007，不在 004 自动实现。
- 继承 012：不增加 Evidence、lineage 或逐项补证；保留写入回执、必要恢复和独立验收依据。

**F8 — 复用路径与校验边界**

- 优先采用已有普通节点、谓词、属性和关系，表达词汇属于语义模型，不增加固定流程平台
  资源类型、流程专用路由、执行存储或画布。本期设计详见下方链接。
- 候选必须使用实际支持的字段。合同校验、引用可解析性、确定性翻译、既有 Shape／授权／
  原子写入约束继续生效；错误定位到条目及字段，修正后可继续同一目标。
- 绑定对象是否正确、条件是否一致、输出在某路径是否可得等业务判断由 Modeling 和独立
  语义验收承担。可复用已声明 Shape 检查局部结构，但不新增流程编译器、全图执行模拟器、
  终止性证明或基于 Agent 数量／尝试次数的不可恢复硬门。

  Task／Skill、候选与交接产物、Protocol 翻译、工具合同、检索返回、页面入口和验收要求。
  不仅隐藏页面，还需解除正常建模与语义消费对追溯能力的依赖。
- 建模 Agent 不承担留存证据的职责；不要求摘录原文、登记证据、建立逐资源证据关联或整理
  追溯包，也不通过翻译、评审或交接间接向其追加补证任务。
- 未创建 Evidence 或未补齐追溯链不产生面向建模 Agent 的缺证告警、重试、返工或阻断，也不作为
  本期建模及语义验收的不通过理由。未采集状态不得伪装成已有证据支持或完整追溯。
- 仅服务于已停用证据要求的逻辑可以删除；与当前写入、检索及恢复共享的实现先确认
  耦合再确定删除范围，不把全量代码或存储删除作为本期完成条件。
- 当前项目没有真实数据，本期不考虑历史 Evidence／lineage 数据的读取、写入、迁移或回填，
  不提供历史只读接口、历史页面或为历史数据保留的兼容路径。此项取代本条先前的历史数据保留
  与读取兼容要求；不据此增加数据清理任务。

**边界**：业务资料与访谈仍用于确认语义和独立验收，未知项保持可见；不要求建模 Agent
另建证据包或为每项语义附加来源引用。参数输入来源、数据源与表字段映射、产生结果的规则等
属于业务模型内容，仍需正确表达。实际查询结果与业务依据仍须支撑独立语义验收结论，停用
Evidence／lineage 不豁免源忠实度和语义正确性。

写入回执、必要修改与恢复记录由现有平台或宿主机制负责，不转化为建模 Agent 的证据留存
任务。停用后的新写入仍须满足 dry-run／apply 完整性、授权、受治理检索和必要恢复要求。
本条改变 v4.0 的能力继承范围，不改写旧版本或历史运行的验收结论，也不授予真实建模额度。

**验收约束（已确认）**：

1. 在不提交 Evidence、不依赖追溯查询的条件下，完成一个真实场景的多视角建模、写入、
   关联检索和独立语义验收；追溯缺失不阻断该流程。
2. **建模 Agent 不感知需要留存证据**：检查实际下发的 Task／Skill、产物模板、工具说明及
   输入输出、评审反馈和交接要求，均不向其提出证据留存或补齐义务；Agent 无需理解
   Evidence／lineage 合同、填写证据字段或调用证据与追溯工具即可完成建模。运行中不因
   缺少证据收到补证任务，不由宿主临时提示绕过旧要求来满足本约束。

**确认状态**：停用主流程依赖、建模 Agent 无证据留存职责、不考虑历史数据读写，

确定，不要求用户逐项批准技术细节。

#### 1. 停用对象与保留内容

本条停用平台的证据追溯产品能力，不按代码、字段或目录是否含有 `evidence`、`lineage`、
`provenance` 字样决定删除范围。具体分类如下：

| 内容 | 本期处理 |
| --- | --- |
| Evidence Reference、原文摘录、逐资源／事实证据绑定、证据覆盖率、缺证状态 | 从正常建模、写入、检索、页面与验收合同中移除；不要求生成或补齐 |
| 完整来源链、推导前提追溯链、专用 lineage／provenance 查询 | 解除主流程依赖，不以链条完整性判断本期建模成功；按 D1 停用专用接口，按 D2 停止纯追溯采集 |
| 业务资料、访谈回答、业务定义、语义说明、未知项 | 继续用于理解与验证语义；不要求把资料逐条复制成平台 Evidence 或候选引用 |
| 参数输入来源、数据源及表字段映射、接口映射、规则与结果的业务关联 | 作为业务模型内容保留，不能因为名称包含“来源”或“依据”而删除 |
| 资源身份、所属 Project／Ontology、图与版本、asserted／derived 及结果过期状态 | 保留正常定位、授权、语义区分与正确读取所需内容；不要求展开完整追溯链 |
| 新运行的 Batch／Attempt、dry-run／apply 回执、必要修改记录、检查点与恢复记录 | 由平台或宿主按既有机制保留，不向建模 Agent 增加整理职责 |
| 独立验收的实际查询响应、获准业务资料及判定理由 | 继续支撑验收结论，与被停用的平台 Evidence 资源区分 |

业务场景本身若包含“凭证”“来源”等概念，仍按普通业务语义建模；不增加按名称禁止此类概念
的校验。本期不重设计追溯系统，也不要求新增按 Project、Ontology 或角色切换追溯模式的开关。

#### 2. 行为要求

**F1 — 建模 Agent 的实际输入与产物**

- v4.0 实际下发的 Task、Skill、角色指令、加载的 references、产物模板、工具说明及动态提示
  均移除证据留存要求。候选合同不向建模 Agent 暴露 `evidence_citations`、原文摘录、来源
  定位、摘录摘要或逐项证据表等追溯专用字段；仅把这些字段改为可选仍不足以完成本条。
- 建模 Agent 负责业务含义、范围、关系、规则、映射与未知项，可以完全不提交追溯专用字段。
  语义说明与必要业务澄清继续保留，但不得借“建模理由”“质量检查”要求另交来源引用或证据包。
- 检查最终组装后 Agent 实际看到的内容；只修改一个 Skill、在运行时告知“忽略旧要求”，或
  在主提示后追加停用说明而保留相冲突的模板，均不满足要求。

**F2 — 翻译、审阅与交接**

- Protocol 可直接翻译不含 Evidence 的候选，审阅仍检查语义是否忠实、引用是否正确，以及
  dry-run 结果与计划写入是否一致；不要求证据引用一一映射、证据回贴或追溯读回。
- Coordinator、Protocol、评审角色、运行校验及交接合同均不得因缺少 Evidence 或完整
  lineage 发出补证任务、拒绝交接或要求重新建模。生产交接保留当前模型、实际执行状态、
  业务范围及已知缺口，不要求建模 Agent 创建来源摘录包或证据覆盖表。
- 不通过宿主代填虚构引用、自动建立占位 Evidence，或把追溯状态强制改成 `supported`／
  `complete` 来通过旧校验；应解除已停用能力对应的依赖和校验。

**F3 — 写入与恢复**

- 正常写入合同不要求 Evidence ID、内联摘录或证据关联；省略这些字段的合法请求应能完成
  dry-run、apply 及读回，且不返回 `missing_evidence` 等补证提示。
- 正常写入不创建 Evidence Reference／Association 或事实证据绑定，不要求 Evidence
  解析、证据计划或补证操作作为提交条件；不会因停用专用证据能力而导致语义写入失败。
- 依赖顺序、Shape／规则校验、版本与并发控制、幂等、原子应用、写入结果确认及必要恢复保持
  原有职责。追溯实现若与这些机制共享代码或数据，应按实际依赖拆分；不能直接删除整个
  canonical write、审计、图版本或检查点机制。可以保留共享机制自动产生的必要内部记录，
  不要求其构成完整 lineage，也不要求建模 Agent 提供追溯输入。
- 按已确认的 D2，停止仅服务于完整追溯的自动记录；保留写入、授权与恢复必需的内部记录，
  不以共享代码为由继续采集完整追溯，也不要求全量拆除历史代码或存储。

**F4 — 语义检索与返回合同**

- 正常 Context Query、资源／事实读取及关联展开不依赖专用 Evidence／lineage 查询才能
  成功；不能只在返回末尾隐藏字段，内部仍逐项查询完整 lineage 作为必要步骤。
- 从正常消费返回及其默认、精简投影中移除追溯专用的 `evidence_reference_ids`、
  `evidence_status`、`lineage`、依赖证据状态与追溯完整性／证明等级等内容。停用状态不再
  按逐资源“缺证”“待补齐”“追溯不完整”呈现，也不得宣称已经获得证据支持或完整追溯。
- 保留业务字段、关系方向、规则关联、映射、资源与图定位以及真实的检索完整性。分页未结束、
  结果截断、授权不可见、未建模或结果过期等情况继续如实表达，不能随追溯告警一起屏蔽。
- 用于解释检索命中的 `label_evidence`、`mapping_evidence`、多表达式匹配依据等，按其
  实际业务／检索职责判断是否保留，不因名称包含 `evidence` 一并删除。Protocol 的检索
  完成校验不再要求 `evidence_status=supported`、非空证据 ID 或 `lineage.status=complete`。

**F5 — 专用接口、工具与合同文档**

本项全面撤下方案已随 D1 于 2026-10-01 确认，适用于所有调用者；A5 按该范围验收。

- v4.0 不再对外提供证据创建、绑定／解绑、解析、证据查询、缺证清单与完整追溯专用入口。
  REST 路由、MCP 工具、运行时工具目录和工具说明同步撤下这些能力，包括旧 provenance 别名
  与 staged evidence 回贴入口；不能只从一个角色的提示中隐藏、其他实际入口仍可使用。
- 不保留历史只读替代接口或证据模式切换。已停用入口收到调用时按既有未提供／不支持合同
  返回，不能伪装成成功写入或成功查询到空数据；无需为此新建通用功能开关或兼容框架。
- 正常建模与消费工具的公开输入、输出和嵌套 Schema 同步调整，不要求调用方提供空证据数组。
  同步更新 [REST 合同](../reference/api.md)、[MCP 合同](../reference/mcp.md)及实际加载的
  候选／Batch references，避免文档继续引导调用停用能力。

**F6 — 页面与用户提示**

- 移除 Evidence 导航和创建／绑定入口、来源摘录与完整追溯展示、缺证筛选、证据覆盖／缺失
  指标，以及实体、事实、查询结果、治理与构建页面中的证据徽标和补证提示。
- 共享页面保留实体、事实、规则、语义校验、查询、修改与恢复所需内容；不因含有证据组件而
  下线整个页面。正常页面不再发起已停用接口请求，不留下空证据卡片、报错或等待中的占位区。
- 不新增历史证据页面、只读模式或“暂时缺少证据”的提示；停用不是每项模型都存在的待办缺口。

**F7 — 独立语义验收**

- 继续用获准业务资料、访谈信息与真实平台查询响应核对源忠实度、覆盖范围、关系、规则、
  映射与未知项。独立验收方可记录判定依据，宿主可保留工具响应，不能把这些职责转交给建模
  Agent，也不要求将它们登记为平台 Evidence。
- 无 Evidence／lineage 本身不扣分、不触发补证、不构成失败；业务含义错误、虚构事实、
  映射错误、缺少必要业务语义或越权仍按原有要求判定。独立验收方不得创建、继续或修复被
  验收的运行，也不得修改其保留记录。

#### 4. 验收标准

以下细化前述两项已确认验收约束。优先复用现有场景、测试和运行路径，不为本条新建建模框架
或一次性语义裁判。R4.0-012 可先行交付，不以其他所有 v4.0 条目实现完成为前置；真实场景
按选定的有界范围验证其涉及的多视角内容。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A1 | 检查 v4.0 实际组装的 Agent 输入、工具目录与候选模板 | 无证据留存任务、追溯专用字段或工具；不依赖“忽略旧要求”的运行时补丁 |

| A3 | 对该模型执行正常资源读取、Context Query 与关联检索 | 不调用专用追溯查询作为必要步骤，不返回逐资源缺证状态或追溯专用字段，业务内容可正常取得 |
| A4 | 执行分页／截断、受限读取及真实语义缺口检查 | 检索完整性、授权与已知缺口仍按原合同表达；缺少追溯本身不使结果降级或失败 |

| A6 | 浏览导航、实体、事实、检索、治理与构建页面 | 无证据创建／绑定／追溯入口、缺证筛选或指标；共享功能可用，不请求停用接口，不留下证据占位区 |

A1—A7 提供合同、功能与运行完整性证据，不能代替 A8 的独立语义验收。分别记录

#### 5. 详细设计交接边界

D1／D2 已确认；详细设计按确定的行为逐项确定路由／工具注册、输入输出 Schema、动态提示、校验分支和页面
组件的最小改动；共享内部记录及存储按新写入和恢复的真实依赖决定是否保留。不要求全量删表、
清库或把每个含追溯字样的内部类型改名，也不为已排除的历史数据增加迁移、回填与兼容分支。
验收时同步核对实际接口与 [术语表](../reference/glossary.md)等活跃文档的 v4.0 适用范围，
不改写旧版本和历史验收结论。待多视角表达稳定且出现实际追溯需求后，再单独决定恢复、
重设计或彻底移除相关能力。

## 重点风险与后续讨论

以下为 2026-09-24 只读设计审阅发现的风险，不是已发生事故，也不是已确定的修正方案。
后续逐条细化时需明确处置，不应把看似可行的表达直接固化为实现。

| 编号 | 风险与可能后果 | 重点需要讨论 | 关联需求 |
| --- | --- | --- | --- |
| K1 | 用类层次承接状态、合同、场景等所有差异，可能形成组合类膨胀；调整条件牵动分类、Action 和查询。RDF 子类也不自动表达方法覆盖或例外优先级。 | 稳定分类、适用范围与动态条件的分界；保留子类适用约定时如何表达条件差异。 | R4.0-002、R4.0-003 |
| K2 | 参数只关联对象类型，无法区分原工单与返修工单等同类对象；按名称或自由文本绑定可能给出结构合法但对象错误的调用解释。 | 对象引用身份、参数来源、属性及调用输出的关联方式，含集合、重复调用和缺失信息。 | R4.0-003、R4.0-004、R4.0-005 |
| K3 | 自然语言说明与脚本成为两份不一致的定义；相同版本号不能证明边界条件、单位、时间及空值处理一致。 | 共同的输入输出语义、版本与例子验证；发生冲突时如何处理，不静默任选一份。 | R4.0-005、R4.0-007、R4.0-008 |
| K4 | 将任何“生成节点”都视为语义推导，会把具体设备评估、业务单据和运行记录混入本体，引出身份、重复、过期及同步问题。 | 区分新语义知识、业务计算结果和业务动作；明确输出身份、落点和产生规则，相关边界未定前不默认物化。 | R4.0-002、R4.0-005 |
| K5 | 受限规则正文或阈值被复制进公开说明、脚本后，隐藏原规则仍可能泄露内容；业务角色与授权事实混用也会跨越管理边界。 | 引用与复制的边界，新资源的保护责任；管理员确认的角色映射。现有 IRI 引用过滤不等于自动理解脚本或文本中的敏感语义。 | R4.0-005、R4.0-006、R4.0-008 |
| K6 | 修改共享 Action／规则会改变多个流程；只保留历史、仍引用当前定义不能保证兼容。业务动作与外部接口耦合还可能让接口调整波及业务模型。 | 引用当前态还是确定版本、哪些变更影响调用、如何检查兼容及修订范围；Action 与外部 Operation 的关系，以及 Schema／接口变更对映射的影响。 | R4.0-003、R4.0-004、R4.0-005、R4.0-007、R4.0-010、R4.0-011 |
| K7 | 数据库与 API 各自建立业务定义，或仅按同名字段关联，可能导致对象身份错配；忽略记录粒度、关联基数和编码差异，会产生结构合法但业务含义错误的查询或调用解释。 | 共享定义与映射资源的边界；业务编号、主键、接口标识的对应；多表关联与状态、单位、时间等转换含义，如何通过实际数据或接口样例验证。 | R4.0-002、R4.0-009、R4.0-010、R4.0-011 |

后续细化可优先用以下反例检验表达约定，当前仅记录问题：

1. 同一流程同时引用原工单和返修工单，如何明确 Action 的目标。
2. 同一个 Action 在两个流程中使用不同输入来源，新增必填参数后如何处理已有引用。
3. 同一工单类型因状态或合同不同，关闭条件不同，是否需要改变分类。
4. 公开流程引用受限规则，同时规则发生版本变更，如何保持含义和可见范围一致。
5. 同一工单在数据库与 API 中使用不同标识或状态编码，如何保持对象一致；关联维修明细后如何避免重复统计工单。
