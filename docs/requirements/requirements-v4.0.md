## 本次讨论的范围与边界

- 面向通用业务场景，从对象、行为、规则、角色、流程等视角建模；同一业务定义通过稳定身份
  和明确关系复用。视角与业务切片是两个维度，不据此固定 Ontology 数量或 Agent 数量。
- 增加数据映射与接口映射视角，分别连接外部数据库和外部 API；共同引用已确认的业务定义。
  独立分析职责、模型产物与验证内容，不要求每个视角单独存储或配置 Agent。
- Ontology 作为语义层，实际业务动作由外部系统执行。业务行与运行记录仍保留在外部系统，
  不要求增加流程执行引擎；平台已有的图校验、推理与实际业务执行保持区别。
- 规则需要保留脚本形式及自然语言说明，供外部 Consumer 理解和使用；脚本语言与执行约定尚未确定。
- 业务角色描述职责，平台权限控制语义可见范围；二者可显式关联，授权仍由管理面确认。
- 本次不考虑页面位置、颜色、折叠状态等视图配置，也不引入面向软件生成的 UI 模型。
- v4.0 阶段性停用证据追溯并解除建模、检索和验收主流程对它的依赖；建模 Agent 不承担
  证据留存职责，具体范围与验收约束见 R4.0-012。
- R4.0-012 的范围与验收约束已确认；R4.0-002 已进入细化草案，其余条目仍为待细化登记。
  草案建议、“待讨论”和风险中的修正方向不代表已批准的技术方案。
  R4.0-001 持续改进保持独立，不作为多视角建模的整包前置。

**边界**：保留来源忠实、业务语义确认、授权及独立验收原则。本次不预定反馈采集方式、

### R4.0-002 多视角语义组织与共享定义

状态：需求细化草案（2026-10-01）；D1 语义角色可识别已获用户确认，其余新增细化为建议草案，
尚未进入详细设计或实现。

**目标与范围**：围绕对象、行为、规则、角色、流程组织业务语义；不同视角引用同一份已确认
定义，不分别维护相互脱离的模型副本。明确对象类别、属性、关系和业务角色职责；需要共性时
使用分类，同名不直接认定为同义。业务含义、适用范围和未知项应能随资源及关系读取。
各视角保留可供大模型理解的自然语言说明，并与结构化语义关联。

以下将原登记展开为可讨论、可验证的要求；除注明继承既有约定的内容外，均为本轮建议草案。
重点关联风险 K1、K2、K7。

#### 1. 最小范围与术语

以“工单”为例：对象视角说明工单是什么及其属性，流程引用该定义描述处理对象，数据和
接口映射也引用该定义描述外部表示。不能因出现在不同视角就创建几份互不关联的“工单”。
流程同时出现“原工单”和“返修工单”时，二者可以引用同一个工单类别，但调用上下文必须
区分；这种区分不自动产生新类别，也不意味着把两张实际业务工单写入语义层。

| 概念 | 本条含义与边界 |
| --- | --- |
| 视角 | 分析和组织业务语义的关注点，包括对象、行为、规则、角色、流程、数据映射、接口映射；不等同于 Ontology、逻辑切片、Agent 或权限边界 |
| 语义角色 | 某项内容表达的是对象定义、行为定义、规则、业务角色、流程或映射等何种业务语义；读取方应能识别，不等同于平台存储类型或权限角色 |
| 共享定义 | 业务含义和适用范围一致、被多处引用的同一语义定义；名称相同不足以证明应当共享 |
| 局部含义 | 某个业务上下文中的用途、责任或限制；必须能辨别其适用上下文，不能静默覆盖共享定义 |
| 对象类别 | 已确认的业务共性；承接 R3.0-009，按实际需要选择普通业务分类或正式 Class，不因出现一个名词就建立 Class |
| 业务角色 | 对业务职责和参与关系的描述；不等于实际用户、API Key、建模 Agent 角色或授予权限的管理面角色 |

本条先确定各视角共同使用的语义组织约定，并细化对象、属性、关系、分类和业务角色职责。
其他视角在本条中只确定共享引用边界，其专属表达由对应需求细化。

#### 2. 功能要求草案

**F1 — 共享身份与明确引用**

- 同一获准 Project 范围内，已确认含义与适用范围一致的定义使用同一稳定身份；在不同视角、
  逻辑切片或获准 Ontology 中引用时，不另建只因展示位置不同而产生的副本。
- 候选中的语义身份和物化后的资源 IRI 应可明确对应；不能由 Modeling Agent 猜测平台 ID，
  也不能仅凭同名、别名或相似描述自动合并资源。沿用现有 Protocol 翻译与回执绑定职责。
- 含义不同的同名定义保持独立，并说明差异或范围；是否同义尚未确认时保留未知，不默认合并。
- 不增加跨 Project 共享、全局定义注册中心或自动实体消歧服务。稳定身份也不替代版本兼容判断，
  共享定义变更及引用重审流程归 R4.0-007。

**F2 — 对象、属性与关系的最小业务含义**

- 对象定义能读取名称、业务含义及适用范围；属性说明其值代表什么，关系说明两端含义、
  方向及适用范围。必要的单位、取值或多值含义应明确，未确认部分保持未知。
- 结构化关联应能解析到所引用的定义；自然语言说明用于解释含义，不能用一段同名文本替代
  本应明确的对象引用，也不从数据库字段名自动生成已确认的业务定义。
- 只表达语义知识、受控参考值和映射意义，外部业务行仍留在外部系统。

**F3 — 分类与局部差异**

- 继承 R3.0-009：语义节点可以没有正式 Class，也可以有多个正式 Class；普通业务分组、
  正式类型成员和子类关系必须区分。不得把“同一视角”自动解释为共同业务类别。
- 只有明确的集合包含含义才使用正式子类关系；状态、合同和场景差异不自动变成子类，
  已确认的稳定类别仍可采用分类。Action 的子类适用和条件差异交 R4.0-003 细化。
- 可共享的定义与特定上下文中的用途、附加条件分别表达；局部说明不能悄悄重写共享含义。
  如果差异改变了定义本身，应作为独立的有范围定义处理；不确定时标明待确认。
- “属于同一类别”不能证明是同一对象引用。原工单／返修工单等调用位置及参数绑定的具体
  表达归 R4.0-004，本条不预定调用节点、变量或绑定语法。

**F4 — 业务角色与职责**

- 业务角色具有可引用的身份和职责说明，并通过明确的业务关系关联其负责、参与或审核的
  业务内容；关系表达的职责含义需可读，不强制所有场景使用相同职责清单。
- 同一业务角色跨流程或视角使用时沿用共享定义；局部职责需保留适用上下文。
- 创建业务角色或职责关系不会授予语义读取或外部执行权限。用户／Key、权限角色、Grant
  及业务角色的管理面映射归 R4.0-006，不由本条引入。

**F5 — 说明、范围和未知项可读**

- 对象、分类、属性、关系和角色定义的自然语言说明须与对应资源或关系明确关联；范围和
  未知项在获准读取时能够取得，不只存在于 Agent 对话或未交付的分析文件中。
- 已知冲突不静默任选一份解释；缺少说明、未知、无适用内容和无权读取不能混为同一状态。
  本条不增加语义评分器或要求平台自行判断业务同义。
- 复用现有受治理资源读取和关系读取作为最小验证路径；跨视角自动召回、上下文组装和
  专门筛选能力归 R4.0-008。
- 继承 R4.0-012：不增加 Evidence、lineage、来源摘录或逐资源补证义务；业务资料忠实度和
  独立语义正确性要求继续生效。

**F6 — 读取时识别语义角色（用户已确认的目标）**

- 读取模型时，Consumer 应能明确识别相关内容表达的是对象、行为、规则、业务角色、流程、
  数据映射还是接口映射。不能要求仅凭名称、所在页面或 Agent 曾经的对话猜测。
- 例如“工单”是对象定义，“关闭工单”是行为定义，“允许关闭的条件”是规则定义；三者
  通过含义明确的关系关联。工单被流程或接口引用后仍是同一对象定义，不因此变成流程或接口。
- 实现建议：通过明确、可读取的语义声明表达上述区分，并关联自然语言解释。具体可采用
  现有类型、关系或其他合适的语义表达，由详细设计核对；业务语义角色不要求与平台内部
  resource kind 一一对应，也不强制全部内容新增正式 Class。
- 本次确认的是读取方能识别业务含义，并未决定额外的“视角标签”字段、固定七类平台资源、
  互斥分类或任意多标签机制。同一资源是否承担多种语义角色，按其已确认业务含义决定，
  不能把“被多个视角引用”直接当成“具有多种角色”。
- 本条先形成共同表达约定并验证对象／分类／业务角色的适用路径。Action、流程、规则和映射
  的专属合同在对应需求中接入同一约定；不要求在 002 中提前实现其全部专属结构。

| A4 | 共享定义被两个上下文使用，其中一个有局部职责或限制 | 读回能辨别共享含义和局部范围，不覆盖另一个上下文；调用绑定细节另按 004 验收 |
| A5 | 读取对象、属性、关系、角色及一个明确未知项 | 名称、说明、方向、适用范围和未知可从相应资源或关系取得；业务角色不自动授予权限 |
| A6 | 既有授权、dry-run／apply 和无 Evidence 合同回归 | 不绕过治理写入或读取，不引入补证任务；不以视角制造新的授权边界 |
| A7 | 读取不同语义角色的定义及被多个视角引用的共享定义 | 能依据明确的语义声明识别各自角色，共享引用不改变定义身份或角色；002 验证共同约定和本条涉及的路径，其余角色随对应需求补齐，统一验证时覆盖全部适用角色 |
| A8 | 后续统一真实建模及独立语义验收 | 根据获准资料和实际读取结果判定共享身份、范围、分类与职责是否正确；错误合并、重复定义和局部含义覆盖能够被检出 |

功能交付时需给出本条实际增量和已有能力复用范围；A8 未完成时保留语义未验收状态。

### R4.0-012 证据追溯能力阶段性停用与多视角建模解耦

状态：已实现；2026-10-01 独立测试 Round 2 判定 A1—A7 功能 PASS。A8／L1 未授权、未执行，整体 PARTIAL。
设计见 [R4.0-012 详细设计](../delivery/designs/2026-10-01-r4-0-012-tracing-suspension-design.md)。
实现、失败修复及验收证据见 [交付记录](../delivery/records/2026-10-01-r4-0-012-tracing-suspension-delivery-record.md)和 [测试记录](../delivery/test-plans/2026-10-01-r4-0-012-tracing-suspension-test-plan.md)。
已确认停用方向、建模 Agent 不承担证据留存职责，以及本期不考虑历史数据读写兼容。

**问题与目标**：多视角下共享定义、Action 调用、规则及映射的追溯关系需要重新评估。
v4.0 优先验证建模效率、语义表达和实际业务问题的回答质量，阶段性停用 Evidence 与完整
lineage 追溯能力，使建模、写入、检索和独立语义验收可以在不创建 Evidence、不补齐追溯链的
条件下完成。本期不承担追溯重设计，也不以重设计完成作为多视角建模的前置条件。

**本期范围**：

- 从 v4.0 主流程移除创建、绑定、维护和查询 Evidence、补齐 lineage 的要求，同步调整
  Task／Skill、候选与交接产物、Protocol 翻译、工具合同、检索返回、页面入口和验收要求。
  不仅隐藏页面，还需解除正常建模与语义消费对追溯能力的依赖。
- 建模 Agent 不承担留存证据的职责；不要求摘录原文、登记证据、建立逐资源证据关联或整理
  追溯包，也不通过翻译、评审或交接间接向其追加补证任务。
- 未创建 Evidence 或未补齐追溯链不产生面向建模 Agent 的缺证告警、重试、返工或阻断，也不作为
  本期建模及语义验收的不通过理由。未采集状态不得伪装成已有证据支持或完整追溯。
- 仅服务于已停用证据要求的逻辑可以删除；与当前写入、检索及恢复共享的实现先确认
  耦合再确定删除范围，不把全量代码或存储删除作为本期完成条件。
- 当前项目没有真实数据，本期不考虑历史 Evidence／lineage 数据的读取、写入、迁移或回填，
  不提供历史只读接口、历史页面或为历史数据保留的兼容路径。此项取代本条先前的历史数据保留
  与读取兼容要求；不据此增加数据清理任务。

**边界**：业务资料与访谈仍用于确认语义和独立验收，未知项保持可见；不要求建模 Agent
另建证据包或为每项语义附加来源引用。参数输入来源、数据源与表字段映射、产生结果的规则等
属于业务模型内容，仍需正确表达。实际查询结果与业务依据仍须支撑独立语义验收结论，停用
Evidence／lineage 不豁免源忠实度和语义正确性。

写入回执、必要修改与恢复记录由现有平台或宿主机制负责，不转化为建模 Agent 的证据留存
任务。停用后的新写入仍须满足 dry-run／apply 完整性、授权、受治理检索和必要恢复要求。
本条改变 v4.0 的能力继承范围，不改写旧版本或历史运行的验收结论，也不授予真实建模额度。

**验收约束（已确认）**：

1. 在不提交 Evidence、不依赖追溯查询的条件下，完成一个真实场景的多视角建模、写入、
   关联检索和独立语义验收；追溯缺失不阻断该流程。
2. **建模 Agent 不感知需要留存证据**：检查实际下发的 Task／Skill、产物模板、工具说明及
   输入输出、评审反馈和交接要求，均不向其提出证据留存或补齐义务；Agent 无需理解
   Evidence／lineage 合同、填写证据字段或调用证据与追溯工具即可完成建模。运行中不因
   缺少证据收到补证任务，不由宿主临时提示绕过旧要求来满足本约束。

**确认状态**：停用主流程依赖、建模 Agent 无证据留存职责、不考虑历史数据读写，

| 资源身份、所属 Project／Ontology、图与版本、asserted／derived 及结果过期状态 | 保留正常定位、授权、语义区分与正确读取所需内容；不要求展开完整追溯链 |
| 新运行的 Batch／Attempt、dry-run／apply 回执、必要修改记录、检查点与恢复记录 | 由平台或宿主按既有机制保留，不向建模 Agent 增加整理职责 |
| 独立验收的实际查询响应、获准业务资料及判定理由 | 继续支撑验收结论，与被停用的平台 Evidence 资源区分 |

业务场景本身若包含“凭证”“来源”等概念，仍按普通业务语义建模；不增加按名称禁止此类概念
的校验。本期不重设计追溯系统，也不要求新增按 Project、Ontology 或角色切换追溯模式的开关。

#### 2. 行为要求

**F1 — 建模 Agent 的实际输入与产物**

- v4.0 实际下发的 Task、Skill、角色指令、加载的 references、产物模板、工具说明及动态提示
  均移除证据留存要求。候选合同不向建模 Agent 暴露 `evidence_citations`、原文摘录、来源
  定位、摘录摘要或逐项证据表等追溯专用字段；仅把这些字段改为可选仍不足以完成本条。
- 建模 Agent 负责业务含义、范围、关系、规则、映射与未知项，可以完全不提交追溯专用字段。
  语义说明与必要业务澄清继续保留，但不得借“建模理由”“质量检查”要求另交来源引用或证据包。
- 检查最终组装后 Agent 实际看到的内容；只修改一个 Skill、在运行时告知“忽略旧要求”，或
  在主提示后追加停用说明而保留相冲突的模板，均不满足要求。

**F2 — 翻译、审阅与交接**

- Protocol 可直接翻译不含 Evidence 的候选，审阅仍检查语义是否忠实、引用是否正确，以及
  dry-run 结果与计划写入是否一致；不要求证据引用一一映射、证据回贴或追溯读回。
- Coordinator、Protocol、评审角色、运行校验及交接合同均不得因缺少 Evidence 或完整
  lineage 发出补证任务、拒绝交接或要求重新建模。生产交接保留当前模型、实际执行状态、
  业务范围及已知缺口，不要求建模 Agent 创建来源摘录包或证据覆盖表。
- 不通过宿主代填虚构引用、自动建立占位 Evidence，或把追溯状态强制改成 `supported`／
  `complete` 来通过旧校验；应解除已停用能力对应的依赖和校验。

**F3 — 写入与恢复**

- 正常写入合同不要求 Evidence ID、内联摘录或证据关联；省略这些字段的合法请求应能完成
  dry-run、apply 及读回，且不返回 `missing_evidence` 等补证提示。
- 正常写入不创建 Evidence Reference／Association 或事实证据绑定，不要求 Evidence
  解析、证据计划或补证操作作为提交条件；不会因停用专用证据能力而导致语义写入失败。
- 依赖顺序、Shape／规则校验、版本与并发控制、幂等、原子应用、写入结果确认及必要恢复保持
  原有职责。追溯实现若与这些机制共享代码或数据，应按实际依赖拆分；不能直接删除整个
  canonical write、审计、图版本或检查点机制。可以保留共享机制自动产生的必要内部记录，
  不要求其构成完整 lineage，也不要求建模 Agent 提供追溯输入。
- 按已确认的 D2，停止仅服务于完整追溯的自动记录；保留写入、授权与恢复必需的内部记录，
  不以共享代码为由继续采集完整追溯，也不要求全量拆除历史代码或存储。

**F4 — 语义检索与返回合同**

- 正常 Context Query、资源／事实读取及关联展开不依赖专用 Evidence／lineage 查询才能
  成功；不能只在返回末尾隐藏字段，内部仍逐项查询完整 lineage 作为必要步骤。
- 从正常消费返回及其默认、精简投影中移除追溯专用的 `evidence_reference_ids`、
  `evidence_status`、`lineage`、依赖证据状态与追溯完整性／证明等级等内容。停用状态不再
  按逐资源“缺证”“待补齐”“追溯不完整”呈现，也不得宣称已经获得证据支持或完整追溯。
- 保留业务字段、关系方向、规则关联、映射、资源与图定位以及真实的检索完整性。分页未结束、
  结果截断、授权不可见、未建模或结果过期等情况继续如实表达，不能随追溯告警一起屏蔽。
- 用于解释检索命中的 `label_evidence`、`mapping_evidence`、多表达式匹配依据等，按其
  实际业务／检索职责判断是否保留，不因名称包含 `evidence` 一并删除。Protocol 的检索
  完成校验不再要求 `evidence_status=supported`、非空证据 ID 或 `lineage.status=complete`。

**F5 — 专用接口、工具与合同文档**

本项全面撤下方案已随 D1 于 2026-10-01 确认，适用于所有调用者；A5 按该范围验收。

- v4.0 不再对外提供证据创建、绑定／解绑、解析、证据查询、缺证清单与完整追溯专用入口。
  REST 路由、MCP 工具、运行时工具目录和工具说明同步撤下这些能力，包括旧 provenance 别名
  与 staged evidence 回贴入口；不能只从一个角色的提示中隐藏、其他实际入口仍可使用。
- 不保留历史只读替代接口或证据模式切换。已停用入口收到调用时按既有未提供／不支持合同
  返回，不能伪装成成功写入或成功查询到空数据；无需为此新建通用功能开关或兼容框架。
- 正常建模与消费工具的公开输入、输出和嵌套 Schema 同步调整，不要求调用方提供空证据数组。
  同步更新 [REST 合同](../reference/api.md)、[MCP 合同](../reference/mcp.md)及实际加载的
  候选／Batch references，避免文档继续引导调用停用能力。

**F6 — 页面与用户提示**

- 移除 Evidence 导航和创建／绑定入口、来源摘录与完整追溯展示、缺证筛选、证据覆盖／缺失
  指标，以及实体、事实、查询结果、治理与构建页面中的证据徽标和补证提示。
- 共享页面保留实体、事实、规则、语义校验、查询、修改与恢复所需内容；不因含有证据组件而
  下线整个页面。正常页面不再发起已停用接口请求，不留下空证据卡片、报错或等待中的占位区。
- 不新增历史证据页面、只读模式或“暂时缺少证据”的提示；停用不是每项模型都存在的待办缺口。

**F7 — 独立语义验收**

- 继续用获准业务资料、访谈信息与真实平台查询响应核对源忠实度、覆盖范围、关系、规则、
  映射与未知项。独立验收方可记录判定依据，宿主可保留工具响应，不能把这些职责转交给建模
  Agent，也不要求将它们登记为平台 Evidence。
- 无 Evidence／lineage 本身不扣分、不触发补证、不构成失败；业务含义错误、虚构事实、
  映射错误、缺少必要业务语义或越权仍按原有要求判定。独立验收方不得创建、继续或修复被
  验收的运行，也不得修改其保留记录。

#### 4. 验收标准

以下细化前述两项已确认验收约束。优先复用现有场景、测试和运行路径，不为本条新建建模框架
或一次性语义裁判。R4.0-012 可先行交付，不以其他所有 v4.0 条目实现完成为前置；真实场景
按选定的有界范围验证其涉及的多视角内容。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A1 | 检查 v4.0 实际组装的 Agent 输入、工具目录与候选模板 | 无证据留存任务、追溯专用字段或工具；不依赖“忽略旧要求”的运行时补丁 |
| A2 | 提交完全不含证据字段的合法候选／Batch，完成 dry-run、apply、读回和交接 | 无补证错误或告警，无 Evidence Reference／Association／事实证据绑定新增；没有使用占位证据或虚构 `supported`／`complete` |
| A3 | 对该模型执行正常资源读取、Context Query 与关联检索 | 不调用专用追溯查询作为必要步骤，不返回逐资源缺证状态或追溯专用字段，业务内容可正常取得 |
| A4 | 执行分页／截断、受限读取及真实语义缺口检查 | 检索完整性、授权与已知缺口仍按原合同表达；缺少追溯本身不使结果降级或失败 |
| A5 | 检查 REST／MCP 注册、实际工具目录及停用入口调用 | 专用能力及旧别名均不可用，合同文档与实际暴露一致，不提供历史只读替代入口 |
| A6 | 浏览导航、实体、事实、检索、治理与构建页面 | 无证据创建／绑定／追溯入口、缺证筛选或指标；共享功能可用，不请求停用接口，不留下证据占位区 |
| A7 | 使用停用后的新运行验证写入拒绝、重试及现有恢复路径 | 非证据错误继续按原合同处理；dry-run／apply、幂等、原子性与必要恢复不因停用而受损；不要求恢复旧证据数据 |
| A8 | 在不提交 Evidence、不调用追溯工具的条件下完成一个真实场景的多视角建模与独立语义验收 | 建模 Agent 全程不承担留存／补证任务；独立验收根据获准业务资料及实际查询判断质量，正确表达与明确未知可接受，错误含义仍能被检出 |

A1—A7 提供合同、功能与运行完整性证据，不能代替 A8 的独立语义验收。分别记录
`L0 Runtime` 与 `L1 Modeling quality` 的结果；未取得真实语义结果时保持未验收或 PARTIAL，
不把 L2 重复性或 L3 产品化作为本条首轮验证前置。本次完成需求决策同步与详细设计，没有执行上述验收或新增
真实建模授权。

#### 5. 详细设计交接边界

D1／D2 已确认；详细设计按确定的行为逐项确定路由／工具注册、输入输出 Schema、动态提示、校验分支和页面
组件的最小改动；共享内部记录及存储按新写入和恢复的真实依赖决定是否保留。不要求全量删表、
清库或把每个含追溯字样的内部类型改名，也不为已排除的历史数据增加迁移、回填与兼容分支。
验收时同步核对实际接口与 [术语表](../reference/glossary.md)等活跃文档的 v4.0 适用范围，
不改写旧版本和历史验收结论。待多视角表达稳定且出现实际追溯需求后，再单独决定恢复、
重设计或彻底移除相关能力。

## 重点风险与后续讨论

以下为 2026-09-24 只读设计审阅发现的风险，不是已发生事故，也不是已确定的修正方案。
后续逐条细化时需明确处置，不应把看似可行的表达直接固化为实现。

| 编号 | 风险与可能后果 | 重点需要讨论 | 关联需求 |
| --- | --- | --- | --- |
| K1 | 用类层次承接状态、合同、场景等所有差异，可能形成组合类膨胀；调整条件牵动分类、Action 和查询。RDF 子类也不自动表达方法覆盖或例外优先级。 | 稳定分类、适用范围与动态条件的分界；保留子类适用约定时如何表达条件差异。 | R4.0-002、R4.0-003 |
| K2 | 参数只关联对象类型，无法区分原工单与返修工单等同类对象；按名称或自由文本绑定可能给出结构合法但对象错误的调用解释。 | 对象引用身份、参数来源、属性及调用输出的关联方式，含集合、重复调用和缺失信息。 | R4.0-003、R4.0-004、R4.0-005 |
| K3 | 自然语言说明与脚本成为两份不一致的定义；相同版本号不能证明边界条件、单位、时间及空值处理一致。 | 共同的输入输出语义、版本与例子验证；发生冲突时如何处理，不静默任选一份。 | R4.0-005、R4.0-007、R4.0-008 |
| K4 | 将任何“生成节点”都视为语义推导，会把具体设备评估、业务单据和运行记录混入本体，引出身份、重复、过期及同步问题。 | 区分新语义知识、业务计算结果和业务动作；明确输出身份、落点和产生规则，相关边界未定前不默认物化。 | R4.0-002、R4.0-005 |
| K5 | 受限规则正文或阈值被复制进公开说明、脚本后，隐藏原规则仍可能泄露内容；业务角色与授权事实混用也会跨越管理边界。 | 引用与复制的边界，新资源的保护责任；管理员确认的角色映射。现有 IRI 引用过滤不等于自动理解脚本或文本中的敏感语义。 | R4.0-005、R4.0-006、R4.0-008 |
| K6 | 修改共享 Action／规则会改变多个流程；只保留历史、仍引用当前定义不能保证兼容。业务动作与外部接口耦合还可能让接口调整波及业务模型。 | 引用当前态还是确定版本、哪些变更影响调用、如何检查兼容及修订范围；Action 与外部 Operation 的关系，以及 Schema／接口变更对映射的影响。 | R4.0-003、R4.0-004、R4.0-005、R4.0-007、R4.0-010、R4.0-011 |
| K7 | 数据库与 API 各自建立业务定义，或仅按同名字段关联，可能导致对象身份错配；忽略记录粒度、关联基数和编码差异，会产生结构合法但业务含义错误的查询或调用解释。 | 共享定义与映射资源的边界；业务编号、主键、接口标识的对应；多表关联与状态、单位、时间等转换含义，如何通过实际数据或接口样例验证。 | R4.0-002、R4.0-009、R4.0-010、R4.0-011 |

后续细化可优先用以下反例检验表达约定，当前仅记录问题：

1. 同一流程同时引用原工单和返修工单，如何明确 Action 的目标。
2. 同一个 Action 在两个流程中使用不同输入来源，新增必填参数后如何处理已有引用。
3. 同一工单类型因状态或合同不同，关闭条件不同，是否需要改变分类。
4. 公开流程引用受限规则，同时规则发生版本变更，如何保持含义和可见范围一致。
5. 同一工单在数据库与 API 中使用不同标识或状态编码，如何保持对象一致；关联维修明细后如何避免重复统计工单。
