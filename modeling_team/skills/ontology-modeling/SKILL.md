# Ontology Modeling

## Existing-model awareness for current unified Tasks

Before writing into an existing model, read get_modeling_context for the relevant authorized
Ontologies: scope, revision, read/write and index/degradation state. Form a bounded working overview
from business-related candidates and surrounding summaries, not counts, names, old memory or the
first list page. Discover connection points with multiple business expressions for the new objects,
actions, roles, conditions and dependencies; explicitly pass the full authorized ontology_ids set
for initial discovery (omitting it searches only the primary Ontology). Read selected actual IRIs
with context_detail=full in each candidate's own Ontology; inspect definitions, RDF types,
incoming/outgoing relationships and necessary intermediate paths. Continue match_cursor and
context_cursor separately with unchanged scope/query/config, or start a fresh query for a new
expression/anchor. Fixed read models have no invented cursor. Truncation, lexical fallback,
forbidden and no match do not prove global absence; rephrase or disclose the precise unread gap.

Compare meaning, concept versus instance, scope, conditions, direction and unknowns before deciding
reuse, create and connect, modify, or clarify. Similarity is discovery evidence, never equivalence
or a reason to add a business edge. Reuse matching identities and suitable relations, avoid synonym
duplicates, and do not force unrelated new concepts into the old graph. Before modifying shared
meaning inspect relevant direct uses and known indirect dependencies; report incomplete impact.
Refresh only affected judgments after revision/permission changes. Record business intent, key read
references/revisions, important selected/excluded candidates and reasons, actual reused/modified
identities and gaps in existing handoff/map notes. Stop discovery when necessary decisions have
support; no fixed search count, full-graph preload or extra approval. If everything is reused with
no change, follow the existing no-write handoff instead of manufacturing an update.

For an old resource with no current-run creation receipt, bind a concrete observed read-model item
at /structuredContent/data/items/N or a full Context Query primary match at
/structuredContent/data/primary_matches/N, using that response's platform_ref.artifact_path.
A preview neighbor or statement is not a concrete Class binding. The program checks scope,
revision, current full RDF type and canonical native namespace before recovering execution identity;
the Agent never decodes an IRI or reads an old run. External IRIs remain usable in supported IRI
slots; an ID-slot gap is repairable, never grounds to copy an old node. After a new write advances
the revision, reread affected old resources by their exact IRI before binding them. Successful
current-run resource_bindings are still selected by change_id/item_id, never array order.
For multi-Ontology fields-only creates, copy optional placement_ref from the Host's confirmed
multi-slice-ontology-plan notification; it selects one frozen plan entry for this request. It is
outside the six-field changes and fields, and must agree with existing candidate/target ownership.
Different owners require separate submissions; relation endpoints do not choose the relation owner.
Cross-graph Mapping references also require confirmed cross_slice_dependencies under the Host's
actual mapping_reference_direction: report the concrete owner/dependency need to Coordinator.
The Host prepares only affected owners and preserves existing references. Read scope and placement
alone do not prove Mapping reference readiness; mapping_reference_scope_required is repairable in
the same goal. Ordinary relation_type endpoints do not acquire this Mapping gate.
After a valuable stage check new business and connection semantics with public questions, adding
affected-old-business regression when shared meanings change. Trust applied receipts. Independent
final semantic acceptance remains separate, and real runs still require existing authorization.


Own business interpretation, semantic design, explicit unknowns, and the semantic candidate.
The selected Task/Profile and your role instructions define candidate schemas and handoff routes.
For current unified Tasks, directly call the Runner's `modeling_submit_model_changes`
using the mounted R4.3-025 request contract. The program owns translation, Sessions,
leases, Batch execution and real bindings. Coordinator retains scope/topology and
necessary business confirmation; no Protocol translation/dry-run review is required.
For older workflows with a separate Protocol role, keep their declared handoff route;
new model dry-run execution remains retired. Do not hand-author technical plans or
act as the independent acceptance judge.

After a successful stage, use public questions for authorized natural-language recall
and actual IRI expansion. Preserve full conditions, direction, calculation scope and
unknowns. Report index/scope not-ready, lexical degradation and incomplete reads
separately from model content gaps. Before final production handoff, use the existing
association scan through `modeling_inspect_associations` and finish owned execution
resources with `modeling_finish_changes`. Trust success receipts, reconcile uncertain
writes by original identity, and keep independent final acceptance separate.

## Read approved business inputs

Use only mounted approved business inputs, public competency questions and confirmed answers.
Separate source-supported business facts, proposed interpretations, unresolved decisions, and
schema/sample mapping inputs. Database names and sample values do not establish business
meaning. Relational business rows remain in their source database; ontology instances express
semantic resources rather than copied rows.

When expressing a confirmed rule or policy, preserve each operative condition, prohibition and
required response behavior. A related precaution is not a substitute for the complete obligation.
Before handing off a candidate, compare its modeled wording with the approved source; identify and
correct any lost qualifier rather than letting a Consumer infer it from a broad policy label.

Business concepts, rules, metrics and mappings belong to ontology data. Do not request a
scenario-specific platform route or field merely to make a reference question answerable.

## Resolve consequential gaps

Before asserting a conclusion, assess terms, identity, lifecycle, relation direction, cardinality,
ordering, metric scope and the consumer answers that depend on it. Identify gaps from the visible
approved inputs yourself; supplied public questions guide coverage but are not an exhaustive answer key.

Ask one material business question at a time through the role's declared user/Coordinator channel.
State the ambiguity and explain which business conclusion it changes. Reuse confirmed answers;
never ask the user to choose Classes, predicates, IRIs or Batch fields. Continue independent work
while awaiting a decision, without treating silence as confirmation.

If a material answer remains unavailable, preserve a scoped explicit unknown using the selected
candidate contract and [platform-flow.md](references/platform-flow.md). Do not guess a value or
turn a plausible interpretation into an asserted fact. Narrow the unknown to the exact unconfirmed
business meaning; retain other source-confirmed facts and the current scope. Keep confirmation state
separate from candidate/plan/application delivery, and explain the reason, impact and next responsible
role/input for each deferred, unknown or out-of-scope disposition in the existing reason/note or
handoff content. Do not add a field or enum for it. Physical source structure and samples do not
establish customer business rules, business-wide legal value universes or permissions. A declared
source enum/CHECK can describe that source column's allowed values; sample values alone cannot.

For the current authorized chain, a declared source field, value constraint or physical link can
be known even while its customer business interpretation is unknown. When needed by that chain or
an approved public question, express known fields, declared values, non-null/unique/foreign-key
declarations and time conditions in the actual model's permitted definition/text or ordinary
nodes/relations. Clearly scope each declaration to the relevant source structure; preserve concrete
conditions and null branches. Keep the distinct unknown customer meaning in the model as well.
Technical file/line locators and current candidate revision/item references belong in the existing
handoff/map note; handoff-only facts do not count as model expression. Absence of a source-locator
field does not exclude a fact or permit new evidence_refs, lineage or provenance fields.
Excluding executable mappings does not
automatically exclude such evidence. Do not turn a physical constraint into a business rule or
expand to every source column. If it cannot be represented under the selected contract, disclose
the undelivered evidence, affected answer and next input in the existing handoff instead of
relabeling it unknown. Necessary shared dependencies require a grounded disposition; excluding
a whole master-data area does not by itself exclude the minimal dependency used by this chain.

Read the Runner's direct original Task objective, actual Task identity and mounted representation
contracts. Coordinator's dispatch references that task_id and supplements the stage, without
replacing the Task or redefining allowed fields. For a conflict, report the original clause,
conflicting instruction, affected facts/items and proposed correction over existing Team Transport;
continue unaffected work. Correct restatement/format errors within the authorized contract without
new business authorization, preserving normal candidate review and execution authorization.
Route genuine scope changes or unresolved business meaning through Coordinator/Delivery to the
original authorizer. Keep a genuine representation gap explicitly undelivered with impact and next
step; do not relabel known facts unknown, relax fields, permanently end the run or wait for
independent acceptance to resolve an ordinary dispatch conflict.

## Design a coherent scenario

Keep a project-level view of logical slices, shared terms, dependencies and cross-slice questions.
Use the approved slice/public-question projection and coordinate ownership differences through the
existing role channel. A slice or source table does not determine an Ontology boundary.

Choose nodes, predicates, rules and any Class roles from the supported meaning and the loaded
representation contract. In the unified graph workflow, concrete business nodes can remain without
a Class. Propose commonality or classification only when the source supports a stable shared
meaning; repeated fields, similar names and sample values alone do not prove a class, membership,
inheritance or a type-level relation. Preserve the selected task's approval and staging boundary.

For controlled values, distinguish analysis from confirmed business semantics. Follow the staged
contract for analysis conclusions, revisions and materialization decisions. Source-table samples
may motivate a question or mapping; they do not authorize confirmation or materialization. Do not
materialize mapping semantics without the applicable mapping approval; a legitimate deferral does not
mean the authorized scope is complete.

For a staged handoff or content review, use only the approved originals visible to this role and the
existing handoff text, candidate IDs and scenario-map note. Trace important facts, relation direction,
conditions/exceptions, knowns and unknowns from source to candidate items or a concrete gap, then trace
each candidate assertion back to an approved basis. A summary does not prove an unread original. Use
the existing contract and references; do not create a per-field table, private schema, extra Agent or
hard gate. Candidate-to-plan coverage cannot discover material that never entered the candidate. Keep
the stage candidate and plan complete for the current chain and necessary dependencies; later detailed
scenarios are not a prerequisite.

## Coordinate viewpoints and shared changes

Declare a confirmed business semantic role in semantic_definition.semantic_role on the
corresponding supported definition, with its business_meaning, applicability and actual unknowns.
The common roles are object, behavior, rule, business_role, process, data_mapping and
interface_mapping; a confirmed additional meaning may use another role. Resource kinds
such as concept, instance or class are a separate dimension. A missing role is an undelivered
declaration, not evidence of an unknown business meaning. Do not infer a role from RDF type.
For fields-only changes the path is fields.semantic_definition.semantic_role. Repair a
misplaced declaration by moving it to the supported field, retaining its approved meaning.
Check the actual returned declaration in the existing governed stage self-check.

Use the Task-selected scenario-map contract. For R4.0-007, send Coordinator the closed coverage,
stable definition_id/candidate-item correspondence and scoped reference review; Coordinator
owns the map. Interleave object, behavior, rule, role, process, data and interface mapping views
as dependencies permit. Unassessed views are not implicitly inapplicable. Do not require seven
outputs or one Agent per view. Keep shared terms, cross-slice dependencies and public CQs visible.

Separate same-name different meanings, shared meaning and local restrictions. Reuse confirmed
shared identity through the current direct authorized read/receipt binding (Protocol binding only in legacy Tasks), never guess IRIs or create a
synonymous duplicate. Main maintenance ownership coordinates changes and grants no permissions.
Before changing or deleting a shared definition, compare complete old/new candidates and direct
plus known indirect uses: object/parameter identity and source, requiredness/cardinality, conditions,
units/time/nulls, rule script/explanation/input/output/scope, mappings and public CQs. Record
unchanged/revised/unknown/conflict and declared scope; incomplete reads or unresolved dependencies
cannot prove compatibility. Retain unknowns/conflicting_meanings in candidate/model, not only chat.

Apply D1: current definitions, compatible identity reuse after review, synchronous affected changes
in one available atomic Batch; otherwise a confirmed distinct new contract written first and safe
reference groups while old meaning remains, or defer only unsafe work. No cross-Batch atomicity,
automatic clones or same-identity version pinning. Stable IRI/version/dry-run is not semantic proof.
Refresh affected review on candidate/resource drift. Checkpoints retain pending reviews; fork
retains neutral keys but rebinds platform identity. Collaboration records are work, not lineage.

### Report current progress (R4.0-014)

At candidate handoff and content-affecting revision, send Coordinator through the existing message
channel the slice/viewpoint, current complete candidate_id/revision/key item_id or approved path,
analyzed/expressed scope, remaining work/unknowns and next role/input. State what survives or is
invalidated from the old revision, preserving unrelated scope. Final handoff includes remaining
unknowns and work. Coordinator checks actual content and alone writes the shared map.

Partial current expression is modeled plus its limits; analysis without expression is pending,
or unknown if unresolved business facts block it. A correctly expressed necessary unknown may be
modeled but remains unconfirmed. not_applicable requires scoped business grounds, not missing
sources. Keep real business unknowns consistent in the candidate and map's explicit_unknowns;
ordinary unstarted work is a progress task, not an invented business unknown. Missing/unverified
artifacts, pending approval/application/acceptance and absent plans are progress/evidence gaps.
An unconfirmed proposal alone does not establish semantic ambiguity; identify an actual unresolved
business meaning before reporting it for explicit_unknowns. Do not infer business
confirmation, applied state, independent PASS or write permission from modeled. Use actual bound
execution results and original verdicts for those separate conclusions; never copy hidden material.

Use the mounted candidate-authoring and task-specific semantic contracts for exact output fields.
Give every claim a clear business or confirmed-answer basis; expose unsupported alternatives
as proposals or unknowns. Preserve identities, scope and dependency links across candidate items.
Do not invent a fallback schema when a field or contract is unclear.

item kinds. Supported fields-only definitions, including Class/relation_type, use a complete

a Class. Choose the representation from the approved source's semantic level,

requests and applied/read references as the semantic delivery without inventing a candidate.

and in references apply only when the selected legacy workflow actually uses Protocol.

## Assess returned execution results

A candidate receipt proves only what that receipt states. Trust Protocol's bound successful
application/Attempt and version confirmation without a routine full resource/statement comparison.
Use business-directed governed reads, public feedback, affected rechecks and final association checks
to identify semantic gaps. Track stage application separately from business quality; a stage may
advance along real dependencies while its quality is unverified. Keep full authorized scope and
remaining stages; pause only real dependents of a defect, including shared references. Original
identity recovery remains required for uncertain writes. A confirmed business meaning and its
candidate/plan/application delivery are separate states; `not_evaluated` and a legitimate deferral
are not semantic PASS or whole-scope completion. Final independent acceptance is separate.
Preserve source-supported business constraints as ordinary semantic knowledge; do not require
SHACL/OWL runs, specialized rule annotations, scripts or their receipts (R4.0-025).

Distinguish absent semantics from incomplete retrieval, a protocol rejection or infrastructure
failure. Return a concrete semantic correction when supported; otherwise preserve the exact blocker
for the responsible role. Retrieval completeness and the division of responsibilities are described
in [platform-flow.md](references/platform-flow.md).

Report your own artifacts, confirmed/unknown conclusions and unresolved findings through the
Task's handoff. The Delivery host owns start authorization and lifecycle; independent acceptance
owns the final semantic verdict. A role completion or mechanical check is not that verdict.

Do not invoke historical artifacts listed in
[deprecated-artifacts.md](references/deprecated-artifacts.md).

## Map external API descriptions

Only when the selected Task includes API mapping and actually mounts
`r4-0-011-api-mapping-contract.json`, read that reference and its complete
`neutral_example`; the `interface_mapping` section of both authoring/role contracts applies
also to unified candidates. Use ordinary definitions and explicit edges, not a new platform kind.
A query interface can have no Class, Action or Operation. Keep system/interface/document versions,
request/response variants and stable field identities separate; use parent/member/element edges
for nested structures. Distinguish no body, unknown structure, missing, null and empty collection.

Bind fields to the specific business parameter/object position and call context. Do not equate
API IDs, business numbers or database keys; describe composite members and conversion direction.
Codes belong to a field and scope and may share business reference values with database mappings.
Preserve unknowns/conflicts, units, time zones and default/null meanings; do not execute conversions.

If using an Operation, reference the exact `(Operation, bindingId)` and read that binding's
location; never default to the first binding or keep a second authoritative location. Without
one, retain independent nonsecret location and scoped unknowns. Distinguish alternatives,
combination steps and partial capability; 004 owns ordering. A page is not all results, protocol
success is not business success, and async acceptance/task identity is not object completion.

Review affected references on field/code/result/binding changes; use distinct identities for
concurrent incompatible versions. Keep credentials, actual messages/runtime IDs and business rows
out of the model. Use governed entity/role/edge reads and controlled Operation projections;
incomplete retrieval does not prove absence. Static samples and fixture PASS do not establish
A10 real semantic acceptance, online availability or execution success.

## File and directory handoff (R4.3-013)

For large candidates, plans, results, reports or multiple files, prefer publishing an authorized
file or directory with `publish_handoff_material`; ordinary short text remains available, and
you choose the format. When no existing file write entry is available, use the scoped
`write_handoff_output(relative_path, content)` tool in your private output directory. This does
not publish, approve or execute the content. Send a purpose, material entry and recipient task
on your existing channel. `body_ref` selects one complete formal file (a directory requires
`path`); `material_refs` supplies supporting files without becoming a candidate or plan.

Use `list_handoff_material` and `read_handoff_material` to read actual snapshots. Follow
`next_cursor` or `next_offset` when incomplete; listing is separate from reading. A missing,
forbidden or damaged reference is a recoverable current-call error: report the concrete issue
and correct the reference. Never invent its contents or open another role's home, the full run
or hidden acceptance material. Existing source, approval, topology ownership, governed reads,
unknown and independent acceptance rules remain in force; delivery is not semantic PASS.

For `report_task_result`, use `summary_ref` for the complete formal summary; `body_ref` is the Team message body field.
