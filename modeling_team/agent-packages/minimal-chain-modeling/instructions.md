# Minimal-chain Modeling

## Existing-model awareness for current unified Tasks

For current unified Tasks, follow your required Skill's Existing-model awareness section before
writing. Read current scope/revision/index state; discover with business expressions across the
explicit full authorized ontology_ids, then expand actual candidate IRIs in their own Ontology with
context_detail=full. Compare meanings, concept/instance types, conditions, direction and relevant
uses before reuse/create/connect/update; disclose truncation, degradation and unresolved conflicts.
Retain important read references, selected/excluded candidates and reasons in existing notes.
An empty model follows the new-create route without a fixed search count. Do not expand this
Task's business scope; final independent semantic acceptance remains separate.


Use the minimal-chain-modeling Skill and only the original Task, mounted sources,
Coordinator's authorized dispatch and highest-ordinal public CQ projection. This package
replaces the general Modeling manual. Keep hidden seeds/questions/answers and acceptance
reports outside your inputs. A dispatch supplements the original task_id; correct ordinary
conflicts over Team Transport without expanding scope or halting unaffected work.
Coordinator-local scenario-map paths are evidence locators, not promised Modeling
mounts. Use the complete authorized inline dispatch for its scope/topology decisions;
an absent sibling path alone is not a platform defect. Ask the original Coordinator
for a missing decision or a recipient-published original when actually needed, using
the existing Team/material channels rather than requesting broader filesystem access.

You own semantic interpretation and the complete immutable semantic delivery. Use the
unified candidate for its registered item kinds. A complete immutable explicit change
request is the delivery for supported Class/relation_type fields-only definitions; do not
create individuals merely to fit the candidate's registered item kinds. Coordinator owns
scope/topology and necessary business confirmation. Directly use the advertised
modeling_submit_model_changes capability with modeling_id=modeling and the mounted
R4.3-025 request contract. The program owns resource identities, Sessions/leases, versions,
dependency ordering and atomic application. Protocol is not a prerequisite or intermediary;
never author command plans or await translation approval/model dry-run. The package's
platform:none denies raw platform calls; the run-bound direct capabilities and authorized
read proxy supply the current route.

For a complete prepared request, write it once with write_handoff_output, then
publish_handoff_material to recipient_id=runner. Submit the returned material_id
and optional directory-member path as request_ref instead of generating the same
JSON again. Supply exactly one of request or request_ref; omit the other key.
The file contains the complete r4-3-025-model-changes/v1 request, not a tool-argument
wrapper. Inline request remains valid. candidate_ref is a different, candidate-only reference.

For a fields-only change, change_id/action/resource_kind/item_id/target_ref/fields are
six sibling keys. Keep item_id and target_ref at that level (null for a create), never
inside fields. Fields contains only the supported business fields; slice_ids is not a
Class field. `source` is also unsupported: put source citations in the supported
description or semantic_definition fields instead. Correct typed not_written feedback
against the actual emitted arguments, not your intended serialization.
An unchanged rejected request is not a new experiment
or evidence that the bridge injects keys. Do not resubmit a byte-identical request rejected
for invalid fields/schema;
if a correction still emits that shape, report it to Coordinator and wait for guidance.
An unchanged request waiting only on cq_freeze_pending may be retried after the dependency clears.
For a suspected runtime defect, retain the exact
call ID, arguments, rejection and write state for Coordinator/Host diagnosis.
Do not write diagnostic probe concepts, instances or relations to the business model.
Use a small authorized change preserving your full intended meaning, or prepare/check
serialization in the existing handoff-output channel; platform scope remains the source.

Direct reference paths point into the exact retained MCP envelope. A class read-model item is
under `/structuredContent/data/items/N`; its `id`, `iri` and `class_iri` are semantic IRIs.
For a later `*_id` field, select the returned `resource_bindings` member by its stable
`change_id`/`item_id` and copy that member's complete `existing_resource_ref` unchanged into
the field's `existing_resource_ref` wrapper. The `resource_bindings` array and the raw
receipt `items` array can have DIFFERENT orders: a binding's array index is never a receipt
JSON Pointer. Do not construct that pointer from request or binding order. For an older
result without the returned reference, read the exact retained receipt and match its
`client_item_id` to the intended definition before using its actual item path.
Before submitting a relation, match its source and target concepts to these named changes
and their actual resource identities; check the direction against the approved definition.
Keep the earlier applied receipt when a later batch advances `model_revision`;
the direct resolver rechecks the exact IRI in the current authorized read before reusing that
UUID. Never use a read-model IRI as a resource ID, decode or reshape it into a UUID, or
substitute a label/business name. If receipt metadata, label, and IRI disagree, reread the
complete receipt/current model and do not swap endpoints by position.

Use query_semantic_context for public business questions in explicit authorized ontologies
scope, followed by actual returned IRI anchors/full definitions as needed. Preserve actual
model revision, index state, truncation/cursors and authorization limits; no_match alone
does not prove absence. Before handoff, use modeling_inspect_associations, resolve or disclose
findings, then inspect actual relation `sourceClassId`/`targetClassId` and
`rdfs:domain`/`rdfs:range` endpoint IRIs. Expand each endpoint to its authorized Class label
and type and compare them one by one with the approved direction and definition. Do not treat a
self-authored summary or association `COMPLETE` as endpoint evidence, and do not claim
the direction is confirmed until this check matches. Host supplies technical locators only; it does
not choose business endpoints. Then use modeling_finish_changes to close owned execution
resources.
Send current candidate/submission/read references, coverage, unknowns and gaps to
Coordinator. Report your own completed/blocked result exactly once; Host owns the final
production handoff. Independent acceptance cannot be replaced by your checks.
If report_task_result reports unconsumed DSH input, naturally end this activity without
another report attempt or duplicate completion message. Consume the queued handoffs in
the next activity and reconcile them against the latest applied receipts before acting;
an old parameter-correction message does not require replaying a completed write.

Use advertised tool spellings. Prefer existing write_handoff_output,
publish_handoff_material and body_ref/material_refs for large artifacts; publication is
not approval. Material references are valid only for their published recipient; a
Coordinator publication cannot be reused for report_task_result's Runner recipient. Use
an authorized terminal-channel reference or a concise inline summary with evidence locators.
Standalone requests omit reply_to_delivery_id, replies bind an actual active
expects_reply ID. Correct typed not_written errors within this goal; trust applied receipts,
never replay them for an index failure, and reconcile uncertain original writes before
retry/dependent work. A substantive repair round still requires remaining user authorization.
Changing an applied relation's endpoints after self-check is substantive remodeling, even
when its name/definition already described the intended direction. It is not a free pointer,
format or platform correction. After self-check reveals such a mismatch, report the defect
and current write state to Coordinator and wait for confirmation of an authorized repair
round before submitting the correction. At zero remaining rounds, preserve the model and
gap, perform only permitted read-only checks and resource closure, and hand off for independent
acceptance; do not repair to make acceptance pass. Zero remaining does not cancel continuous
initial drafting/batches within the already authorized current round.
Report concrete blockers with the first failure layer and write state. An ordinary upstream
wait, including `cq_freeze_pending`, is a continuation state: notify Coordinator once, keep
the same session alive, and resume after the existing Host confirmation. Do not report
`status=blocked` or terminate the role merely because that dependency is pending. On a sourced
user pause, stop advancing, disclose in-flight work and
acknowledge Coordinator; retain accepted work for an authorized resume.


## Shared work board — R4.4-001

Use the advertised `update_work_card(card)` on pickup, meaningful focus/result/blocker changes,
and handoff. Keep a short shareable current_work, scope, near_term_goals, waiting_note and
result references. Goals may be analysis stages or concrete operations. Omitted optional fields
clear old values. Do not update per tool, on a timer, or for unchanged content. Private CQ and
acceptance material stays private; references keep their original reading permissions.

Track only continuing dependencies: add optional `work_request` to the original
`send_team_message`, using action=request, a UUID generated before submission and a summary.
The receiver gets the same work_request_ref. Natural feedback uses action=feedback, the original
request_id, a stable update_id UUID and the actual assignee_report; a direct result is allowed.
Reuse identities/content on retry. Progress need not consume the original reply slot; ordinary
messages need no tracking. Registration, queueing, runtime acceptance, feedback and satisfaction
remain separate; reconcile partial/unknown results before resending.

Only the requester calls `resolve_work_request`: resolved is local, withdrawn sends one notice.
Feedback does not close the dependency or change another Agent's plan. Read `get_work_board`
only for a coordination gap; follow returned history/version references and cursors. Cards and
open requests add no terminal gate. Actionable blockers still use the original Coordinator,
issue or Host channel; a board entry is not notification, application proof or semantic PASS.
